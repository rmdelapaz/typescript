Warm-up: Session 2 Retrieval

  1. W1 const flats = { name: 'Sandpiper Flats', terrain: 'marsh' } passed where a Site is expected gives TS2345 ending in "Type 'string' is not assignable to type 'Terrain'". Why, and the fix? Answer: The property was inferred as string (a const object's properties can change); annotate where it is created: const flats: Site = ….
  2. W2 spotsTaken || 'unknown' with spotsTaken = 0: what prints, and what should it be? Answer: unknown; use ??, which falls back only on null and undefined.
  3. W3 const meta = JSON.parse(text): what is its type, and what does the course write instead? Answer: any; the course writes const meta: unknown = JSON.parse(text) and narrows it before use.
  4. W4 In LoadState, which property tells the members apart, and what is it called? Answer: kind: the discriminant of a discriminated union.

2.3 · Functions and Generics: self-check

Q1
What does node scratch.ts print?
function spotsText(left: number, unit = 'spots'): string {
  return `${left} ${unit} left`
}
console.log(spotsText(1, 'spot'), '/', spotsText(4))
A) 1 spots left / 4 spots left
B) 1 spot left / 4 undefined left
C) 1 spot left / 4 spots left
D) Nothing: npm run check reports TS2554 first
Why: A default parameter is used only when the caller leaves the argument out; spotsText(4) gets 'spots'. From the caller's side it is simply optional: the hover shows unit?: string (Lesson 2.3, Optional, Default and Rest Parameters).
A is wrong: The first call passes 'spot', which replaces the default.
B is wrong: The default fills the gap: never undefined inside the function.
D is wrong: One or two arguments are both allowed (Expected 1-2 arguments).
Q2
Why does npm run check reject function eventLine(town?: string, title: string)?
A required parameter cannot follow an optional one (TS1016): with one argument, TypeScript could not tell which one you meant. Put the optional parameter last, give it a default, or use an options object
Why: The lesson's rule for optional parameters, with its real error TS1016. An options object ({ showStatus = false, prefix = '-' }: LineOptions = {}) removes the ordering problem altogether, and it is exactly how React props work (Lesson 3.2).
Q3
With type EventFormatter = (event: CleanupEvent) => string and printAll(list, format: EventFormatter), which call does npm run check accept?
A) printAll(events, (event) => event.capacity)
B) printAll(events, () => 'one more cleanup')
C) printAll(events, (title: string) => title)
D) printAll(events, (event, page: number) => event.title)
Why: A function that takes FEWER parameters fits a function type (it simply ignores the cleanup); the return type must still be a string. The lesson's two failing calls are A (returns a number) and C (the wrong parameter type).
A is wrong: Returns a number: TS2322, "the expected type comes from the return type of this signature".
C is wrong: TS2345: Types of parameters 'title' and 'event' are incompatible.
D is wrong: A second REQUIRED parameter that printAll never passes: not assignable.
Q4
groupBy<T, K>(items: T[], keyOf: (item: T) => K): Map<K, T[]> is called as groupBy(events, (event) => event.status) with events: CleanupEvent[]. What does the hover show it returns?
A) Map<string, CleanupEvent[]>
B) Map<K, T[]>
C) Map<any, any[]>
D) Map<EventStatus, CleanupEvent[]>
Why: TypeScript infers both type parameters from the arguments: T from the array, K from what the callback returns. The labeled bin reads its label from what you put in (Lesson 2.3, project Step 4 and its screenshot).
A is wrong: status is an EventStatus, not any string.
B is wrong: The type parameters are filled in at the call.
C is wrong: Generics keep the checks: that is the point over any.
Q5
findById<T extends { id: string }> is called with a list of bag counts. tsc prints this. What does it mean?
scratch.ts:22:22 - error TS2345: Argument of type 'number[]' is not assignable to parameter of type '{ id: string; }[]'.
A) The constraint is doing its job: numbers have no id, so they cannot be searched by id
B) findById needs an explicit type argument: findById<number>(...)
C) The constraint must be removed for numbers
D) bagCounts needs an annotation
Why: extends reads "has at least". The constraint lets the body use item.id AND stops calls with items that have none, at the call, where the mistake is (Lesson 2.3, Constraints).
B is wrong: T would still have no id: the call stays wrong.
C is wrong: Then the body's item.id is TS2339 again.
D is wrong: Its type, number[], is inferred correctly; it just is not a list of things with ids.
Q6
This statusLabel gets TS2366 with its : string. What happens if you delete : string?
type EventStatus = 'draft' | 'scheduled' | 'completed' | 'cancelled'

function statusLabel(status: EventStatus): string {
  if (status === 'scheduled') {
    return 'Scheduled'
  }
  if (status === 'completed') {
    return 'Completed'
  }
}

console.log(statusLabel('draft'))
The check goes silent (the inferred return type becomes "Scheduled" | "Completed" | undefined), and statusLabel('draft') quietly returns undefined
Why: A written return type makes TypeScript check every path against the promise, inside the function. That is the course's reason to write return types on helpers other code relies on (Lesson 2.3, Common Mistakes; Lesson 2.2's bonus question).

2.4 · Typing Real Data: self-check

Q7
In ts-lab you change import type { CleanupEvent, Volunteer } from './shapes.ts' to import { CleanupEvent, Volunteer } from './shapes.ts'. What happens?
A) npm run check reports TS1484 (and TS5097), and node functions.ts stops with does not provide an export named 'CleanupEvent'
B) Nothing: both forms do the same
C) Only the editor complains; Node runs it
D) node functions.ts first runs shapes.ts and prints its eight lines
Why: Types are stripped before Node runs the files, so at run time there is no CleanupEvent to import. verbatimModuleSyntax makes the check ask for import type, so the tools can delete the line (Lesson 2.4, What happens without type).
B is wrong: They differ exactly at run time.
C is wrong: Node fails with a SyntaxError.
D is wrong: With import type, shapes.ts never runs; without it, the import fails before anything prints.
Q8
What does node scratch.ts print, and is npm run check silent?
function isText(value: unknown): value is string {
  return typeof value === 'string'
}
const words: unknown[] = ['gloves', 3, 'bags', null]
const texts = words.filter(isText)
console.log(texts.map((word) => word.toUpperCase()))
[ 'GLOVES', 'BAGS' ], and yes, the check is silent
Why: filter has an overload for type guards: passing isText makes the result string[], so word.toUpperCase() is allowed. With a plain boolean return type, texts would be unknown[] and the check would refuse (Lesson 2.4, A type predicate says what "true" means).
Q9
A guard promises value is number but its body is return value !== undefined. What does TypeScript do?
A) Reports TS2322 in the guard's body
B) Checks the value at run time and throws
C) Compiles without a word, and treats every value that passes (even the text 'twelve') as a number
D) Refuses to narrow with a guard it cannot verify
Why: A type predicate is a promise TypeScript cannot check: it trusts the body completely. So a guard checks every property its type promises and is tested with good and bad data; Module 8 hands the job to Zod (Lesson 2.4, the stop sign).
A is wrong: The body returns a boolean, which is all TypeScript asks.
B is wrong: Types never run.
D is wrong: It narrows exactly as the predicate says.
Q10
type StatusLabels = Record<EventStatus, string>, and const labels: StatusLabels = { draft: 'Draft', scheduled: 'Scheduled', completed: 'Completed' }. What does the check say?
A) Nothing: Record allows any keys
B) TS2353: 'cancelled' is an extra property
C) Nothing at check time; reading labels.cancelled crashes later
D) An error: property 'cancelled' is missing
Why: A Record over a union insists on EVERY key, which is why the lesson calls it a favorite for lookup tables: add a fifth status and TypeScript lists every table that needs it (Lesson 2.4, Utility Types; Lesson 3.3 uses one).
A is wrong: Record<string, string> would; a union of keys is exact.
B is wrong: Nothing extra is there; one is missing.
C is wrong: The check catches it before anything runs.
Q11
With noUncheckedIndexedAccess on and const siteIds: string[], which line is NOT affected?
A) const firstId = siteIds[0] (its type)
B) for (const id of siteIds) { console.log(id.toUpperCase()) }
C) siteIds[2].toUpperCase()
D) return items[0] in a function promising T
Why: Reading by index may find nothing, so it gives string | undefined; a for...of loop only visits items that exist, so id stays a string (Lesson 2.4, The setting that makes items[0] honest).
A is wrong: It becomes string | undefined.
C is wrong: TS18048 (or TS2532): possibly undefined.
D is wrong: TS2322: Type 'T | undefined' is not assignable to type 'T'.
Q12
You put API_URL=http://localhost:4000 (no prefix) in .env.local and read import.meta.env.API_URL in the HQ. What happens?
A) It works: every variable in .env.local reaches the code
B) The check reports TS2339 (only VITE_API_URL is declared), and at run time the value is undefined: Vite passes only VITE_ names
C) Vite keeps it secret on the server
D) The build fails with a Vite error
Why: Only VITE_-prefixed variables reach browser code, and with strictImportMetaEnv every name must be declared in vite-env.d.ts. And whatever does reach the code is public: nothing in the front end is secret (Lesson 2.4, Environment Variables).
A is wrong: Vite filters by the prefix, on purpose.
C is wrong: There is no server here: everything ends up in the browser or nowhere.
D is wrong: Vite builds; the value is simply missing (and the type check catches the name first).

The Lesson Pages' Own Quick Quizzes

Lesson 2.3 · Functions and Generics
  1. C TS2554: Expected 2-3 arguments, but got 1: count and word are required and plural has a default, so a call needs two or three arguments. The follow-up line says an argument for word was not provided.
  2. A (event: CleanupEvent) => string: A function type looks like an arrow function with types and no body: the parameters in parentheses, then the arrow and the return type. Give it a name with a type alias, such as EventFormatter.
  3. C string | undefined: TypeScript infers T from the argument: an array of strings, so T is string and the result is string or undefined (the array might have been empty).
  4. B Add a constraint: findById<T extends { id: string }>: A constraint tells TypeScript that every T has a string id, so item.id is allowed inside, lists without ids are rejected at the call, and each call still returns its own type.
  5. D Mistakes are reported inside the function, where the bug is, and callers get a clear promise: A written return type is a promise the function is checked against, so a mistake is reported on the line inside the function (as with TS2741 in paginate) instead of at callers in other files, and the signature documents what callers can rely on.
Lesson 2.4 · Typing Real Data
  1. C Node removes it with the other types, so shapes.ts never runs: A type-only import is removed with the other types, so shapes.ts never runs. With a plain import, Node would ask shapes.ts for a CleanupEvent at run time and fail, which is what TS1484 warns about.
  2. B When the function returns true, TypeScript treats the argument as a Volunteer: The function still returns a boolean. The predicate is a promise: after a true answer, TypeScript treats the argument as a Volunteer. TypeScript trusts it, so the body must really check.
  3. D CleanupEvent | undefined: Nothing guarantees an item at a given position, so indexing adds undefined. That is the TS2532 on events[0].title, fixed with ?. and ??.
  4. A On a server that calls the map service for the app, never in the front end: Vite copies every VITE_ variable into the JavaScript that every visitor downloads, so the front end cannot keep a secret. A server (like shoreline-api) keeps the key and calls the map service on the app's behalf.
  5. C Partial<Omit<CleanupEvent, 'id'>>: Omit removes the id, and Partial makes everything that is left optional. The API's EventChanges type is built the same way from NewEvent.

Exit Ticket

  1. Function type: (event: CleanupEvent) => string (usually named: type EventFormatter = …).
  2. The constraint: the body reads item.id; extends { id: string } guarantees every T has one and refuses lists without ids (TS2345 at the call).
  3. getJSON: throws Unexpected data from GET /api… and never returns unchecked data; everything past the door can trust its type.

Common Wrong Answers and What They Reveal

  • Q1 A or B. Mixes up default and passed values. Run both calls, hover the function.
  • Q3 A or C. Believes any function fits a function type. Show the TS2322 "expected type comes from the return type of this signature".
  • Q4 A or C. Thinks generics widen. Hover the call in the lesson's screenshot.
  • Q7 B or C. Has not seen that types vanish at run time. Run the plain import: SyntaxError.
  • Q9 A or D. Expects TypeScript to verify guards. Write the lying guard and run it with 'twelve'.
  • Q12 A or C. Thinks .env files are private to the app. Grep the built file for the address.
