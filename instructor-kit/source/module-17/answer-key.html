A1
An effect fetches one cleanup with getEvent(eventId, controller.signal), lists [eventId] as its dependencies and returns () => controller.abort(). What does that cleanup function protect against? (1 point)
A) Nothing in the browser: it only matters in tests
B) A slow answer for the previous eventId arriving late and overwriting the page after the id changed (and a request left running after the component is gone)
C) The API answering with a 500
D) Strict Mode running the effect twice in production
Why: Each new id runs the cleanup first: the old request is aborted, and the .catch returns early when controller.signal.aborted, so only the latest answer reaches the state (Lesson 4.1: race conditions).
A is wrong: Race conditions happen in the browser whenever answers arrive out of order.
C is wrong: A 500 is an answer: fetch resolves with ok false, the request function turns it into an ApiError.
D is wrong: Strict Mode's double run happens only in development.

A3
The HQ's useApi(key, load) lists key in its effect's dependencies but reads load through useEffectEvent. Why? (1 point)
A) A new key means new data, so the effect must run again; the caller's load is usually an inline arrow, a new function on every render, which would restart the effect (and the request) on every render
B) useEffectEvent makes the request faster
C) Hooks may not take functions as arguments
D) TypeScript cannot type load any other way
Why: Key = what to load, load = how. Listing the arrow as a dependency made the first version send hundreds of requests a second with tsc and the linter silent (Lesson 4.2). useEffectEvent always calls the latest load without being a dependency.
B is wrong: It changes when the effect runs, not how fast the request is.
C is wrong: Hooks take any arguments; useApi itself takes a function.
D is wrong: load is typed (signal: AbortSignal) => Promise<T> either way.

A5
A component reads its data with use(promise) inside a <Suspense> boundary. Where must that promise come from? (1 point)
A) From a call such as getEvent(id) in the component's body, so every render has fresh data
B) From a try block around use, so errors are caught
C) From an effect's cleanup function
D) From something stable that hands back the SAME promise for the same id: a cache (Lesson 4.4's eventPromises) or a route loader (Lesson 6.3)
Why: A promise created while rendering is a new pending promise on every render: the component suspends forever while requests keep going out. use also may not sit in a try/catch: errors go to an error boundary.
A is wrong: Each render would suspend on a new promise: the fallback forever.
B is wrong: use cannot be called in a try/catch (the linter reports an error); a boundary catches the rejection.
C is wrong: A cleanup runs when the effect is undone; it has nothing to do with use.
A6
An ErrorBoundary wraps <EventDetails>. Which error does it NOT catch? (1 point)
A) An error thrown in the onClick handler of a button inside EventDetails
B) An error thrown while EventDetails renders
C) A rejected promise that EventDetails reads with use()
D) An error thrown while a child of EventDetails renders
Why: Boundaries catch errors thrown during rendering (a rejected use() throws while rendering). Event handlers and async code run after rendering: catch those in the handler and show the message with state.
B is wrong: Rendering errors are exactly what a boundary catches.
C is wrong: use throws the rejection while the component renders: the boundary catches it.
D is wrong: The nearest boundary above catches errors from the whole subtree.

C is wrong: The default branch handles it: nothing is thrown.

A8

B) The session saved in sessionStorage

A9

A) The Profiler counts each render twice in production
B) Rendering means calling the components and comparing the result; React changes the page only where the result differs
C) The browser caches the DOM between key presses

A10

B) Generic constraints are not allowed in .tsx files

A15
A page keeps const [loading, setLoading] = useState(true), const [error, setError] = useState<string | null>(null) and const [sites, setSites] = useState<Site[] | null>(null). Name one problem with three separate pieces of state, and write the type Lesson 4.1 uses instead. (2 points)
Three booleans/nullables allow impossible combinations (loading and an error at once, an old error left over next to new data), and every update must remember to set all three. Lesson 4.1: type LoadState<T> = { kind: 'loading' } | { kind: 'failed'; message: string } | { kind: 'ready'; data: T }, one useState<LoadState<Site[]>>({ kind: 'loading' })
Marking (2 points): 1 point: a real problem (impossible or contradictory combinations, or three setters to keep in step). 1 point: a union with a discriminant (kind or similar) whose ready member alone carries the data and whose failed member carries the message. A union without data in it, or any, scores 0 for the type.
A16
A timer's reducer ends its switch with default: return assertNever(action), and tsc prints the error below. What does it tell you, and what is the fix? (2 points)
import { assertNever } from './utils/assertNever.ts'

interface TimerState {
  running: boolean
  seconds: number
}

type TimerAction =
  | { type: 'start' }
  | { type: 'tick' }
  | { type: 'pause' }
  | { type: 'reset' }

export function timerReducer(state: TimerState, action: TimerAction): TimerState {
  switch (action.type) {
    case 'start':
      return { ...state, running: true }
    case 'tick':
      return state.running ? { ...state, seconds: state.seconds + 1 } : state
    case 'pause':
      return { ...state, running: false }
    default:
      return assertNever(action)
  }
}
src/review.ts:23:26 - error TS2345: Argument of type '{ type: "reset"; }' is not assignable to parameter of type 'never'.
Found 1 error in src/review.ts:23
No case handles the 'reset' action, so in the default branch action is still { type: 'reset' } instead of never. Fix: add case 'reset': return { running: false, seconds: 0 } (a new state object), and the error disappears.
Marking (2 points): 1 point: reads the message (the 'reset' action has no case; whatever reaches default must be never). 1 point: a case 'reset' that returns a new state. Removing the action from the union is accepted only with a reason; deleting assertNever or adding as never scores 0 for the fix.
A17
A teammate says: "/volunteers is protected: guests and volunteers never see its link in the header." Explain in two or three sentences why that is not enough, and what the HQ does instead (both sides). (2 points)
Anyone can type the address, follow an old link or call the API directly: hiding a link is courtesy, not protection. The HQ puts the route under the organizersOnly guard loader, which runs before the page renders (guests are redirected to /sign-in?next=..., volunteers get a 403 answer), AND shoreline-api checks the token on every request (401 / 403): the API is the lock.
Marking (2 points): 1 point: the address or API can be reached without the link (hiding is not security). 1 point: names both protections, the guard loader in the router (redirect for guests and/or 403 for other roles) and the API's own check. Only one of the two: 1 point total.

Q1
In development, the Network tab shows each page's request twice, the first one canceled. In the preview build there is one. Why?
A) The API answers slowly the first time
B) A missing dependency array
C) Strict Mode runs each effect, its cleanup and the effect again in development; the cleanup aborts the first request
D) The browser retries every failed request
Why: Strict Mode's start, clean up, start is development only: it proves the cleanup works. The aborted request is the cleanup doing its job (Lesson 4.1).
A is wrong: Speed has nothing to do with it: the count is always two.
B is wrong: No array would send hundreds of requests, not two.
D is wrong: The first request was canceled by our own cleanup, not retried.
Q2
Without an annotation, what is the type of error in .catch((error) => ...), and what does the HQ write instead?
A) Error; nothing to change
B) any; the HQ writes (error: unknown) and narrows with instanceof ApiError
C) ApiError; the HQ casts it
D) never; catch never runs
Why: A promise can reject with anything, and .catch's parameter is any, so error.no.such.thing compiles. unknown forces a check first: describeError(error) narrows with instanceof.
A is wrong: Anything can be thrown, not only Error objects.
C is wrong: TypeScript cannot know the rejection's type.
D is wrong: Catch runs whenever the promise rejects.
Q3
A custom Hook returns early (if (!query) return null) before it calls useEffect. Which check reports it?
A) npx tsc -b, with an error on the return
B) npm run lint: oxlint's rules-of-hooks error, "called conditionally"
C) React, as a TypeScript error in the browser
D) Nothing: Hooks may be called conditionally inside custom Hooks
Why: Hooks must be called in the same order on every render, in custom Hooks too. tsc is silent; oxlint's react-hooks(rules-of-hooks) reports an error (Lesson 4.2).
A is wrong: Types are fine: tsc says nothing.
C is wrong: The browser never sees TypeScript.
D is wrong: Custom Hooks follow the same rules as components.
Q4

B is wrong: State would render again on every start and stop for a value nobody sees.
C is wrong: Still no argument: the same TS2554.
D is wrong: Still no argument, and any turns checking off.
Q5
On the event page, why does the back link sit OUTSIDE the ErrorBoundary and <Suspense> that wrap the details?
A) Links cannot be inside a boundary
B) So it renders faster
C) Error boundaries remove everything in the app

A is wrong: Anything can be inside.
B is wrong: Placement is about what stays on screen.
C is wrong: Only without any boundary does React remove the whole app.
Q6
Why must a reducer return a new object instead of calling state.marks.set(...) and returning state?
React compares the old and new state with Object.is: the same object means "nothing changed", so the screen does not update (and Strict Mode's second call would apply the change twice). A copy with the change keeps the old state intact; ReadonlyMap makes tsc refuse set
Why: Lesson 5.1's rules: pure, no in-place change, no side effects, the same state back only when nothing changed.
Q7

A) The cleanup that one EventCard shows
B) The text in the events search box
C) The signed-in session, read by the header, the event cards and the data Hooks at many depths
D) The open/closed state of one dialog
Why: Context is for values many components at different depths need. A value one component or one parent passes down is clearer as a prop or local state (Lesson 5.2's context vs props table).
A is wrong: A plain prop from the list.
B is wrong: Page state (and, after 6.2, the address).
D is wrong: Local state of the component that owns the dialog.

Common Wrong Answers and What They Reveal

  • A2 B (return the promise). Has not read the message's second line: an effect returns nothing or a cleanup. Lesson 4.1's async-effect card again.
  • A4 D (as HTMLInputElement). Reaches for assertions: the same habit as as StatusFilter in A12. Ask: when is the ref null?
  • A7 A (tsc reports it). Believes the switch is checked without assertNever: A16 tests the fixed version.
  • A14 A (redirect to sign-in). Mixes up 401 and 403: guests sign in, signed-in people without the role get 403.
  • Self-check 3 A (tsc). Thinks the type checker enforces the Rules of Hooks: it is the linter's job.
