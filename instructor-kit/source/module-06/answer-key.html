3.3 · Lists and Conditional Rendering: self-check

Q1
Where does the key go in events.map((event) => <li><EventCard event={event} /></li>)?
A) Inside EventCard, on its article
B) On the <li>, the element the map callback returns
C) On the <ul> around the list
D) Anywhere inside the item: React finds it
Why: React compares the elements map returns, so the key belongs on the <li> (key={event.id}). A key inside EventCard is on the wrong element, and EventCard never receives a key prop anyway (Lesson 3.3, Putting the key inside the item component).
A is wrong: EventCard draws one item; the list's items are the <li> elements.
C is wrong: The <ul> is one element, not an item of the list.
D is wrong: React reads the key only on the elements in the array.

B) A TypeScript error, because a number is not an element

Why: && returns its left side when it is falsy, and 0 is a number React draws. tsc and oxlint both accept it (real output: <div>0</div>). Write waiting.length > 0 && ... (Lesson 3.3, The 0 trap).
A is wrong: false, null and undefined draw nothing; 0 draws.
B is wrong: A number is a valid ReactNode.

Q4

Why: A component may return undefined, so a switch with a missing case compiles (the kit ran it: npx tsc -b printed nothing). A lookup table would complain; a switch does not until Lesson 5.1's never check (Lesson 3.3, Exercise 3).

B is wrong: undefined draws nothing; nothing throws.
C is wrong: No such rule is on in the course's oxlint.

Q7
tsc prints this for StatusPicker. Which line made TypeScript reject 'finished'?

B) useState<StatusFilter>('all'): the type argument holds every update to the union
C) type StatusFilter = EventStatus | 'all', because it has five words
D) The button's type="button"
Why: useState('all') would widen the state to string and accept any word; the type argument makes the setter take a SetStateAction<StatusFilter> (Lesson 3.4, When useState Needs a Type).

Q8

src/Scratch.tsx:7:55 - error TS2322: Type 'string' is not assignable to type 'never'.
never[] (an empty array tells TypeScript nothing); useState<string[]>([])
Why: An array that can hold nothing at all: every element you add is 'not assignable to never'. Say what it will hold with a type argument (Lesson 3.4, The state starts as an empty array).
Q9
A named handler, function handleChange(event) { setQuery(event.target.value) }, gives this. What does the parameter need?
src/Scratch.tsx:6:25 - error TS7006: Parameter 'event' implicitly has an 'any' type.
A) event: any
B) event: Event
C) event: ChangeEvent<HTMLInputElement>, imported with type from react
D) Nothing: move it into a useState call
Why: A handler written in place (onChange={(event) => ...}) gets its type from the prop; a named function has no context, so annotate it with React's event type for the element (Lesson 3.4, Typed Event Handlers).
A is wrong: any silences TS7006 and switches the checks off.
B is wrong: React passes its own synthetic ChangeEvent, not the DOM's Event: the types do not match.
D is wrong: Hooks hold state; they do not type handlers.
Q10
A terrain menu and the list of sites it filters sit side by side inside SiteFinder. Where does the chosen terrain live?
A) In the menu component, where the choice happens
B) In a module-level variable both can read
C) In both components, kept in sync with effects
D) In SiteFinder, the closest common parent, passed down as props
Why: Siblings cannot reach into each other; data flows down. The parent holds the state, the menu becomes a controlled component with a value and an onChange callback, and the list is derived (Lesson 3.4, Where State Lives; Lab 3.4, Task 2).
A is wrong: Then the list never hears about it (the lab's starter).
B is wrong: A plain variable does not make React draw again.
C is wrong: Two copies of one fact fall out of step; keep one source of truth.
Q11
npm run lint prints this (an error, not a warning). What does it ask you to do?
× react-hooks(rules-of-hooks): React Hook "useState" is called conditionally. React Hooks must be called in the exact same order in every component render.
A) Move the useState call above the early return, so it runs on every render
B) Rename the Hook so it starts with use
C) Wrap the useState call in a useEffect
D) Add a key to the textarea
Why: React tells a component's state apart by the order of its Hook calls; a Hook after an early return runs on some renders and not others (Lesson 3.4, The Rules of Hooks).
B is wrong: useState already starts with use.
C is wrong: Hooks may not be called inside other Hooks' callbacks either.
D is wrong: Keys are for lists.
Q12
A search box stores both query and the filtered list, and handleChange does setQuery(value) then setVisible(events.filter(... includes(query) ...)). Why is the count always one keystroke behind, and what is the fix?
query in the handler is this render's snapshot, the text BEFORE the keystroke; keep only query in state and derive the list during render
Why: The setter asks for a new render; it does not change the variable you already have. Less state is the fix: one source of truth, nothing to fall out of date (Lesson 3.4, Derive, don't store; Lab 3.4, Task 3).

import type { DebrisCount } from './api/types.ts'
import { debrisLabels } from './labels.ts'

interface DebrisListProps {
  items: DebrisCount[]
}

// Task 1: the counts as a list, biggest first, each with its label (Task 2's table).
export function DebrisList({ items }: DebrisListProps) {
  if (items.length === 0) {
    return <p className="empty-state">Nothing counted yet.</p>
  }

  const sorted = items.toSorted((a, b) => b.count - a.count)
  return (
    <ol className="debris-list">
      {sorted.map((item) => (
        <li key={item.category}>
          {debrisLabels[item.category]}: {item.count}
        </li>
      ))}
    </ol>
  )
}
// Task 3: what the crew hears on the morning of a cleanup, and who is waiting for a spot.
export type TideCall =
  | { kind: 'go' }
  | { kind: 'delayed'; minutes: number }
  | { kind: 'cancelled'; reason: string }

interface TideBannerProps {
  call: TideCall
  waiting: string[]
}

export function TideBanner({ call, waiting }: TideBannerProps) {
  return (
    <section aria-label="Tide call">
      <CallLine call={call} />
      {waiting.length > 0 && <p>{waiting.length} people are waiting for a spot.</p>}
    </section>
  )
}

function CallLine({ call }: { call: TideCall }) {
  switch (call.kind) {
    case 'go':
      return <p>On as planned.</p>
    case 'delayed':
      return <p>Starts {call.minutes} minutes late: the tide is still high.</p>
    case 'cancelled':
      return <p role="alert">Cancelled: {call.reason}</p>
  }
}

The solution's picker update, the controlled menu's handler and the parent:

import { useState } from 'react'
import type { Site } from './api/types.ts'
import { TerrainFilter, type TerrainChoice } from './TerrainFilter.tsx'

// Task 2: the state lives in the closest common parent; the visible list is derived, never stored
export function SiteFinder({ sites }: { sites: Site[] }) {
  const [terrain, setTerrain] = useState<TerrainChoice>('all')
  const visible = sites.filter((site) => terrain === 'all' || site.terrain === terrain)

  return (
    <>
      <TerrainFilter value={terrain} onChange={setTerrain} />
      <p role="status">
        Showing {visible.length} of {sites.length} sites.
      </p>
      <ul>
        {visible.map((site) => (
          <li key={site.id}>{site.name}</li>
        ))}
      </ul>
    </>
  )
}

What each task shows: (1) push + set hands React the same array (no redraw) and useState([]) is never[]; the fix is useState<string[]>([]) and setJoined((current) => current.includes(id) ? current.filter(...) : [...current, id]); (2) the menu becomes controlled and narrows with isTerrain (no as), the parent holds useState<TerrainChoice>('all') and derives visible; (3) the stored list filtered with the previous keystroke's text (after g, then gl: it shows the matches for g, four); deriving removes the bug and a piece of state. Accept onChange={(event) => onChange(isTerrain(event.target.value) ? event.target.value : 'all')} inline: it narrows the same way.

The Lesson Pages' Own Quick Quizzes

Lesson 3.3 · Lists and Conditional Rendering
  1. B To match each item with the one it drew last time, so it can keep, update, move, add or remove items correctly: React compares the new list with the last one by key: same key means the same item, kept and updated; a new key is created; a missing key is removed. That is why keys must be stable and unique among siblings.
  2. D A div containing the character 0: The && expression evaluates to its falsy left side, the number 0, and React draws numbers. Write signups.length greater than 0 so the left side is a real boolean.
  3. C npx tsc -b reports TS2741: property 'draft' is missing: Record with a union of keys requires every key. tsc reports TS2741, Property draft is missing, so the table cannot fall out of date with the type.
  4. A { kind: 'failed'; message: string }: Checking the discriminant narrows the union to the one member whose kind is failed, so state.message is a string you can read safely.
  5. D key={event.id}: The API's id is unique, comes from the data and never changes for the same event, which is exactly what a key needs to be.
Lesson 3.4 · State and Events
  1. C 1: All three calls read the snapshot of this render, where bags is 0, so each asks for 1. Updater functions that add one to the current value would chain and give 3.
  2. A string: The DOM gives every select value as a string, whatever the options say. That is why EventFilters checks it with isEventStatus before passing it up as a StatusFilter.
  3. D In EventsPage, the closest common parent: EventsPage is the closest common parent of everything that reads or changes query. It passes the value down as props and a callback for changes, and derives the lists from it.
  4. B never[]: An empty array literal gives TypeScript nothing to go on, so the state is never[] and adding any id is a TS2322 error. Write useState with a type argument, such as an array of string.
  5. A npx tsc -b reports TS2322, and in the browser React stops with "Too many re-renders": setOpen(true) runs while the button is drawn and returns void, which is not a MouseEventHandler (TS2322). Run anyway, it sets state during render, again and again, until React stops with Too many re-renders.

Exit Ticket

  1. The table: const terrainLabels: Record<Terrain, string> = { sand: 'Sandy beach', rocky: 'Rocky shore', marsh: 'Tidal marsh', mixed: 'Sand and rocks' } (any labels; the four keys are what TypeScript checks).
  2. useState('all'): the state widens to string, so any word is accepted (and the errors appear where the wider type is used); useState<StatusFilter>('all').
  3. The two questions: can it be worked out from what you already have (then derive it, it is not state)? Who reads it and who changes it (put it in the closest component above all of them, no higher)?

Common Wrong Answers and What They Reveal

  • Q1 A (key inside EventCard). Thinks of the key as the item's own data; show that React reads keys only on the array map returns.
  • Q3 A (an empty div). Treats 0 like false. Rerun the lesson's two renders: <div>0</div>.
  • Q4 A (tsc reports it). Over-trusts the compiler with switches; contrast with the table's TS2741.
  • Q7 A or C. Has not connected the type argument with what the setter accepts; hover the setter with and without it.
  • Q10 A or C. Keeps state where the event happens; draw the round trip.
  • Q12 "React is slow" or "setState is asynchronous". Close, but the model is the snapshot: the handler reads this render's value.
