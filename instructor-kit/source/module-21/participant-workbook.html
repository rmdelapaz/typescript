Lesson

9.1

Testing Components

By the end you can
  • Explain what unit, component and end-to-end tests each check in the HQ, and why tests should describe what people see rather than how the code works inside
  • Set up Vitest, jsdom and React Testing Library in a Vite project, sharing the app's own vite.config.ts
  • Write unit tests for functions and Zod schemas with describe, it, expect, it.each and typed sample-data factories
  • Render components and find elements the way people do, by role and accessible name, choosing between getBy, queryBy and findBy
  • Build a typed renderWithProviders helper (cache, sign-in, router) and reset the app's module-level state between tests
  • Read a failing test's output and decide whether the test or the app is wrong
Key ideas
  • Three sizes: unit (a function), component (a component in jsdom's pretend page), end-to-end (the whole app in a real browser, Lesson 9.3). Most of a healthy suite is the first two.
  • Vitest reads vite.config.ts: the same plugins as the app (the React Compiler included); environment: 'jsdom', setupFiles, include. It strips types without checking them: tsc -b still checks your tests.
  • describe / it / expect, Arrange-Act-Assert; toBe for single values, toEqual for objects and arrays; it.each([...] as const) for tables.
  • See every test fail once, then ask: is the test wrong, or the app?
  • Queries: by role and name first, then label, then text, test id last; getBy (here now), queryBy (not here), findBy (soon). A query that cannot find something is often an accessibility bug.
  • A render helper puts the app's providers around a component; module state (cache, session, stores, storage) is reset after every test.
Worked example: a failure is information

The lesson's first test with Jul changed to July on purpose:

 FAIL  src/utils/format.test.ts > formatDate > shows a day of the crew calendar with its weekday
AssertionError: expected 'Sat, Jul 4, 2026' to be 'Sat, July 4, 2026' // Object.is equality
Expected: "Sat, July 4, 2026"
Received: "Sat, Jul 4, 2026"

Read it like a compiler error: the test (describe > it), the expected value, the received one, the line. Then decide: the app writes short month names on purpose, so the test is wrong. Change the app to long names instead and two tests fail: then the app is wrong. A red test is information, not a verdict on you.

Glossary

TermMeaning
unit / component / end-to-end testOne function / one component in a pretend page / the whole app in a real browser
VitestThe test runner built for Vite: reads vite.config.ts, runs *.test.ts(x)
jsdomA pretend browser page inside Node: elements, events, focus; no layout, no pictures
React Testing Libraryrender() and screen with queries that find elements the way people do
jest-domExtra matchers for elements (toBeInTheDocument, toHaveFocus); import @testing-library/jest-dom/vitest
matcherThe second half of a check: .toBe(x), .toEqual(x), .toHaveLength(n)
Arrange-Act-AssertSet up the input, run the code, check the result
it.eachOne test per row of a table; %s puts the row into the name
test factoryA function that returns complete, typed sample data (makeEvent(changes))
getBy / queryBy / findByHere now (throws) / not here (null) / soon (waits)
accessible nameWhat a screen reader announces with an element's role
setup fileRuns before each test file (setupFiles): jest-dom, cleanup, resets
render helperRenders a component inside the app's providers (renderWithProviders)
test isolationEach test starts from the same state, whatever ran before it
