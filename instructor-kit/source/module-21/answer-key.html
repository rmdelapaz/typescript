Checkpoint 3: Model Answer

The tests are the specification for C1 and C2; the model solution is labs/module-21/checkpoint-3/solution/. Every output below is a real run of labs/check_labs.py (a fresh copy of the folder, Node 24, a learner's terminal).

C1: src/schemas.ts
import { z } from 'zod'

const HOURS = 'Hours must be a whole number from 1 to 12.'

/** C1: the "Add a shift" form. Every value arrives as text; the output is ready for the API */
export const shiftFormSchema = z.object({
  volunteer: z.string().trim().min(2, 'Add a name (2 letters or more).'),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, 'Pick a date.'),
  hours: z.coerce.number<string>({ error: HOURS }).int(HOURS).min(1, HOURS).max(12, HOURS),
})

/** What the form holds (text) and what the schema hands on (a number of hours) */
export type ShiftFormValues = z.input<typeof shiftFormSchema>
export type ShiftFormData = z.output<typeof shiftFormSchema>

z.coerce.number<string>(...) says the input is text, so ShiftFormValues has hours: string and ShiftFormData hours: number. The { error: HOURS } option gives the not-a-number case ('lots') the same message as the other three checks.

C2: src/queries.ts
import { mutationOptions, QueryClient, queryOptions } from '@tanstack/react-query'
import { getShifts, postShift } from './api.ts'
import type { NewShift } from './types.ts'

export const queryClient = new QueryClient({ defaultOptions: { queries: { retry: false } } })

/** C2: one site's shifts. Keys go from general to specific: every list of shifts starts with 'shifts' */
export function shiftsQuery(siteId: string) {
  return queryOptions({
    queryKey: ['shifts', siteId],
    queryFn: () => getShifts(siteId),
  })
}

/** C2: add a shift, then mark every list of shifts out of date */
export function addShiftMutation() {
  return mutationOptions({
    mutationFn: (shift: NewShift) => postShift(shift),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['shifts'] }),
  })
}

Invalidating ['shifts'] (not ['shifts', siteId]) marks every site's list out of date: the test checks Driftwood Cove's list after a Pelican Point shift.

W1 to W4: model answers
  1. W1 Both pages read the same cache entry (the same query key), and the mutation invalidated ['events'], so every query under that key refetches (or reads the updated entry): one source of truth (Lessons 7.1 and 7.2).
  2. W2 cancelQueries for the affected key, save the previous value (getQueryData), write the new value (setQueryData); onError writes the saved value back (then invalidate on settle). Lesson 7.2's check-in mark.
  3. W3 Any two of: no refetch or invalidation (stale after a mutation elsewhere), no loading or error state, no deduplication of requests, data survives sign-out unless cleared by hand, a second source of truth that drifts from the cache. Zustand is for client state such as theme and density (Lesson 7.3).
  4. W4 Without when, Zod skips a refine until every other field is valid, so the organizer would not see the time problem until the rest was fixed. when says which fields the check needs, so it runs as soon as those two are valid.

9.1 · Testing Components: self-check

Q1
Which test follows "test what people see and do" best?
A) The header calls useAuth() exactly once
B) EventCard receives a site prop
C) The header's nav has the CSS Module class nav
D) An organizer's navigation has a link named Volunteers
Why: A person (and a screen reader) meets roles and names, never Hooks, props or class names. A test about the link named Volunteers survives any rewrite of the header; one about how often useAuth runs breaks on a refactor that changes nothing a person sees (Lesson 9.1, Why Tests).
A is wrong: That is how the code works inside: refactoring breaks it although nothing visible changed.
B is wrong: Props are internals; Testing Library deliberately gives you no way to read them.
C is wrong: CSS Module names are hashed in the build and say nothing about what a person gets.
Q2
You changed Jul to July in the first formatDate test on purpose. Vitest prints this. Who is wrong, the test or the app?
 FAIL  src/utils/format.test.ts > formatDate > shows a day of the crew calendar with its weekday
AssertionError: expected 'Sat, Jul 4, 2026' to be 'Sat, July 4, 2026' // Object.is equality
Expected: "Sat, July 4, 2026"
Received: "Sat, Jul 4, 2026"
A) The app: formatDate should write July
B) The test: the app writes short month names on purpose
C) Vitest: the two strings are the same
D) jsdom: it cannot format dates
Why: Read a failure like a bug report (which test, expected, received, the line), then ask the question every failure deserves. Here the expected value is the mistake: Lesson 3.4 chose short months. Changing the app's month: 'short' to 'long' instead fails two tests, and then the test is right.
A is wrong: The app's short month names are a deliberate choice from Lesson 3.4.
C is wrong: Vitest highlights exactly the letters that differ.
D is wrong: formatDate runs Intl.DateTimeFormat in Node; jsdom is not involved.
Q3
A test must say "the error summary is not on the page". Which line?
A) expect(screen.getByRole('region')).not.toBeInTheDocument()
B) expect(screen.getAllByRole('region')).toHaveLength(0)
C) expect(await screen.findByRole('region')).toBeNull()
D) expect(screen.queryByRole('region')).not.toBeInTheDocument()
Why: queryBy returns null when nothing matches, so the check can run. getBy throws before expect runs; findBy waits and then rejects; getAllBy throws on zero matches too (Lesson 9.1, the query table and Common Mistakes).
A is wrong: getByRole throws "Unable to find" first: the test fails although the summary really is gone.
B is wrong: getAllBy throws when there are no matches, like getBy.
C is wrong: findBy rejects after a second when nothing appears; it never resolves to null.
Q4
With one line commented out of the setup file, the whole suite ends like this. Which line, and why does a test that passed alone now fail?
 Test Files  3 failed | 4 passed (7)
      Tests  8 failed | 21 passed (29)
cleanup() in afterEach: every render stays on the page, so queries find the component twice ("Found multiple elements")
Why: This project imports describe/it/expect instead of using Vitest's globals, so Testing Library cannot register its own cleanup; setup.ts calls it. The tell: "Found multiple elements" in a test that worked alone (Lesson 9.1, Common Mistakes, measured: 8 of 29).
Q5
A teammate writes makeEvent({ capacity: '12' }) in a test. Vitest runs it happily. What does npx tsc -b say?
A) Nothing: tests are not type-checked
B) error TS2322: the string is not assignable to number
C) A warning, because tests may use any data
D) error TS2741: capacity is missing
Why: factories.ts takes Partial<CleanupEvent>, so every property you pass must still have the right type. Vitest strips types without checking them (like Node in Lesson 1.1); tsc -b checks the test files too, because they live in src. That is why the build still matters when the tests are green.
A is wrong: tsc -b checks every file in src, test files included.
C is wrong: TypeScript has no warnings, only errors; and test data gets no exemption.
D is wrong: Partial makes capacity optional; it is the TYPE of the value that is wrong.
Q6
getByRole('button', { name: 'Show details for Tide Pool Morning Cleanup' }) failed and listed a button named "Show detailsfor Tide Pool Morning Cleanup". The right response?
A) Switch to getByTestId so the name no longer matters
B) Expect "Show detailsfor" in the test
C) Move the space outside the visually hidden text
D) Delete the test: jsdom is wrong
Why: The test found a fragile spot: tools differ on a space at the start of hidden text. Putting it where nobody can lose it ({' '} before the hidden text) gives every tool the same name, and the test stays a check on what screen readers announce (Lesson 9.1, Reading a query's error; Lab 9.1's planted bug 4 is the same pattern).
A is wrong: That hides an accessibility question instead of answering it.
B is wrong: That pins the wrong name down forever.
D is wrong: The test was right to fail: the markup really is fragile.

Modules 7 and 8 review: self-check

Q7
In the HQ, which query key fits a volunteer's sign-ups, seen by the signed-in viewer (Lesson 7.1)?
A) ['signups', viewerId(session), volunteerId]
B) ['volunteers', volunteerId, 'signups', viewerId(session)]
C) [viewerId(session), 'volunteers']
D) ['volunteerSignups']
Why: Keys go from general to specific, with the viewer LAST on viewer-dependent data: then invalidateQueries({ queryKey: ['volunteers'] }) reaches it, and signing in or out gives a separate cache entry (Lesson 7.1, queries.ts).
A is wrong: The viewer in the middle breaks the general-to-specific order.
C is wrong: Starting with the viewer means invalidating ['volunteers'] never matches it.
D is wrong: One key for every volunteer and viewer: they would overwrite each other.
Q8
A mutation succeeded. Which call makes every list of cleanups fetch again the next time it is shown?
A) queryClient.invalidateQueries({ queryKey: ['events'] })
B) queryClient.clear()
C) queryClient.setQueryData(['events'], [])
D) window.location.reload()
Why: invalidateQueries marks every query whose key STARTS with ['events'] as out of date: active ones refetch now, the others on their next use. Checkpoint 3's C2 asks for exactly this with ['shifts'].
B is wrong: clear() throws away every query in the cache, sessions' data included.
C is wrong: That writes an empty list as if it came from the API.
D is wrong: A reload throws away the whole app state for one list.
Q9
The check-in desk marks Diego as attended at once, before the API answers. If the PATCH fails, what must the mutation have done first (Lesson 7.2)?
A) Cancel the running roster queries and keep the old entry, so onError can put it back
B) Nothing: React Query rolls back by itself
C) Invalidate the roster before sending
D) Retry the PATCH until it succeeds
Why: An optimistic update cancels in-flight queries (so they cannot overwrite the new mark), saves the previous entry, writes the new one, and onError writes the saved one back; afterwards it invalidates. Lesson 9.2 tests exactly this rollback.
B is wrong: There is no automatic rollback: the cache only knows what you wrote.
C is wrong: Invalidating first triggers a refetch that races the optimistic write.
D is wrong: Retrying a refused change forever is not a rollback.
Q10
Which value belongs in the Zustand store rather than the TanStack Query cache (Lesson 7.3)?
A) The list of cleanups
B) The signed-in organizer's roster
C) The compact or roomy list density
D) The impact totals
Why: Client state is what only this browser knows and the API never sends: theme, density, open panels. Server state (anything the API owns) belongs in the query cache, with its loading, refetching and invalidation.
A is wrong: The API owns the cleanups: server state.
B is wrong: The roster comes from the API: server state.
D is wrong: Totals are computed by the API: server state.
Q11
In const schema = z.object({ capacity: z.coerce.number<string>() }), what are z.input<typeof schema> and z.output<typeof schema>?
A) { capacity: string } and { capacity: number }
B) { capacity: number } both
C) { capacity: unknown } and { capacity: number }
D) { capacity: string } both
Why: The form holds text (the input type) and the schema hands on a number (the output type); coerce.number<string>() says which text it accepts. React Hook Form's values use the input type, the API call the output type (Lesson 8.1).
B is wrong: The form's field values are text until the schema converts them.
C is wrong: <string> narrows the input to string; without it the input would be unknown.
D is wrong: The output is converted: that is what coerce does.
Q12
In the impact form's debris field array (Lesson 8.2), what must each row's React key be?
A) The row's index
B) The category name
C) The id that useFieldArray gives each row
D) A random number made while rendering
Why: useFieldArray gives every row a stable id; removing row 2 then keeps row 3's input (and its value and focus) instead of shifting everything up. Indexes move when rows are removed; categories can be empty or repeated while typing; random keys remount every render.
A is wrong: Indexes shift on remove, so React reuses the wrong inputs.
B is wrong: A category can be empty or chosen twice while the organizer types.
D is wrong: A new key on every render throws every input away.

/** A worked 3-hour shift at Pelican Point Beach */

    id: 'sh1',
    volunteer: 'v04',
    site: 'Pelican Point Beach',
    date: '2026-07-04',
    hours: 3,
    status: 'worked',
    ...changes,
  }
}
import { describe, expect, it } from 'vitest'
import { badgeFor, formatHours, hoursWorked } from './hours.ts'
import { makeShift } from './test/factories.ts'

describe('hoursWorked', () => {
  it('adds up the hours of the worked shifts', () => {
    const shifts = [makeShift({ hours: 3 }), makeShift({ id: 'sh2', hours: 2.5 })]
    expect(hoursWorked(shifts)).toBe(5.5)
  })

  it.each(['planned', 'missed'] as const)('counts a %s shift as 0 hours', (status) => {
    expect(hoursWorked([makeShift({ status })])).toBe(0)

  it('is 0 with no shifts at all', () => {
    expect(hoursWorked([])).toBe(0)
  })

describe('badgeFor', () => {

    [9.5, 'none'],

    [24.5, 'bronze'],

    [50, 'gold'],

    expect(badgeFor(hours)).toBe(badge)
  })
})

describe('formatHours', () => {
  it('writes one hour in the singular', () => {
    expect(formatHours(1)).toBe('1 hour')

The Lesson Page's Own Quick Quiz

Lesson 9.1 · Testing Components
  1. B An organizer's navigation has a link named Volunteers: A role and an accessible name are what a person (and a screen reader) meets on the page, so the test survives any rewrite of the header that keeps the same result.
  2. D expect(screen.queryByRole('region')).not.toBeInTheDocument(): queryByRole returns null when nothing matches instead of throwing, so the expect can check that the summary is not in the document.
  3. A The display store kept the compact setting from the earlier test: The display store is module state shared by every test in the file. The compact test changed it, and without a reset in afterEach the next test still sees compact lists.
  4. C tsc -b reports an error: the key's type says the data must be a whole ImpactReport: The key made by eventImpactQuery is typed with ImpactReport, so setQueryData expects a whole report. tsc -b (and npm run build) report the missing properties, even though Vitest alone would run the test.
  5. B Move the space outside the visually hidden text, so every tool computes the same name: The name is part of what people hear, so the test pointed at a fragile spot: a space at the start of hidden text, which some accessibility engines drop. Moving the space outside the hidden text gives the same name everywhere.

Warm-up and Exit Ticket

The warm-up's answers are in the Facilitator Guide (Opening Segment).

  1. Three sizes: unit, component, end-to-end. Only end-to-end sees the real browser, the build and the server together: layout, colors, real files, reloads (Lesson 9.3).
  2. getBy / queryBy / findBy: here now (throws when missing) / not here (null) / soon (waits up to a second).
  3. Passes alone, fails together: shared state from an earlier test: the query cache, the session, the display store, storage, or a component that was not cleaned up. Reset it in afterEach (setup.ts).

Common Wrong Answers and What They Reveal

  • Q2 A (the app is wrong). Trusts the test over the code by default. Run the month: 'long' break: now two tests fail and the test is right.
  • Q3 A or D. Has not internalized that getBy and getAllBy throw. Have them run it and read the message.
  • Q5 A. Thinks green tests mean correct types. Show Exercise 2's TS2322 on weightKg: '18.5'.
  • Q7 A or C. The viewer goes last on viewer-dependent keys; invalidation matches prefixes.
  • Q10 B. Confuses "data the organizer sees" with "data the browser owns". Ask: who sends it?
  • Q12 A. Index keys: remove row 2 live in the impact form and watch row 3's value jump.
