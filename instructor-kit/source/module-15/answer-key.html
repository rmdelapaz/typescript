6.1 · React Router 8: self-check

Q1
Measured in the HQ after Lesson 6.1: from the home page, through Events, one cleanup, Back, Forward and the logo back home. How many HTML pages did the browser load?
A) Six, one for each step
B) One: the first
C) Three: one for each different address
D) None: the dev server keeps the page
Why: A router link renders a real <a href> but cancels the browser's page load on a plain click; the router writes the address with the History API and renders the matching route. Back and Forward work without a page load too (Lesson 6.1, Links That Do Not Reload).
A is wrong: That was the HQ before the router: every plain link reloaded the whole app.
C is wrong: The address changes each time, but the document does not.
D is wrong: The very first visit still loads the app's index.html.
Q2
What does npx tsc -b say about this route list?
import { createBrowserRouter } from 'react-router'
import { EventsPage } from './pages/EventsPage.tsx'
import { NewEventPage } from './pages/NewEventPage.tsx'

// An index route is the page AT its parent's address: it cannot have pages of its own
export const router = createBrowserRouter([
  {
    index: true,
    element: <EventsPage />,
    children: [{ path: 'new', element: <NewEventPage /> }],
  },
])
A) Nothing: React Router ignores children on an index route
B) error TS2339: Property 'children' does not exist
C) error TS2322: children must be undefined, because index: true picked the index member of the RouteObject union
D) Nothing at build time; the browser shows an error screen
Why: RouteObject is a discriminated union: IndexRouteObject has children?: undefined. The real message ends with Type '[{ path: string; element: Element; }]' is not assignable to type 'undefined'.: read it from the bottom up. An index route is the page AT its parent's address, so it cannot have pages of its own.
A is wrong: TypeScript checks every route object's shape.
B is wrong: children exists, but its type on this member is undefined.
D is wrong: The type checker catches it before anything runs.
Q3
tsc prints this for a new back link. What is the fix?
src/Scratch.tsx:4:16 - error TS2322: Type '{ href: string; children: string; }' is not assignable to type 'IntrinsicAttributes & LinkProps & RefAttributes<HTMLAnchorElement>'.
Found 1 error in src/Scratch.tsx:4
Use to instead of href: <Link to="/events">
Why: A router Link takes to; it still renders a real <a href> in the browser. TypeScript lists Link's props, so the typo is caught (and the Did you mean points at ref, which is not the fix). The same rule makes <Button as={Link}> require to (Lesson 6.1, Link through the polymorphic Button).
Q4
The sites page throws while rendering. The errorElement sits on the LAYOUT route (path: '/' with AppLayout). What does the visitor see?
A) The header with Sites marked current, the message and the footer
B) React Router's own Unexpected Application Error! screen
C) A blank page with an error in the Console
D) The message, but no header and no footer: the error element replaced the layout too
Why: An error element replaces the route it sits on, layout included. On a pathless route INSIDE the layout it replaces only the page, which is what the HQ does (Lesson 6.1, When a Page Crashes, measured three ways).
A is wrong: That is the pathless route inside the layout: the HQ's choice.
B is wrong: That is what happens with no errorElement on any route.
C is wrong: React Router catches the error; the page is not blank.
Q5
The route is written 'events/:id' while EventPage reads eventId from useParams(). What happens?
A) npx tsc -b and npm run lint pass; on /events/e08 the page shows "Something went wrong on this page" and the Console names EventPage's error
B) npx tsc -b reports TS2339: eventId does not exist
C) The cleanup page works: React Router matches the names by position
D) Page not found
Why: Both sides are just strings, so TypeScript stays quiet (the kit ran it: npx tsc -b printed nothing). eventId is undefined, EventPage throws its own message, and the errorElement shows the crash page. Lesson 6.2's useParams<'eventId'>() names the parameter; it still cannot see the route list.
B is wrong: Untyped useParams() allows any name; each value is string | undefined.
C is wrong: Parameters are matched by name, not position.
D is wrong: The address still matches 'events/:id'; only the name differs.
Q6
Why does EventPage put key={eventId} on its ErrorBoundary?
When only the parameter changes the route stays the same, so React keeps the components and their state; a new key mounts fresh ones (boundary, Suspense, tabs)
Why: Measured in the lesson: without a key, going from one cleanup to another kept the old selected tab and showed no panel. A key is React's identity for a component (list keys, Lesson 3.3).

6.2 · Search Params, Nested Routes and Typed Navigation: self-check

Q7
What does the second line print?
const params = new URLSearchParams('q=pelican point&status=completed')
console.log(params.get('q'), params.get('page'), params.has('status'))
A) pelican point null true
B) pelican+point undefined true
C) pelican point '' true
D) pelican%20point null false
Why: get decodes the value (+ or %20 become a space) and returns null for a missing name: string | null. toString() writes spaces as + again (q=jetty&status=completed after a set). URLSearchParams is a browser class, so this ran in Node too.
B is wrong: Spaces come back as spaces, and a missing name is null, not undefined.
C is wrong: Missing means null, not an empty string.
D is wrong: get decodes, and has('status') is true.
Q8
const status: StatusFilter = searchParams.get('status') ?? 'all' gives this. How does the HQ fix it, and why not with as StatusFilter?
src/Scratch.tsx:6:9 - error TS2322: Type 'string' is not assignable to type 'StatusFilter'.
Found 1 error in src/Scratch.tsx:6
readParam(searchParams, 'status', isEventStatus) ?? 'all': a type predicate checks the text; an as would let ?status=banana through
Why: The address is input from outside the app, like the API's JSON in Lesson 2.4: check it, then trust it. Measured: /events?status=banana showed All statuses and all 15 cleanups.
Q9
Signed in as Maya on the crew page: Next page →, click Kwame Asante, Next page → again (address /volunteers/v09?page=3), then type ma in the search. Now Back. Where are you?
A) /volunteers/v09?page=3
B) /volunteers/v09?q=m
C) /volunteers/v09?page=2
D) /volunteers
Why: Typing uses replace: true, so the first letter REPLACED the ?page=3 entry and the letters added none; Back goes to the entry before it (Lesson 6.2, Exercise 1, measured).
A is wrong: That entry was replaced by the typing.
B is wrong: Replace means the letters are never places to go back to.
D is wrong: That is several entries further back.
Q10
Someone removes <Outlet /> from VolunteersPage. Signed in as Maya, they click Aisha Rahman. What happens?
A) npx tsc -b fails: the child route has nowhere to render
B) React Router shows its error screen
C) The card replaces the list

Why: The router matched the child route; there is simply nowhere to draw it, and nothing complains (tsc, lint and the Console were all quiet, measured). A nested page that does nothing: check the parent's Outlet first.

B is wrong: Nothing throws.

Q11
These four lines are in a Scratch.tsx in the HQ (data mode). How many errors does npx tsc -b report?
import { generatePath, href } from 'react-router'

// href(): checked only in framework mode, where React Router generates the list of routes
export const typoInPath = href('/volunters/:volunteerId', { volunteerId: 'v04' })
export const missingValue = href('/volunteers/:volunteerId')

// generatePath(): reads the parameter names from the pattern you pass
export const fine = generatePath('/volunteers/:volunteerId', { volunteerId: 'v04' })
export const typoInName = generatePath('/volunteers/:volunteerId', { volunterId: 'v04' })
A) Four: each line has a mistake
B) One, on the generatePath line with volunterId
C) Two, on the two href lines
D) None: all four compile
Why: href() is typed from the generated route list of framework mode; in data mode it accepts any path and any params, so the typo path and the missing value compile (and fail at run time). generatePath reads the names from the pattern: error TS2741.
A is wrong: The fine line is fine, and both href lines compile.
C is wrong: That is what href would report in framework mode.
D is wrong: generatePath does check the parameter names.
Q12
In the crew list, names link with to={{ pathname: volunteer.id, search: searchParams.toString() }}; the Pagination links use to={{ search }} with no pathname. What does each keep?
The name links keep the search (page, q, skill) and change the path; the page links keep the path (the open card) and change only the search
Why: Links resolve relative to their route, and a path alone drops the query: on page 2, a name link without the search jumped back to Page 1 of 3 (Common Mistakes). Next page from /volunteers/v16?page=2 went to /volunteers/v16?page=3.

  2. A string | undefined, because TypeScript cannot know which route rendered the page: useParams cannot see which route rendered the component, so every parameter may be missing. The page narrows it with a check before using it as a string.
  3. D On a pathless route inside the layout route, around the pages: The error element replaces the route it belongs to, including that route's element. On a pathless route inside the layout, only the page area is replaced, so the header, footer and navigation keep working.
  4. Lesson 6.2 · Search Params, Nested Routes and Typed Navigation
  1. B /events?q=pelican: The status change pushed a new entry, so Back removes it. The typing replaced entries instead of adding them, so the search stays and the menu shows All statuses again.
  2. D string | null: URLSearchParams.get returns the text of the first value with that name, or null when there is none. The HQ narrows it with readParam and a type predicate before using it as a StatusFilter.
  3. A At the <Outlet /> inside VolunteersPage, beside the list: The :volunteerId route is a child of the volunteers route, so it renders at the Outlet inside VolunteersPage. The search, the list and the layout stay mounted around it.
  4. C Nothing: in data mode href accepts any path, so the link would lead to "Page not found": href only checks paths against the route list that framework mode generates. In data mode it accepts any string, so the typo compiles and the link leads to Page not found. The measurement showed exactly that.
  5. A Router updates run as low-priority transitions; without it the box lost letters and the cursor jumped to the end: React Router applies its updates as transitions, which can wait. A text box whose value comes from the address then shows a stale value for a moment, so the cursor jumps and fast letters are lost. flushSync applies that one update immediately.

Exit Ticket

  1. Three routes: the layout route (AppLayout: header, footer, <Outlet />, focus and scroll after a navigation), the pathless route (errorElement: <PageCrashed />, so a crashing page keeps the layout), the index route (HomePage at /).
  2. Who reads what: the router reads the path (/events) to choose the page; the page reads the query string (q, status) to decide what to show. searchParams.get('status') is string | null.
  3. Keep the search: a link with only a path drops the query string, so on page 2 the list would jump back to Page 1 of 3 (and lose a search or skill filter). { pathname, search } passes it along.

Common Wrong Answers and What They Reveal

  • Q1 A ("six"). Still thinks of links as page loads. Open the Network panel filtered to Doc and click through the HQ: one document.
  • Q2 A or D. Expects routes to be untyped configuration. Hover createBrowserRouter's parameter: RouteObject[].
  • Q4 A. Has not separated "the route the error element sits on" from "the page that crashed". Draw the tree; cross out everything under the route with the error element.
  • Q5 B. Believes useParams knows the route list. It does not, even with a type argument (Lesson 6.2).
  • Q7 B or D. Has not met URL decoding: run P3's first line in the browser Console.
  • Q9 A. Treats replace as "no history at all" rather than "overwrite the current entry". Walk Exercise 1 on the projector.
  • Q11 C or D. Trusts a function's name. That is exactly the lesson's point: test the promise with a deliberate typo.
