9.2 · Interactions and Async: self-check

Q1
Why does every user.click and user.type need await?
A) It slows the test down to a person's speed
B) It waits for the API to answer the request the click sends
C) Each action returns a Promise that resolves once its events have fired and React has updated the page
D) Without it, user-event falls back to fireEvent
Why: user-event fires the whole chain of browser events (pointer, mouse, focus, click; key down, input, key up for every letter) one after another; await lets React finish each update, so the next line sees the page after the action. A request the click starts still needs findBy (Lesson 9.2, Common Mistakes: "Unable to find" right after a click).
A is wrong: Speed has nothing to do with it: the events fire as fast as the test can.
B is wrong: The click's Promise does not wait for network answers: that is findBy's job.
D is wrong: There is no fallback; without await the next line simply looks too early.
Q2
renderApp('/events/e08/edit', organizer) has just returned. Which line finds the title field?
A) screen.getByLabelText('Title (5 to 80 characters)')
B) await screen.findByLabelText('Title (5 to 80 characters)')
C) screen.queryByLabelText('Title (5 to 80 characters)')
D) screen.getByTestId('title')
Why: Right after render the page shows the first-load placeholder ("Loading Shoreline Crew HQ…") while the loader fetches; findBy keeps looking for up to a second. After the first findBy the page is there and getBy is fine (Lesson 9.2, Common Mistakes).
A is wrong: getBy looks once, now, and finds the loading placeholder.
C is wrong: queryBy returns null now and never waits.
D is wrong: There is no test id, and a label is what a person uses.
Q3
The guard line in editEventLoader was commented out. The guest still ends up on the sign-in page, and the guard test prints this. What went wrong that nobody clicking through would see?
AssertionError: expected [ 'GET /api/events/e08', …(1) ] to deeply equal []

- Expected
+ Received

- []
+ [
+   "GET /api/events/e08",
+   "GET /api/sites",
A) The guest saw the edit form for a moment
B) The child loader asked the API for the cleanup and the sites before the guest was sent away
C) The sign-in page loaded twice
D) MSW answered requests it should have refused
Why: The guard route's own loader still redirects, so the screen looks right; but editEventLoader ran at the same time and fetched data a guest may not see. recordRequests() makes the invisible half of the rule testable: expect(requests).toEqual([]) (Lesson 9.2, Step 5).
A is wrong: The redirect still happens before anything renders.
C is wrong: One sign-in page; the extra requests are the problem.
D is wrong: MSW answered exactly what was asked: the asking was the bug.
Q4
A test calls server.use(...) to make POST /api/photos answer 413. What does the NEXT test get?
A) The API's own answer again, because server.resetHandlers() runs after every test
B) 413 again until the file ends
C) An error: two tests cannot change the same address
D) Whatever the slower test set last
Why: server.use puts a handler in front of the API's own for the rest of the test; setup.ts's afterEach calls resetHandlers(). Tests stay independent, in any order (Lesson 9.2, One answer, for one test).
B is wrong: resetHandlers removes it after each test.
C is wrong: Overrides stack and are removed; nothing forbids them.
D is wrong: Tests in a file run one after another, and each starts clean.
Q5
With the retry lines removed from setup.ts, the "page whose data does not load" test fails after about a second with this. The app does show its alert. Why does the test not see it?
TestingLibraryElementError: Unable to find role="alert"
The app's cache was still retrying the 500 (with pauses) when findByRole gave up after its 1-second default; tests set retry: false
Why: A test that fails after a round thousand milliseconds, or only on a slow machine, is often waiting for a built-in delay: retries, debouncing, animations. Turn the delay off for tests or control the clock (Lesson 9.2, Common Mistakes; Exercise 1).
Q6
Lab 9.2's sign-up form must not send anything without a name. Which line in the test proves the "nothing"?
A) expect(api.signups).toEqual([])
B) expect(screen.getByText('Add your name.')).toBeInTheDocument()
C) expect(screen.getByRole('button')).toBeEnabled()
D) expect(requests).toEqual([]) after recordRequests()
Why: Only a log of the requests themselves proves none was SENT. api.signups would stay empty also if a request went out and the API refused it; the message proves only the screen. The planted bug in debug_SignUpForm.tsx sends first and checks later: the screen looks right and the request log catches it.
A is wrong: An empty list of sign-ups does not prove no request was made.
B is wrong: That proves the message, not the network.
C is wrong: An enabled button says nothing about requests.

9.3 · End-to-End and Accessibility Tests: self-check

Q7
Right after fill('pelican'), a test checks expect(await page.getByText('Found 3 cleanups').isVisible()).toBe(true) and fails. Why?
A) Playwright cannot read text in main
B) The search needs the API restarted
C) Strict mode: the text matches several elements
D) isVisible() checks once, during the search's 300 ms pause; a web-first assertion keeps checking
Why: await expect(locator).toBeVisible() retries for up to 5 seconds until it is true; isVisible() answers "right now". The same goes for waitForTimeout: wait for what you expect to see, never for a number of milliseconds (Lesson 9.3, Common Mistakes).
A is wrong: Playwright reads any text a person could see.
B is wrong: Nothing is wrong with the API.
C is wrong: Strict mode applies to actions and assertions on locators; this one fails with Received: false.
Q8
Why does the HQ's Playwright config say workers: 1?
A) All tests share one real API whose data each test resets and changes; two at once would get in each other's way
B) Chromium opens one tab at a time
C) One worker is faster
D) Playwright's free version allows one worker
Why: A reset in one worker would wipe data another worker's test is using. With one shared server the HQ keeps tests in a line, resets before each and cleans up after the last (globalTeardown). Big teams give each worker its own server or account instead.
B is wrong: Chromium can run many pages and contexts.
C is wrong: More workers are usually faster; safety is the reason.
D is wrong: Playwright is free and open source in full.
Q9
After a CSS change, every light-theme axe test passes and every dark-theme one fails with color-contrast. Which is true?
A) axe is unreliable in dark mode; remove those tests
B) tsc or oxlint would have caught it too
C) Some text in dark mode really is too faint; only a real browser computing the dark colors could find it
D) A Vitest test in jsdom would have shown it
Why: Colors are computed by a real browser from your CSS and the color scheme; jsdom computes none, and neither type checker nor linter reads colors. Lab 9.3 shows the same split: the starter's dark --muted fails only the dark scan.
A is wrong: The tests found a real problem.
B is wrong: Neither tool reads CSS colors.
D is wrong: jsdom has no layout and computes no colors.
Q10
New rule: a photo bigger than 5 MB is refused with the API's message. Where does its test belong?
A) An end-to-end test uploading a real 6 MB photo
B) An axe scan of the impact report page
C) A component test with an MSW override that answers 413
D) A unit test of the API's core only
Why: Rare error answers are what the component level is for: an override causes the 413 in milliseconds, and the test checks what the person sees. The end-to-end level keeps one good journey with one good photo (Lesson 9.3, What to Test Where).
A is wrong: Slow, and a big file in the repository for an edge case the level below covers.
B is wrong: axe checks accessibility, not upload rules.
D is wrong: That proves the API refuses; not that the HQ shows the message.
Q11
What does the check-in test's page.reload() prove that Lesson 9.2's tests could not?
The mark came back from the REAL server after the page and its cache were thrown away: the API really saved it
Why: Lesson 9.2's mock API lives inside the test run; a reload in a real browser throws away the page, the cache and the session's memory, so whatever shows afterwards came from shoreline-api itself.
Q12
A learner's first e2e run prints this. What do they run?
  ✘  1 e2e/plan.spec.ts:13:1 › an organizer plans a cleanup and finds it in the list (35ms)
...
    Error: browserType.launch: Executable doesn't exist at ~/.cache/ms-playwright/chromium_headless_shell-1254/chrome-headless-shell-linux64/chrome-headless-shell
npx playwright install chromium: the npm package is Playwright's code; the browser is a separate download
Why: About 330 MB, stored once per computer in Playwright's cache folder, not in the project. On Linux, npx playwright install-deps chromium adds missing system libraries; in CI, --with-deps does both (Lesson 10.2).

import { api, API_URL, recordRequests, server, type ApiErrorBody } from './test/server.ts'

// Given (do not change): the mock API starts once, is fresh for every test, and fails on unanswered requests
beforeAll(() => server.listen({ onUnhandledFrame: 'error' }))
beforeEach(() => api.reset())
afterEach(() => {
  server.resetHandlers()
  server.events.removeAllListeners()
})
afterAll(() => server.close())

/** The form for Weekend Cove Cleanup, and a user who types and clicks like a person */
function renderForm() {
  const user = userEvent.setup()
  render(<SignUpForm apiUrl={API_URL} eventId="e08" />)
  return { user }
}

describe('SignUpForm', () => {
  it('shows the spots left once the API answers', async () => {
    renderForm()
    expect(screen.getByText('Checking the spots…')).toBeInTheDocument()
    expect(await screen.findByText('6 spots left')).toBeInTheDocument()
  })

  it('signs a volunteer up and counts the spot', async () => {
    const { user } = renderForm()
    await user.type(screen.getByLabelText('Your name'), 'Diego Herrera')
    await user.click(screen.getByRole('button', { name: 'Sign up' }))

    expect(await screen.findByText('You are on the list, Diego Herrera.')).toBeInTheDocument()
    expect(screen.getByText('5 spots left')).toBeInTheDocument()
    expect(api.signups).toEqual(['Diego Herrera'])
  })

  it('works with the keyboard alone', async () => {
    const { user } = renderForm()
    await user.tab()
    expect(screen.getByLabelText('Your name')).toHaveFocus()
    await user.keyboard('Ana Lima{Enter}')
    expect(await screen.findByText('You are on the list, Ana Lima.')).toBeInTheDocument()
  })
})

describe('SignUpForm when something is wrong', () => {
  it('asks for a name and sends nothing', async () => {
    const { user } = renderForm()
    await screen.findByText('6 spots left')
    const requests = recordRequests()

    await user.click(screen.getByRole('button', { name: 'Sign up' }))

    expect(screen.getByText('Add your name.')).toBeInTheDocument()
    expect(screen.getByLabelText('Your name')).toHaveAttribute('aria-invalid', 'true')
    expect(requests).toEqual([])
  })

  it('shows the API message when the cleanup is full', async () => {

The Lesson Pages' Own Quick Quizzes

Lesson 9.2 · Interactions and Async
  1. B Each action returns a Promise that resolves once its events have fired and React has updated the page: Each action fires a chain of events and lets React finish its updates in between. Its Promise resolves when that is done, so the next line checks the page after the click, not before it.
  2. D await screen.findByLabelText('Title (5 to 80 characters)'): The page appears only after the loader has fetched the cleanup and the sites. findByLabelText keeps looking (up to a second by default) and resolves when the field is there.
  3. A The API's own answer again, because server.resetHandlers() runs after every test: setup.ts calls server.resetHandlers() after every test, which removes the overrides and leaves only the API's own handlers, so the next test talks to the real rules again.
  4. C A child loader could ask the API for data before the guard sends the guest away, while the page still looks right: With the guard call removed from editEventLoader, the guest is still redirected, so the page looks right, but the loader has already asked the API for the cleanup and the sites. Only the request list shows it.
  5. D The app's cache is still retrying with pauses when findByRole gives up after one second: The app's query client retries a failed request twice with a pause before each try, so the error message is still on its way when findByRole gives up after its default one second.
Lesson 9.3 · End-to-End and Accessibility Tests
  1. C isVisible() checks once, while the search is still waiting; a web-first assertion would keep checking: isVisible checks once, at that instant, and the search is still in its 300 ms pause. await expect(locator).toBeVisible() keeps checking until the text appears or the timeout ends.
  2. A All tests share one real API whose data each test resets and changes, so two at once would get in each other's way: All tests share one shoreline-api, and each test resets its data first. Two tests at once would reset or change the data the other one is using, so they run one after another.
  3. D Some text in dark mode really is too faint, and only a real browser rendering the dark theme could find it: Only a real browser computes the colors each theme produces. In dark mode the text no longer has enough contrast with its background, which is a real problem for people using dark mode, and only the dark scan can see it.
  4. B A component test with an MSW override that answers 413: It is an error case on one screen: a component test with an MSW override answering 413 (as in Lesson 9.2) checks the message quickly and reliably. End-to-end tests are kept for the main journeys.
  5. A The mark came back from the real server after the page and its cache were thrown away, so the API really saved it: A reload empties the page and the query cache, so the pressed button that comes back was loaded from shoreline-api. That shows the real server saved the mark, which no in-memory test can show.

Warm-up and Exit Ticket

The warm-up's answers are in the Facilitator Guide.

  1. The API's own code: the tests follow the real rules, status codes and messages, and cannot drift from the API; hand-written answers can.
  2. Only in a real browser: a real photo upload, CSS colors (dark-mode contrast), layout and overflow, a reload against the real server, the production build itself (any one).
  3. Where it goes: many cases → unit; one screen, including errors and what must not happen → component with MSW; only works when everything is real together → one end-to-end test for the main path.

Common Wrong Answers and What They Reveal

  • Q1 B. Thinks the click waits for the network. Show the missing-await message, then where findBy comes in.
  • Q2 A. Has not seen the first-load placeholder. Print screen.debug() right after renderApp.
  • Q3 A. Expects a visible symptom. The point of the request log is the invisible half of a rule.
  • Q7 C. Mixes up strict mode and timing. Strict mode errors say "resolved to N elements".
  • Q9 A or D. Blames the tool or overestimates jsdom. Run Lab 9.3's dark-only failure.
  • Q10 A. Wants every rule end-to-end. Ask what the test costs and what it can see.
