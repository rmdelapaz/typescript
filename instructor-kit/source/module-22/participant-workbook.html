9.2

Interactions and Async

By the end you can
  • Click, type, tab and upload in tests with user-event, and explain why each action is awaited
  • Answer the app's requests in tests with MSW 3 running the API's own code, reset it between tests and fail on requests nobody answers
  • Wait for data with findBy and waitFor, and replace one answer for one test with server.use(), typed with the API's own types
  • Test whole pages through the app's real routes, including loaders, redirects and the organizers-only guard
  • Test custom Hooks and TanStack Query mutations with renderHook, including an optimistic update and its rollback
Key ideas
  • user-event fires the events a person causes; userEvent.setup() before render; await every action.
  • MSW 3 catches requests inside Node; the HQ's handlers run shoreline-api's own core (src/mocks, never edited). onUnhandledFrame: 'error', api.reset() before each test, resetHandlers() after.
  • Waiting: findBy for elements the API brings; waitFor for things that are not elements; getBy after an awaited action that changed the page at once.
  • server.use(): one answer for one test, typed satisfies ApiErrorBody. Prefer the real rule (Weekend Cove really is full).
  • renderApp(route, session) renders the real routes (loaders, guards, redirects); recordRequests() proves what was not sent.
  • renderHook tests a Hook on its own (initialProps, rerender, unmount, a wrapper for providers); retries off in tests.

9.3

End-to-End and Accessibility Tests

By the end you can
  • Set up Playwright so one command builds the HQ, starts or reuses shoreline-api and the preview server, and runs the tests in Chromium
  • Write end-to-end tests with locators by role and label, auto-waiting actions and web-first assertions, and read their failures
  • Keep tests that share one real server independent: a reset before every test, one test at a time, and a clean API afterwards
  • Run axe accessibility checks on the HQ's key pages in both themes, and explain what automated checks can and cannot find
  • Decide for any behavior whether it needs a unit, component or end-to-end test, and why most of a suite should not be end-to-end
Key ideas
  • End-to-end = the build in a real browser against the real server: bytes, pictures, colors, layout, reloads.
  • Playwright: fixtures ({ page }, { request }), locators by role and label (strict: one element or an error), actions that wait, web-first assertions that retry (await expect(...)).
  • One real server: reset before every test (POST /api/_reset), workers: 1, a globalTeardown that leaves the beach as you found it. It resets YOUR running API too.
  • axe (@axe-core/playwright, WCAG A/AA tags) in both themes after each page's heading: a floor, not a ceiling.
  • What to test where: many cases → unit; one screen, errors, nothing sent → component; only real together → one e2e journey.
  • First run can take a minute or two before "Running…"; npx playwright install chromium when it says Executable doesn't exist.

Glossary

TermMeaning
user-eventTesting Library's way to act like a person: await user.click(...), user.type, user.tab, user.keyboard
MSW (Mock Service Worker)Catches requests (in Node for tests, in a service worker in a browser) and answers them with handlers
onUnhandledFrame: 'error'MSW 3: a request no handler answers fails loudly (MSW 2 said onUnhandledRequest)
server.use / resetHandlersOne answer for one test / remove those answers after each test
renderAppThe HQ's helper that renders the real routes in a memory router
renderHookRuns a Hook inside a tiny component and keeps its result in result.current
end-to-end testThe build in a real browser against the real server
Playwright, locatorThe e2e runner / a description of an element, found again each time it is used
web-first assertionawait expect(locator)... that retries until true (5 seconds by default)
strict modeA locator for an action must match exactly one element
axeAn accessibility checker; @axe-core/playwright runs it in Playwright's page
globalTeardownRuns once after the last test: the HQ resets the API there
testing pyramid / trophyTwo pictures of a healthy suite; both keep end-to-end tests few and chosen
