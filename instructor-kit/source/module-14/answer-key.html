Session 14 12 self-check items Confidential

Start Here · Warm-up

  1. useAuth() throws when the context value is undefined. Why is that better than a default value? A component rendered outside AuthProvider fails at once with a message that says what to fix, instead of quietly showing a guest (Lesson 5.2). Today's Tabs use the same pattern for their parts.
  2. AuthProvider's value is a new object on every render. Lesson 5.2 said that is fine for now. When would it not be? When the provider renders often for reasons that do not change the value: every reader would render again for nothing. Lesson 5.3 measures it (and finds the HQ's AuthProvider is fine).
  3. The check-in desk keeps its marks in a reducer (Lesson 5.1). What happens to them if the desk component is removed from the page and added back? They are gone: unmounting a component throws its state away, and the roster is fetched again. Lesson 5.4 hides tab panels instead of removing them for exactly this reason.

Q7
Why does Tabs.tsx NOT export TabsContext?
A) To keep the bundle smaller
B) So only the parts in the same file can read it: the rest of the app sees four components
C) Because a .tsx file may not export a context
D) Because createContext needs a default value to be exported

interface IdListProps<T extends { id: string }> {

Lesson 5.4 · Component Patterns
  1. B It reads the selected id from a private context that Tabs provides: Tabs keeps the selected id in state and provides it through TabsContext. Each Tab reads the context with useTabs and compares its own id, so the caller never wires anything by hand.
  2. C DebrisCount, inferred from items: TypeScript infers the type parameter T from the items prop: DebrisCount. Then getKey and renderItem are checked against it, so item.category is known.
  3. A An error: disabled does not exist on the props of an a element: With as set to a, the props are an anchor's props, and an a element has no disabled attribute, so TypeScript reports TS2322: Property disabled does not exist. The props follow the as prop.
  4. D So the panels stay mounted and keep their state, like the check-in marks: A removed panel unmounts its content, and the state in it is lost: measured, the check-in marks went back to 0 of 7 and the roster was fetched again. A hidden panel stays mounted and keeps its state.
  5. B Only the call site: as={Link} to="/events/new" replaces as="a" href="/events/new": as accepts any ElementType, components included, and ComponentPropsWithRef of Link brings in its to prop. Only the call site changes, from as a with href to as Link with to; Button itself stays as it is.

Exit Ticket

  1. Three reasons: its own state changed (a set call or dispatch); its parent rendered; a context it reads changed.
  2. A memo component with no props that still renders: it reads a context whose value is a new object on every render of the provider; keep the value the same object with useMemo and its functions with useCallback (or let the compiler do it). memo never blocks a context update.
  3. A pattern and its HQ component: compound components, Tabs (TabList, Tab, TabPanel); render prop + generic component, DataList<T>; polymorphic as prop, Button.
