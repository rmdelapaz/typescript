4.2

Custom Hooks

By the end you can
  • Explain what a custom Hook is, when a plain function is the better choice, and why two components that call the same Hook do not share its state
  • Follow the Rules of Hooks inside your own Hooks, and read the linter's rules-of-hooks errors
  • Type what a Hook returns: nothing, one value, a tuple with as const, or an object with an interface
  • Write generic Hooks (useDebouncedValue<T>, useApi<T>) whose types follow the arguments you pass
  • Pass a function into a Hook safely with useEffectEvent, and explain what a data library like TanStack Query adds on top of a Hook like useApi
Key ideas
  • Custom Hook: a function whose name starts with use and calls Hooks. It shares logic between components, never state: two callers, two states, two requests.
  • Rules of Hooks inside your Hook: top level only, never after an early return; only from components and Hooks. The linter finds Hooks by name (rules-of-hooks is an error; tsc is silent).
  • Return shapes: nothing (void), one value, a tuple (as const, or every name gets the union), an object (an exported interface in the return annotation).
  • Generic Hooks take T from the arguments: useDebouncedValue(query, 300) is a string; useApi('/sites', getSites) is ApiResult<Site[]>.
  • Key and load: a function made during render is new every render; in a dependency array it floods the API. The key decides when; useEffectEvent reads the latest load without triggering.
  • What useApi lacks (cache, retries, refetch on focus, invalidation) is why TanStack Query replaces it in Lesson 7.1.
Worked example: useApi, read in four moves

The Hook every data page uses after this lesson (the finished Lesson 4.2 code):

shoreline-hq/src/hooks/useApi.ts
export function useApi<T>(key: string, load: (signal: AbortSignal) => Promise<T>): ApiResult<T> {
  const [state, setState] = useState<LoadState<T>>({ kind: 'loading' })
  const [attempt, setAttempt] = useState(0)
  // The latest load function, without making the effect run again when it changes
  const loadLatest = useEffectEvent(load)

  useEffect(() => {
    const controller = new AbortController()
    loadLatest(controller.signal)
      .then((data) => setState({ kind: 'ready', data }))
      .catch((error: unknown) => {
        if (controller.signal.aborted) return
        console.error(error)
        setState({ kind: 'failed', message: describeError(error) })
      })
    return () => controller.abort()
  }, [key, attempt])

  function reload() {
    setState({ kind: 'loading' })
    setAttempt((count) => count + 1)
  }

  return { state, reload }
}

Read it in four moves. Same pattern as 4.1: LoadState, AbortController, the aborted check, describeError. Key = WHAT: a string; the same key on every render means "nothing changed", so it is in the array (with attempt). Load = HOW: a new function on every render is fine, because the effect calls loadLatest, the useEffectEvent copy that always sees the latest load without triggering anything. Try again for free: reload shows loading and counts one more attempt in the same click.

A page then needs one line: const sites = useApi('/sites', getSites); TypeScript infers ApiResult<Site[]> from getSites.

4.3

Refs and the DOM

By the end you can
  • Explain what a ref is, when to choose a ref over state, and why reading a ref while rendering is a mistake
  • Type refs to values and to DOM elements (useRef<HTMLInputElement>(null)), and read the errors TypeScript gives for null, the wrong element and React 19's required argument
  • Use callback refs, including React 19's cleanup function, and avoid the arrow-function return that React 19's types reject
  • Pass a ref to your own component as an ordinary prop, the React 19 way
  • Manage focus on purpose: a keyboard shortcut, the first invalid field, and a modal dialog rendered through a portal that gives the focus back when it closes
Key ideas
  • A ref is an object with current that survives renders; changing it renders nothing. If the screen should change when it changes, it is state; otherwise it can be a ref. Never read ref.current during render.
  • DOM refs: useRef<HTMLInputElement>(null) → current is HTMLInputElement | null; use ?.. The type argument names the element (a div's ref on an input is TS2322).
  • Callback refs: ref={(el) => { … }} runs when the element arrives; in React 19 it may return a cleanup, which must return nothing (braces!).
  • Ref as a prop (React 19): ref?: Ref<HTMLInputElement> in a component's props; the component chooses which element a parent reaches. forwardRef is the old way.
  • Focus management: an element disappears → somewhere useful; a form finds problems → the first field to fix; a dialog opens → inside it; closes → back to its opener. Document listeners live in an effect (the browser's KeyboardEvent).
  • Portals and <dialog>: createPortal renders into body while staying in React's tree; showModal() gives the top layer, an inert page, Escape and initial focus.
Worked example: the HQ's Dialog

The dialog every confirmation in the HQ uses (the finished Lesson 4.3 code):

shoreline-hq/src/components/Dialog.tsx
export function Dialog({ title, onClose, children }: DialogProps) {
  const dialogRef = useRef<HTMLDialogElement>(null)
  const openerRef = useRef<Element | null>(null)
  const titleId = useId()

  useEffect(() => {
    const dialog = dialogRef.current
    if (dialog === null) return
    if (!dialog.open) {
      openerRef.current = document.activeElement // remember where the focus was
      dialog.showModal() // focus moves into the dialog, the page behind it goes inert
    }
    return () => {
      // Closing: give the focus back to the control that opened the dialog
      const opener = openerRef.current
      if (opener instanceof HTMLElement) opener.focus()
    }
  }, [])

  return createPortal(
    <dialog ref={dialogRef} aria-labelledby={titleId} className={styles.dialog} onClose={onClose}>
      <h2 id={titleId}>{title}</h2>
      {children}
    </dialog>,
    document.body,

Two refs, two jobs: dialogRef holds the element so the effect can call showModal(); openerRef holds a plain value nobody sees (where the focus was), so the cleanup can give the focus back. The !dialog.open check keeps Strict Mode's second run from remembering the wrong opener. createPortal puts the <dialog> in body, while it stays inside EventCard in React's tree (its props, state and events).
