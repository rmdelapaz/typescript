Q4
A loader for a cleanup's page can await a request or return it as a promise. Which one should it AWAIT?
A) The impact report, so the Impact tab never says Loading
B) Nothing: awaiting in a loader blocks the browser
C) The cleanup itself: the page makes no sense without it, and a 404 must decide the answer
D) Both, always, so the page appears complete
Why: Await what the page cannot do without and what decides the answer (404, redirect); return a promise for what can follow. The impact report is returned unawaited and use()d inside Suspense, so a missing report costs one tab, not the page (Lesson 6.3, Await what the page needs).
A is wrong: Then everyone waits for two requests, and an error in the report costs the whole page.
B is wrong: The router awaits the loader; the old page stays on screen meanwhile.
D is wrong: That makes every visit as slow as the slowest part.
Q5
Why does the HQ's ErrorPage write answer?.statusText || 'Something went wrong on this page' with || and not ???
A) ?? does not work after optional chaining
B) statusText is a number
C) A response without a status text has '', which should fall back too; ?? only falls back for null and undefined
D) || narrows unknown, ?? does not
Why: An empty string is not null, so ?? would keep it and show an empty heading. || falls back for every falsy value, which here is exactly the empty text (Lesson 6.3, Step 1).
A is wrong: ?? works fine after ?.; it just falls back too rarely here.
B is wrong: statusText is a string; status is the number.
D is wrong: Neither operator narrows unknown; isRouteErrorResponse does.
Q6
The HQ's nextPath gets the address /sign-in?next=%2F%2Fexample.com. What does it return?
export function nextPath(url: URL): string {
  const next = url.searchParams.get('next')
  if (next === null || !next.startsWith('/') || next.startsWith('//') || next.startsWith('/\\')) {
    return '/'
  }
  return next
}
A) //example.com
B) /
C) /example.com
D) It throws, and the sign-in page shows the error page
Why: The value is //example.com: it starts with / but also with //, which browsers read as another site, so nextPath gives the home page. The kit ran the stage's own function: //example.com gives /. Without the check, signing in would hand the person to someone else's page (an open redirect).
A is wrong: That is the open redirect the check exists to stop.
C is wrong: nextPath never rewrites a value; it accepts it or returns /.
D is wrong: It returns a string for every input.
Q7
Theo (a volunteer) is signed in and opens /events/new. Why does the guard answer 403 "Organizers only" instead of redirecting him to sign in?
A) Signing in again would not help him: he is signed in, just not allowed, so a redirect would only loop
B) A redirect cannot be thrown from a loader
C) The API answers 403, and the guard copies it
D) 403 pages are faster than redirects
Why: 401 means "I don't know who you are" (sign in), 403 means "I know, and no". The guard throws data(message, { status: 403, statusText: 'Organizers only' }); the shared ErrorPage shows the heading and the sentence (the lesson's screenshot).
B is wrong: Guards throw redirect() for guests all the time.
C is wrong: The guard runs before any request; it never asks the API.
D is wrong: Speed has nothing to do with it.
Q8
Someone writes organizersOnly with the Hook they already have. tsc is quiet; oxlint says this. Why, and what does the HQ do instead?
  × react-hooks(rules-of-hooks): React Hook "useAuth" is called in function "organizersOnly" that is neither a React function component nor a custom React Hook function. React component names must start with an uppercase letter. React Hook names must start with the word "use".
A loader runs outside React, before any component renders, and Hooks only work while a component renders; the guard reads the store with readSession()
Why: It is an error, not a warning (exit 1). That is why the session moved into a store in client.ts: the guards read it, the sign-in action writes it, request() clears it on a 401, and React subscribes with useSyncExternalStore.
Q9
The guard route has NO shouldRevalidate. As Maya on /volunteers you type "mra", move the cursor two places left and type "a". What happens (measured)?
A) Nothing unusual: the guard is instant
B) npx tsc -b reports that the route needs shouldRevalidate
C) oxlint warns about the guard route
D) The box shows "mara" but the cursor jumps to position 4 instead of 2
Why: Every letter changes the search, the router re-runs the route's loaders by default, and a navigation with a loader waits for it, even an instant one; flushSync cannot help with that wait. onlyWhenThePathChanges skips the guard when only the search changed. Both versions type-check and lint cleanly: only the behavior tells you.
A is wrong: Instant is not the same as no wait: the navigation still waits for the loader.
B is wrong: Types cannot see this; it is runtime behavior.
C is wrong: Both versions lint cleanly.
Q10
Exercise 3 gives the nested :volunteerId route its own volunteerLoader, but WITHOUT calling organizersOnly(args) inside it. A guest opens /volunteers/v16. What happens?
A) The card appears: the child loader ran first
B) The error page shows "Organizers only"
C) The guest ends on the sign-in page, but the browser has already sent GET /api/volunteers/v16 (answered 401)
D) Nothing is sent: the parent guard always runs before the child loader
Why: Loaders of a route and its children run at the same time, not one after the other; the guard's redirect wins, but the child's request is already out. Calling organizersOnly(args) first in the child loader stops it (measured: no request). Today's lab tests the same thing: without the call, 3 tests fail.
A is wrong: The guard's redirect still wins.
B is wrong: A guest is redirected; 403 is for signed-in volunteers.
D is wrong: That is the assumption Exercise 3 disproves.
Q11
Maya types a wrong password into the HQ's sign-in page (a React Router <Form> with signInAction). Without the lesson's passwordRef effect, what would the password box hold afterwards?
A) Nothing: React resets every form after an action
B) The wrong password she typed: a router Form keeps what was typed
C) The text "Email or password is incorrect."
D) Her previous, correct password from sessionStorage
Why: React 19's form actions reset the fields; React Router's actions do not (the lesson's comparison table, measured before the fix). The effect on [result] empties the password through its ref and moves the focus, keeping Lesson 5.2's promise: keep the email, never the password.
A is wrong: That is the React 19 form action of Lesson 5.2, not the router's.
C is wrong: The message is shown in the role="alert" paragraph, not in the field.
D is wrong: Passwords are never stored.
Q12
useSyncExternalStore(onSessionChange, readSession): why does readSession() return the saved variable instead of reading and parsing sessionStorage on each call?
getSnapshot must return the SAME object until the session really changes; parsing creates a new object on every call, so React would see a change on every render
Why: React compares snapshots with Object.is: a fresh object each time means "changed" every time (React warns and re-renders without end). The store keeps current, and only saveSession replaces it and calls the listeners.

export function nextPath(url: URL): string {
  const next = url.searchParams.get('next')
  if (next === null || !next.startsWith('/') || next.startsWith('//') || next.startsWith('/\\')) {

Common Wrong Answers and What They Reveal

  • Q1 B. Still pictures render then fetch. Show the lesson's pending screenshot: the old list, faded, with the sign.
  • Q2 A, B or C. Has not seen that any is assignable to everything; run P1 together.
  • Q4 A or D. Treats "complete" as better than "fast". Ask what one failing report would cost each version.
  • Q6 A. Believes a leading / is enough; the open redirect is exactly that belief.
  • Q7 C. Thinks the guard asks the API. It runs before any request, from the store.
  • Q9 A, B or C. Expects the tools to catch timing problems. Only the behavior tells you; type mra in the crew search on the projector.
  • Q10 D. The lesson's Exercise 3 is the counterexample; the lab's guard-only-in-parent run is the same in a test.
