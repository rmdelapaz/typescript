Lessons

8.1

React Hook Form + Zod

By the end you can
  • Write a Zod 4 schema that is both a TypeScript type and the checks behind it, with messages people understand
  • Tell a schema's input type from its output type (z.input, z.output) and give useForm the right generics
  • Build a form with React Hook Form: register, handleSubmit, formState and zodResolver
  • Show the API's 400 field errors under the right fields with setError, and a form-wide message with a root error
  • Decide when a form needs a library and when React 19's form actions are enough, and say why
Key ideas
  • A Zod schema is one value that checks data and gives TypeScript types: z.object, z.string().trim().min(5, …), z.enum, .refine, z.coerce.number<string>(), an object refine with path and when.
  • Two types: z.input (what the boxes hold: text) and z.output (what a successful check gives: numbers). z.infer is the output.
  • safeParse returns a union on success; z.flattenError(error).fieldErrors gives field → messages.
  • React Hook Form: useForm({ resolver: zodResolver(schema), defaultValues }) with no type arguments; register(name), handleSubmit(save), formState.errors, isSubmitting, setError.
  • The API's 400: setError each key a type predicate accepts (the first one focused) and 'root.server' for the form-wide message. The form is a courtesy; the API is the lock.
  • Two forms, one schema: Plan a cleanup keeps useActionState with safeParse; the edit form uses RHF. Zod stays out of client.ts for the bundle's sake (Lesson 10.1).
Worked example: the schema with Node

The lesson's quick look at the schema, run with Node (node src/try-schema.ts):

// A quick look at the schema with Node. Delete this file when you are done.
import { z } from 'zod'
import { eventFormSchema } from './api/schemas.ts'

const typed = {
  title: '  Dune Grass Cleanup ',
  siteId: 'north-jetty',
  date: '2099-06-14',
  startTime: '09:00',
  endTime: '11:30',
  capacity: '12',
  meetingPoint: 'North jetty steps',
  description: '',
}
console.log(eventFormSchema.parse(typed))

const result = eventFormSchema.safeParse({ ...typed, title: 'Dune', capacity: 'lots', endTime: '08:00' })
if (!result.success) {
  console.log(z.flattenError(result.error).fieldErrors)
}
{
  title: 'Dune Grass Cleanup',
  siteId: 'north-jetty',
  date: '2099-06-14',
  startTime: '09:00',
  endTime: '11:30',
  capacity: 12,
  meetingPoint: 'North jetty steps',
  description: ''
}
{
  title: [ 'Use at least 5 characters for the title.' ],
  capacity: [ 'Capacity must be a whole number from 1 to 200.' ],
  endTime: [ 'The end time must be after the start time.' ]
}

Read it twice. The first object is the checked data: the title lost its spaces, capacity is 12, a number (the output type). The second is z.flattenError(...).fieldErrors: one list of messages per field, the shape the HQ's FieldError already shows, and the end-time message arrives with the others because the object refine has when.

8.2

Complex Forms

By the end you can
  • Describe a list inside a form with a Zod array schema, including a rule about the whole list that puts its message on the right row
  • Build rows people can add and remove with React Hook Form's useFieldArray, with stable keys, typed field paths and sensible focus
  • Build an error summary that takes the focus after a failed save and links to every field with a problem
  • Upload a file with FormData: check it in the browser, send it without breaking the request, and explain the API's 413 and 415 answers
  • Save with PUT and refresh every cached answer the save changes
  • Decide when a long form should become steps, and how to check one step at a time
Key ideas
  • A list in a schema: z.array(rowSchema); counts check the text (regex) and then transform(Number): an empty box is a message, not 0.
  • A rule about the list: .superRefine with context.addIssue({ path: [index, 'category'], … }) puts the message on the repeated row; when lets it run while a count is wrong.
  • useFieldArray: fields (key by field.id), append(row, { focusName }), remove(index) then focus something; paths like items.${index}.count are typed.
  • Error summary: key={submitCount}, takes the focus, links that focus each field; shouldFocusError: false; messages under the fields stay.
  • Uploads: check type and size first (accept is a hint); FormData without a Content-Type header; the API answers 413/415; upload first, keep the id.
  • Save with PUT, write the answer with setQueryData, invalidate what else changed. Steps only when the parts are separate tasks.
Worked example: a rule on the right row

The lesson's report check with Node (node src/try-impact.ts): a duplicate row and an empty box.

// The report schema with Node: a duplicate row and an empty box
import { z } from 'zod'
import { impactReportSchema } from './api/schemas.ts'

const result = impactReportSchema.safeParse({
  volunteersAttended: '11',
  bags: '',
  weightKg: '18.5',
  items: [
    { category: 'plastic-bottles', count: '40' },
    { category: 'glass', count: 'lots' },
    { category: 'plastic-bottles', count: '3' },
  ],
  notes: '',
})
if (!result.success) {
  for (const issue of result.error.issues) {
    console.log(issue.path.join('.'), '→', issue.message)
  }
  console.log(z.flattenError(result.error).fieldErrors)
}
bags → Bags must be a whole number from 0 to 500.
items.1.count → Count must be a whole number from 0 to 100000.
items.2.category → Plastic bottles is already in the list: add to its count.
{
  bags: [ 'Bags must be a whole number from 0 to 500.' ],
  items: [
    'Count must be a whole number from 0 to 100000.',
    'Plastic bottles is already in the list: add to its count.'
  ]
}

Each issue's path says exactly where it belongs: items.2.category is row 3's menu (rows count from 0). The flattened object at the end lost the rows: for nested data, use the paths (React Hook Form's resolver does).
