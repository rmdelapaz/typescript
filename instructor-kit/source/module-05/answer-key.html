3.2 · Props, Children and Composition: self-check

Q1
NextCleanup draws <SiteName name="Driftwood Cove" town="Port Marisol" />. What does React pass to SiteName?
A) Two arguments: 'Driftwood Cove' and 'Port Marisol'
B) Nothing: the component reads the attributes from the page
C) One object: { name: 'Driftwood Cove', town: 'Port Marisol' }
D) A string of HTML it has to parse
Why: Every attribute goes into ONE props object, the second argument of _jsx(SiteName, { name, town }) in the compiled code; the parameter destructures it (Lesson 3.2, Props: a Component's Options Object).
A is wrong: That is how a plain function with two parameters is called; components get one object.
B is wrong: Components never read the page; the parent hands them their data.
D is wrong: TSX compiles to function calls with objects, not to HTML strings.
Q2
A teammate made the step-free badge orange for sites without a step-free route, and tsc prints this. What is the honest fix?
src/components/SiteCard.tsx:19:11 - error TS2322: Type '"success" | "warning"' is not assignable to type '"info" | "success" | undefined'.
Found 1 error in src/components/SiteCard.tsx:19
A) Decide whether the design needs a new tone: add 'warning' to Badge's union (and a .badge-warning style), or keep 'info'
B) Write tone={... as any}
C) Change Badge's tone to tone?: string
D) Delete the tone prop from Badge
Why: The union is the list of looks Badge can draw (a class per word in index.css). Either the design grows by one word, in the union and in the CSS together, or the card uses a tone that exists. Every other answer makes a badge with no style possible (Lesson 3.2, Step 4; Exercise 2).
B is wrong: any switches checking off; the badge would get a class nothing styles.
C is wrong: Then any typo becomes a class name and nothing warns you.
D is wrong: Every badge loses its colors to silence one error.
Q3
Predict what npx tsc -b says about this line in src/Scratch.tsx.
import type { Site } from './api/types.ts'

type SiteImage = Site['picture']
error TS2339: Property 'picture' does not exist on type 'Site'. (the property is called image)
Why: An indexed access type names a property's type, so the property must exist: the same check as reading site.picture in code, only at the type level (Lesson 3.2, Reuse the domain types).
Q4
TideTime declares label?: string. Its first line was changed to function TideTime({ time, label, highlight = false }: TideTimeProps) and tsc prints this. Which change fixes it without changing any caller?
src/Scratch.tsx:10:8 - error TS18048: 'label' is possibly 'undefined'.
Found 1 error in src/Scratch.tsx:10
A) Make label required in TideTimeProps
B) Type the props as any
C) Write label?.toUpperCase()
D) Give label a default in the destructuring: label = 'Low tide'
Why: An optional prop is string | undefined inside the component; a default removes the undefined, so label is a plain string and every caller keeps working (Lesson 3.2, Optional Props and Defaults).
A is wrong: Then every caller that leaves it out gets TS2741: you changed the callers.
B is wrong: any switches the checks off for every prop.
C is wrong: It compiles, but the first TideTime draws ': 06:40' with no label at all.
Q5
Exercise 1's ContactLine takes volunteer: Pick<Volunteer, 'name' | 'phone'> (phone is string | null). Which object literal can a caller pass?
A) { name: 'Hannah Becker' }
B) { name: 'Hannah Becker', phone: null }
C) { name: 'Hannah Becker', phone: 5550102 }
D) { name: 'Hannah Becker', phone: null, role: 'organizer' }
Why: Pick keeps exactly name and phone, both required; null is a real value ("we know there is no phone"). Leaving phone out is TS2741, a number is TS2322 and an extra property in an object literal is TS2353 (Lesson 3.2, Exercise 1; workbook P3).
A is wrong: Missing is not null: TS2741.
C is wrong: phone is text or null: TS2322.
D is wrong: Object literals may not carry properties the type does not list: TS2353.
Q6
A component does site.name = site.name.toUpperCase() before it returns. What reports it?
A) tsc, with TS2540 (read-only property)
B) oxlint's react(immutability) warning; tsc says nothing
C) React, with an error in the console
D) Nothing at all: it is fine to fix up a prop
Why: The props object is not marked readonly, so npx tsc -b is silent; npm run lint warns react(immutability): This value cannot be modified. Work out a new value instead: <h2>{site.name.toUpperCase()}</h2> (Lesson 3.2, Props are read-only).
A is wrong: Only properties typed readonly give TS2540; Site's are not.
C is wrong: React does not watch your objects; the parent's data simply changes behind its back.
D is wrong: It changes the parent's data and breaks the same-inputs-same-output rule from Lesson 3.1.
Q7
tsc prints this for the Note component. Explain the message and name the two-line fix.
src/Scratch.tsx:11:6 - error TS2322: Type '{ title: string; children: Element; }' is not assignable to type 'IntrinsicAttributes & NoteProps'.
  Property 'children' does not exist on type 'IntrinsicAttributes & NoteProps'.
The paragraph between the tags arrived as a children prop and NoteProps has none: add children: ReactNode to NoteProps and draw {children}
Why: Content between a component's tags becomes props.children. A component that does not declare it does not accept any; without TypeScript the paragraph would silently disappear (Lesson 3.2, Children and Composition).
Q8
function SiteName(name: string) is used as <SiteName name="Driftwood Cove" />, and tsc prints this. What is wrong?
src/Scratch.tsx:6:11 - error TS2322: Type '{ name: string; }' is not assignable to type 'string'.
A) The name must be passed in braces: name={'Driftwood Cove'}
B) SiteName must return a string
C) The parameter is the whole props object: destructure it, ({ name }: { name: string })
D) Components cannot take strings, only objects
Why: React passes { name: string; } (one object); the function expects a string. Destructure the props object in the parameter list (Lesson 3.2, Forgetting the braces around the props).
A is wrong: A string in quotes and in braces is the same value.
B is wrong: A component returns TSX; the problem is its parameter.
D is wrong: Props can hold strings; they arrive inside the props object.
Q9
A Badge should show one short word on any page (a town, a terrain, a status). Which props fit best?
A) label: string and tone?: 'info' | 'success' with a default
B) site: Site, so it can pick the word itself
C) children: ReactNode, so it can hold anything
D) One boolean per color: info, success, warning, danger
Why: A general-purpose component takes plain values so any page can use it; variants are a union with a default, not several booleans; a badge holds one short label, so children would invite paragraphs (Lesson 3.2, Designing a Component's Props).
B is wrong: That ties a general component to one kind of data: the home page could not use it for a status.
C is wrong: Children are for frames like Card; a badge is one word.
D is wrong: Booleans allow impossible combinations (info AND danger); a union allows exactly one.
Q10
Someone deletes the line {children} from AppLayout and saves. What tells them before the browser does?
A) Nothing: only the empty page shows it
B) React prints a warning in the console
C) oxlint's react(jsx-key)
D) npx tsc -b: TS6133, 'children' is declared but its value is never read
Why: noUnusedParameters (Lesson 1.2) catches the destructured children that is never used, which here means an empty layout. Only because it is unused: use it somewhere else and nothing warns (Lesson 3.2, Step 7).
A is wrong: The compiler does catch it, through the unused parameter.
B is wrong: React has nothing to warn about: the component returns valid TSX.
C is wrong: jsx-key is about lists without keys.
Q11
Old code: TideTime.defaultProps = { label: 'Low tide' } on a function component that destructures { time, label }. With React 19.3, what does <TideTime time="06:40" /> render, and do tsc or oxlint complain?
<p>: 06:40</p> (no label); neither tool says a word
Why: React 19 ignores defaultProps on function components written in TSX, while tsc and oxlint accept the assignment silently. Move each default into the destructuring (Lesson 3.2, Common Questions).

// Task 1: a small rounded label with a tone. Two tones only: 'info' (the default) and 'warning'.
interface TagProps {
  label: string
  tone?: 'info' | 'warning'
}

export function Tag({ label, tone = 'info' }: TagProps) {
  return <span className={`tag tag-${tone}`}>{label}</span>
}
import type { ReactNode } from 'react'

// Task 2: a frame with a heading. Whatever sits between <Panel> and </Panel> goes under the heading.
interface PanelProps {
  title: string
  children: ReactNode
}

export function Panel({ title, children }: PanelProps) {
  return (
    <section className="panel">
      <h2>{title}</h2>
      {children}
    </section>
  )
}
import type { Site } from './api/types.ts'
import { Panel } from './Panel.tsx'
import { Tag } from './Tag.tsx'

// Task 3a: a site's picture. It needs the picture object only, not the whole site.
export function SitePhoto({ image }: { image: Site['image'] }) {
  return (
    <img
      className="site-photo"
      src={image.url}
      alt={image.alt}
      width={image.width}
      height={image.height}
    />
  )
}

// Task 3b: small pieces composed: the Panel knows nothing about sites, the tile does
export function SiteTile({ site }: { site: Site }) {
  return (
    <Panel title={site.name}>
      <SitePhoto image={site.image} />
      <p>
        <Tag label={site.town} />{' '}
        <Tag
          label={site.accessible ? 'Step-free route' : 'No step-free route'}
          tone={site.accessible ? 'info' : 'warning'}
        />
      </p>
    </Panel>
  )
}

What each task shows: (1) a union prop with a default; the test file's @ts-expect-error lines TEST the type: with tone?: string the first one is "unused" (TS2578) because tone="danger" was accepted; (2) content between the tags arrives as children, and until PanelProps declares it, both the test file and SiteTile get TS2322 (the props TypeScript received included children); (3) Site['image'] for the part, and a tile composed from pieces that know nothing about sites. Accept <Tag ... /> pairs in any order and any wrapper element; the tests look for the texts and classes only. Watch for tone = 'info' written in the interface (tone?: 'info' is a type, not a default).

The Lesson Page's Own Quick Quiz

Lesson 3.2 · Props, Children and Composition
  1. C Badge({ label: 'sand' }), with one object holding every attribute: All attributes are collected into one props object, and the component receives it as its single argument. Destructuring in the parameter list unpacks it, just like an options object in Lesson 2.3.
  2. A A <Card> was used with content inside it but no title attribute: A Card was used with content between its tags (which became children) but without the required title attribute. The fix is in the place that uses Card: add a title.
  3. D 'info' | 'success': The default fills in the value when the prop is left out, so undefined is gone inside the component, and the union of the two words stays. That is why the template literal can only produce badge-info or badge-success.
  4. B ReactNode: ReactNode is React's union of everything it can draw: elements, strings, numbers, arrays of nodes and the values that draw nothing. It is the usual type for children.
  5. A The type of the image property of Site: an object with url, alt, width and height: An indexed access type names the type of one property of another type. Here it is the object with url, alt, width and height, and it follows the API's type if that ever changes.

Exit Ticket

  1. Banner: interface BannerProps { title: string; tone?: 'info' | 'warning' } and function Banner({ title, tone = 'info' }: BannerProps).
  2. children: the content between the component's tags, passed as a prop; typed ReactNode (anything React can draw).
  3. SiteCard versus Badge: SiteCard shows a site, so the domain object is its clearest contract (and keeps working when the card shows one more property); Badge is general-purpose and takes plain values so any page can use it.

Common Wrong Answers and What They Reveal

  • Q1 A (two arguments). Still thinks of components as functions with positional parameters. Show the compiled _jsx(SiteName, { ... }) again.
  • Q4 C (label?.toUpperCase()). Makes the error go away instead of deciding what the screen should show. Ask: what does the first TideTime draw now?
  • Q6 A (TS2540). Expects TypeScript to guard every rule. Name the division of labor: types for shapes, the linter for React's rules, tests for behavior.
  • Q9 B (site: Site). Has not separated domain components from general ones; walk through the design table with Badge on the home page.
  • Q10 A (nothing catches it). Did not connect noUnusedParameters with the empty layout; rerun Step 7's second break.
  • Lab Task 1: tone?: string kept, @ts-expect-error deleted. Edited the test instead of the type: the test file is the contract; put it back and read TS2578 again.
