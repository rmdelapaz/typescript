4.4 · Suspense, use() and Error Boundaries: self-check

Q1
A page has the header, a back link, then <Suspense> around EventDetails, which calls use(eventPromise(id)). The API is slow. What is on the screen?
A) Nothing at all until the cleanup arrives
B) The header and the back link, and the Suspense fallback below them
C) The header only; the back link waits too
D) An error message, until the promise resolves
Why: Everything outside the nearest boundary stays; only the part inside it shows the fallback. With no boundary at all the whole app waits: #root stayed empty (measured in the lesson).
A is wrong: That is the app with no Suspense anywhere.
C is wrong: The back link sits outside the boundary.
D is wrong: Waiting is not failing: errors go to the error boundary.
Q2
A teammate writes const event = use(getEvent(eventId)). tsc and the linter are quiet. What do people see, and what is the fix?
"Loading…" forever, with requests going out non-stop; keep ONE promise per id (eventPromise(id)) instead of a new one every render
Why: A component that suspends is rendered again from the top; a new promise is pending again, so it suspends again. The lesson measured well over a thousand requests in three seconds; the kit's run of the same file: no type errors, 0 lint warnings.
Q3
Which tool printed this (first lines), and why is the code wrong?
  ⚠ react(error-boundaries): Avoid constructing JSX within try/catch
  × react-hooks(rules-of-hooks): React Hook "use" cannot be called in a try/catch block.
A) tsc: use() returns undefined in a try
B) The browser: use() cannot be imported here
C) oxlint: use() must not sit in try/catch; its errors belong to an error boundary
D) oxlint, but it is only style
Why: use() suspends by throwing, so the catch would catch the WAITING and show the error at once (measured). Remove the try; put an error boundary around the component.
A is wrong: tsc has nothing to say about it.
B is wrong: The import is fine.
D is wrong: The rules-of-hooks part is an error, not style.
Q4
Which error does the HQ's ErrorBoundary catch?
A) An error thrown in an onClick handler inside it
B) A rejected promise in a setTimeout callback
C) An error thrown inside the boundary's own render
D) A component inside it that throws while rendering
Why: Boundaries catch errors thrown while rendering the components INSIDE them, including a rejected promise read with use(). Not handlers, not async code, not themselves (the next boundary up does). Lab 4.4's last test proves the click case.
A is wrong: The screen does not depend on it; React leaves the page as it is.
B is wrong: Async code handles its own errors.
C is wrong: The next boundary up catches that.
Q5
tsc reports this for the ErrorBoundary class (first lines). What is missing?
src/components/ErrorBoundary.tsx:21:3 - error TS2416: Property 'state' in type 'ErrorBoundary' is not assignable to the same property in base type 'Component<ErrorBoundaryProps, ErrorBoundaryState, any>'.
  Type '{ failed: boolean; }' is not assignable to type 'Readonly<ErrorBoundaryState>'.
    Property 'error' is missing in type '{ failed: boolean; }' but required in type 'Readonly<{ failed: true; error: unknown; }>'.
A) A type annotation on the field: state: ErrorBoundaryState = { failed: false }
B) The word static
C) A constructor that calls super(props)
D) as const after the object
Why: Without the annotation TypeScript infers { failed: boolean } for the field, which no longer fits the class's declared union state. Annotate it, and only failed: true has an error.
B is wrong: static belongs on getDerivedStateFromError (and is silent when missing).
C is wrong: Field initializers need no constructor.
D is wrong: as const would make it readonly, still not the union.
Q6
The API was down; the page shows Could not load this cleanup with Try again; the API is back. Why does EventPage pass onRetry={() => forgetEvent(eventId)}?
A rejected promise stays rejected: without forgetting it, the retry reads the same failure and sends no request
Why: Measured in the lesson: with onRetry removed, pressing Try again sent nothing and showed the same error. Forgetting makes the next render ask the API again.

5.1 · useReducer with Discriminated Unions: self-check

Q7
Which state is a good fit for useReducer rather than several useState calls?
A) A search box's text
B) Whether a card's details are open
C) Marks and an undo history that must change together, by rules
D) The list of cleanups from the API
Why: Several values that change together, rules for each change, and a next state that depends on the history: one reducer keeps the rules in one place. Server data stays out of reducers.
A is wrong: One value, one obvious setter: useState.
B is wrong: A toggle: useState.
D is wrong: Server data: useApi now, TanStack Query in 7.1.
Q8
tsc reports these two errors for the tally's buttons. Which actions were dispatched?

src/Scratch.tsx:30:55 - error TS2322: Type '"clear"' is not assignable to type '"added" | "reset"'.
Found 2 errors in the same file, starting at: src/Scratch.tsx:27
A) { type: 'added' } without a weight, and { type: 'clear' }, which is no TallyAction
B) { type: 'added', weightKg: '4' } and { type: 'reset' }
C) Two correct actions in the wrong order
D) { type: 'reset', weightKg: 4 } twice
Why: The first message names the member you meant and the field it misses (and where weightKg is declared); the second lists the types that exist. Typed actions catch both before the browser sees them.
B is wrong: A string weight would be a different message.
C is wrong: Order is not a type error.

Q9
A new member was added to TallyAction and the reducer ends with assertNever. What does this tell you, and what do you do?
src/Scratch.tsx:21:26 - error TS2345: Argument of type '{ type: "removed"; weightKg: number; }' is not assignable to parameter of type 'never'.
Found 1 error in src/Scratch.tsx:21
No case handles removed: add a 'removed' case to that switch
Why: assertNever only accepts a value narrowed to never. Adding a member to a union and running npx tsc -b gives a to-do list: one error per switch that needs the new case.
Q10
A reducer ends with default: return state, and a teammate adds an action with no case for it. What happens?
A) tsc reports the missing case
B) The app throws when the action is dispatched
C) Nothing anywhere: it compiles, and the action silently does nothing
D) React warns in the console
Why: The kit ran it: npx tsc -b printed nothing. A default that returns the state swallows every action nobody handles; return assertNever(action) instead.
A is wrong: Only with assertNever (or an annotated return type and no default).
B is wrong: It returns the state.
D is wrong: Nothing warns.
Q11
Inside the reducer someone writes state.marks.set(id, 'attended') then return state. With marks typed as a plain Map, what do people see after a click, and why?
Nothing changes on screen: the same state object came back, so React saw no change and did not render
Why: React compares old and new state with Object.is. The project types marks as ReadonlyMap so this is TS2339 instead of a silent bug: copy first (new Map(old)), then change the copy.
Q12
In development, a console.log as the first line of rosterReducer prints twice per click. Why, and is it a problem?
A) A bug: dispatch was called twice
B) Strict Mode runs the reducer twice to flush out impure reducers; a pure reducer does not care
C) React always runs reducers twice, also in production
D) The reducer is in the dependency array
Why: Measured in the lesson: two logs, one check-in counted. A reducer that sent a request would send it twice: side effects go in handlers or effects.
A is wrong: One click, one dispatch.
C is wrong: Development only.
D is wrong: Reducers are not effects.

P3
A reducer ends with default: return state and the union has a removed member with no case. What does npx tsc -b print?
import { useReducer } from 'react'

interface Tally {
  bags: number
  weightKg: number
}

type TallyAction =
  | { type: 'added'; weightKg: number }
  | { type: 'removed'; weightKg: number }
  | { type: 'reset' }

function tallyReducer(tally: Tally, action: TallyAction): Tally {
  switch (action.type) {
    case 'added':
      return { bags: tally.bags + 1, weightKg: tally.weightKg + action.weightKg }
    case 'reset':
      return { bags: 0, weightKg: 0 }
    default:
      return tally
  }
}

export function BagTally() {
  const [tally, dispatch] = useReducer(tallyReducer, { bags: 0, weightKg: 0 })

  return (
    <section>
      <p role="status">
        {tally.bags} bags, {tally.weightKg} kg
      </p>
      <button type="button" onClick={() => dispatch({ type: 'added', weightKg: 4 })}>
        Add a 4 kg bag
      </button>
      <button type="button" onClick={() => dispatch({ type: 'reset' })}>
        Reset
      </button>
    </section>
  )
}
(no output: no errors)
Why: The default swallows the missing case: no error, and the action silently does nothing. return assertNever(action) turns it into an error.

The Lesson Pages' Own Quick Quizzes

Lesson 4.4 · Suspense, use() and Error Boundaries
  1. B The component suspends and the nearest Suspense boundary shows its fallback: The component suspends: React stops rendering it and shows the fallback of the nearest Suspense boundary above. When the promise resolves, React renders the component again and use returns the cleanup.
  2. D The loading fallback forever, while requests keep going out: Every render creates a new pending promise, so every render suspends, and each resolved promise starts another render with yet another promise. The measured demo sent well over a thousand requests in three seconds and never showed the title. The promise has to come from a cache or be started outside rendering.
  3. A A rejected promise read with use() inside it: use throws the rejection's error while the component renders, and errors thrown during rendering are what error boundaries catch. Errors in event handlers and in async code such as timers are not caught; handle those where they happen.
  4. C Catching rendering errors needs getDerivedStateFromError, and there is no Hook for it yet: Catching a child's rendering error needs the static getDerivedStateFromError method (or componentDidCatch), and React 19.3 has no Hook that does the same. So boundaries are classes, written by you or by a library such as react-error-boundary.
  5. B So the next render gets a new request instead of the same rejected promise: The cache still holds the rejected promise, and a rejected promise stays rejected: use would throw the same error at once. Forgetting it makes eventPromise start a new request on the next render. Measured: without onRetry, Try again sent no request and showed the error again.
Lesson 5.1 · useReducer with Discriminated Unions
  1. D It dispatches { type: 'checkIn', signupId: 's088' }, and rosterReducer returns the next state: The button only reports what happened. React calls rosterReducer with the current state and that action; the reducer returns a new state with the mark and one more history entry, and the desk renders again.
  2. B An error: property weightKg is missing in that object but required by the added action: TS2345: the object is not assignable to TallyAction, because the added member requires weightKg. TypeScript even points at where weightKg is declared. Each action carries exactly the data its kind needs.
  3. C npx tsc -b fails: the startOver action is not assignable to a parameter of type never: In the default branch, action is narrowed to whatever no case handled: the startOver member. That is not assignable to never, so tsc reports TS2345 and names the missing action, at the switch that needs the new case.
  4. A Nothing changes on screen: React got the same state object back, so it did not render: The reducer returned the same object, so React's Object.is comparison saw no change and did not render. Measured: the counts and the badge stayed as they were. Typing the marks as ReadonlyMap makes the set call a compile error instead.
  5. C The rows are server data that later lessons load differently; the reducer keeps only today's marks and history, so it never has to change: The rows are server data: today a saved copy, then useApi after sign-in (5.2), then TanStack Query (7.1). The reducer holds only what the desk itself decides, the marks and their history, so it survives both of those changes untouched. (Lesson 7.2 later changes it on purpose, when saved marks become server data too.)

Exit Ticket

  1. Suspense: the waiting (its fallback while something inside suspends). Error boundary: the failing (its fallback when something inside throws while rendering, including a rejected use()).
  2. Stable promise: a suspended component renders again from the top; a new promise would be pending again and suspend forever, sending a request each time.
  3. assertNever: a compile error naming each action no case handles, and a loud failure if an unexpected value arrives at run time.
