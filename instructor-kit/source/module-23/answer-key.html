10.1 · Performance and the Build: self-check

Q1
npm run build prints "Some chunks are larger than 500 kB after minification". Best first step?
A) Raise build.chunkSizeWarningLimit until it goes away
B) Treat it as a failed build and roll back
C) Look inside the bundle, then split out what most visitors do not need
D) Replace React with a smaller library
Why: It is a warning, not an error: one big file usually means everyone downloads code they do not need. Measure (who downloads what), look (the treemap), then split (Lesson 10.1). Raising the limit changes nothing a visitor downloads.
A is wrong: That silences the message and changes no byte.
B is wrong: The build worked; the warning is advice.
D is wrong: React DOM is the price of using React; the treemap shows bigger wins.
Q2
Before Lesson 10.1, the HQ's build ends like this. What does every visitor download, guest or organizer?
dist/assets/index-B-Vm3u1y.js                            581.69 kB │ gzip: 182.31 kB
A) All 581.69 kB: React, the router, the query library, the form libraries and every page
B) About 182 kB to parse and run
C) Only the code for the pages they open
D) Nothing until they click
Why: One JavaScript file holds everything. The network carries the gzip size (182.31 kB), but the phone still parses and runs all 581.69 kB. The lesson's Network table: 1 file, 581.69 kB, for every kind of visit.
B is wrong: Gzip is what travels; the browser unpacks and runs the full size.
C is wrong: Without dynamic imports there is nothing to load later.
D is wrong: The single file is the first thing index.html loads.
Q3
In a data router, a route's lazy downloads the page's file when?
A) When the app starts
B) After the loader's data has arrived
C) At the same time as the route's loaders, after the click
D) Only after the page has rendered
Why: React Router starts the loaders and the file download together and renders when both are done (measured: the Impact page's file was requested before /api/impact answered). React.lazy inside a page starts only when React renders it: a waterfall.
A is wrong: That would put it back in the first visit.
B is wrong: That is React.lazy's waterfall, not the route's lazy.
D is wrong: The page needs its code to render at all.
Q4
A guest opens a shared link to /events/e08/edit. With the HQ's lazy routes, what happens?
A) The guest sees the edit form: lazy pages skip the guard
B) Nothing is downloaded: the guard runs before any file is requested
C) The build refuses lazy routes behind guards
D) The edit page's file is downloaded while the guard decides, then the guest is sent to sign in
Why: The file loads in parallel with the loaders, so guests following organizer links download that page (measured: 557.32 kB in 7 files). Fine: nothing in front-end code is secret. Splitting is for speed, not for secrets; the guards decide what a person sees, the API what anyone may do.
A is wrong: The guard's loader still redirects.
B is wrong: Loaders and the lazy file start together.
C is wrong: There is no such rule.
Q5
This line gives a type error. Why?
const ImpactChart = lazy(() => import('../components/ImpactChart.tsx'))
A) Charts cannot be loaded lazily
B) React.lazy needs a module with a default export, and ImpactChart is a named export
C) ImpactChart.tsx has its own type error
D) lazy() must be called inside the component
Why: Read the bottom line of TS2322: "Property 'default' is missing". Return { default: ImpactChart } from your own async function (Lab 10.1 Task 2 does the same for TideTables). And call lazy at the top level, never inside a component.
A is wrong: Any component can be lazy.
C is wrong: The error is about the import's shape.
D is wrong: Inside a component, a new lazy component on every render would reload and reset.
Q6
Why do React, React DOM, React Router and TanStack Query get their own vendor group?
A) It makes a guest's first download smaller
B) Vite requires a vendor group
C) It loads those libraries only on the pages that use them
D) Its file keeps its name when only the HQ's own code changes, so returning visitors reuse it
Why: The bytes are the same; the caching is not. Measured: after a tagline change only index got a new name; vendor (355.82 kB) kept vendor-DenlHpDj.js. Lab 10.1's Task 3 shows the same with React alone.
A is wrong: Every page needs those libraries; a group does not remove bytes.
B is wrong: Groups are optional.
C is wrong: Groups decide which file, not when it loads.
Q7
A teammate replaced the two groups with { name: 'vendor', test: /node_modules[\\/]/ },. The build prints this. What happened?
dist/assets/vendor-DJqBY5YG.css                            0.69 kB │ gzip:   0.35 kB

dist/assets/vendor-CUGVkuZG.js                           483.56 kB │ gzip: 149.12 kB
A) Nothing: the forms file was just renamed
B) Zod and React Hook Form moved into the vendor file every page loads, so guests download them again
C) The organizer pages are no longer lazy
D) The build is smaller, so it is better
Why: A group that catches a module the main file needs makes the main file load the whole group. There is no forms file any more, so a test that only looked for that name would pass; the budget test counts bytes and fails (Lesson 10.1, Common Mistakes).

Q8
An old tutorial's manualChunks: { vendor: [...] } in vite.config.ts. What does Vite 8 do?
A) Works as in Vite 7
B) Ignores it silently
C) tsc reports TS2769 (manualChunks must be a function) and the build stops: use codeSplitting.groups
D) Splits every package into its own file
Why: Vite 8 bundles with Rolldown; rollupOptions is a deprecated alias, and Rolldown accepts only the function form of manualChunks (itself deprecated). TypeScript reads the config and says so before the build fails with "manualChunks is not a function".
A is wrong: Vite 7 bundled with Rollup; Vite 8 does not.
B is wrong: It fails loudly, twice.
D is wrong: That is not what it does in any version.
Q9
The e2e budget test checks two things about a guest's visit. Name both, and why a name check alone was not enough.
No /assets/forms- file, AND the total JavaScript under 440 kB; the catch-all vendor group had no forms file yet sent the form libraries to every guest
Why: A budget fails on any cause, including ones you did not think of: one static import of an organizer page, a new library, a group that catches too much (Lesson 10.1, Step 6).
Q10
Why does toCsv put a ' in front of a cell such as =HYPERLINK(...)?
A) Spreadsheets need it for every text cell
B) A cell starting with = + - @ can run as a formula when the file is opened; the quote makes it plain text
C) To mark the cell as a number
D) RFC 4180 requires it
Why: CSV injection: a name or note typed into the app could become a formula on the council's computer. RFC 4180 is about quoting commas, quotes and line breaks; the formula guard is an extra safety rule (Lesson 10.1, Step 4; Lab 10.1 Task 1).
A is wrong: Only cells that start with a formula character.
C is wrong: Numbers are written as they are.
D is wrong: RFC 4180 does not mention formulas.
Q11
In Lab 10.1 the starter's toCsv takes rows and columns typed with any, and the handed-out test file has a @ts-expect-error line. npm run typecheck prints this. What does it mean?
src/csv.test.ts:37:5 - error TS2578: Unused '@ts-expect-error' directive.
The directive expected a type error that never came: the loose toCsv accepts a column that reads a property the rows do not have; a generic toCsv<Row> makes that line an error, and the directive is then used
Why: Testing a type, not a value: @ts-expect-error turns "this must NOT compile" into a check. Vitest runs the code without checking types, so only tsc can run this test.
Q12
Lesson 10.1's Exercise 1 lazy-loaded the 1.31 kB impact chart with React.lazy and measured it. The verdict?
A) Not worth it: it already arrives with the lazy Impact page, and splitting adds a request after the data
B) Worth it: every kilobyte counts
C) It broke the tests
D) It made the vendor file smaller
Why: Measure, then decide. A second request that starts only after /api/impact answered, plus a "Loading the chart…" moment, to save about a kilobyte. With a 100 kB charting library the same few lines would be a clear win (Lab 10.1's tide tables are that case).
B is wrong: Requests cost too; a kilobyte is not worth a waterfall.
C is wrong: The tests passed.
D is wrong: The chart is the HQ's own code, not a vendor library.

Task 1, src/csv.ts:

// Rows of data as a CSV file that spreadsheets open (RFC 4180: CRLF line endings, "…" with doubled quotes)

/** One column of the file: its heading, and how to read its value from a row */
export interface CsvColumn<Row> {
  heading: string
  value: (row: Row) => string | number
}

// A text cell starting with = + - @ could run as a formula when a spreadsheet opens the file ("CSV injection"):
// a ' in front makes the spreadsheet show it as text.
function cell(value: string | number): string {
  if (typeof value === 'number') return String(value)
  const text = /^[=+\-@\t\r]/.test(value) ? `'${value}` : value
  return /[",\r\n]/.test(text) ? `"${text.replaceAll('"', '""')}"` : text
}

/** A heading line, then one line per row, each ending with CRLF */
export function toCsv<Row>(rows: readonly Row[], columns: readonly CsvColumn<Row>[]): string {
  const lines = [
    columns.map((column) => cell(column.heading)),
    ...rows.map((row) => columns.map((column) => cell(column.value(row)))),
  ]
  return lines.map((line) => line.join(',')).join('\r\n') + '\r\n'
}

Task 2, src/App.tsx:

import { lazy, Suspense, useState } from 'react'

// The tables' code (and their data) arrive in a file of their own, the first time someone opens them.
// React.lazy wants a module with a default export, so name the one TideTables.tsx exports.
const TideTables = lazy(async () => {
  const { TideTables } = await import('./TideTables.tsx')
  return { default: TideTables }
})

/** Tide Watch: most visitors only read the next cleanup's tide; few open the full tables */
export function App() {
  const [showTables, setShowTables] = useState(false)
  return (
    <main>
      <h1>Tide Watch</h1>
      <p>Next cleanup: Saturday at Driftwood Cove. Low tide at 09:40, the best time to reach the rocks.</p>
      <button type="button" aria-expanded={showTables} onClick={() => setShowTables((shown) => !shown)}>
        {showTables ? 'Hide the tide tables' : 'Show the tide tables'}
      </button>
      {showTables && (
        <Suspense fallback={<p role="status">Loading the tide tables…</p>}>
          <TideTables />
        </Suspense>
      )}
    </main>
  )
}

Warm-up and Exit Ticket

The warm-up's answers are in the Facilitator Guide.

  1. Before splitting: measure what each visitor downloads (Network tab on the preview), look inside (treemap), then split what most visitors do not need; measure again.
  2. Guest and edit page: React Router downloads the lazy file with the loaders, before the guard redirects. Fine: front-end code is public; the guard decides what a person sees, the API what anyone may do.
  3. Budget vs warning: the warning fires only above 500 kB per chunk; the budget catches any change that sends a guest more JavaScript (a static import, a new library, a catch-all group), and names the forms file if it appears.

Common Wrong Answers and What They Reveal

  • Q1 A. Treats warnings as noise. Ask what the change did for a visitor.
  • Q2 B. Confuses transfer with cost. The phone runs the full size.
  • Q3 B. Mixes up React.lazy and route lazy: the waterfall is React.lazy's.
  • Q4 B or C. Believes splitting hides code. Open any lazy file in the Network tab.
  • Q6 A. Thinks groups reduce bytes. They change names and caching.
  • Q12 A. Splits by reflex. Exercise 1 measured the opposite.
