Session 2 12 self-check items Confidential

Warm-up: Session 1 Retrieval

  1. W1 node spots.ts printed NaN; npx tsc --noEmit spots.ts printed TS2551. Why the difference? Answer: Node removes the types and runs what is left; tsc reads the types and checks them. Running is not checking.
  2. W2 npx tsc -b prints nothing at all in shoreline-hq. Good or bad? Answer: Good: tsc speaks only when something is wrong.
  3. W3 npm run build printed error TS2322. Did vite build run? Answer: No: the script is tsc -b && vite build, and && stops at the first failure.
  4. W4 Which tool flags an unused constant as a warning, and which one makes it an error? Answer: oxlint (npm run lint) warns; tsc reports TS6133 because the app's tsconfig sets noUnusedLocals.

2.1 · Types and Inference: self-check

Q1
In a fresh scratch.ts you write let volunteers = 21 and const capacity = 18. What do the two hovers show?
A) let volunteers: number and const capacity: number
B) let volunteers: number and const capacity: 18
C) let volunteers: 21 and const capacity: 18
D) let volunteers: any and const capacity: any
Why: let may change later, so TypeScript infers the general type; a const never changes, so it gets the literal type 18 (Lesson 2.1, Inference). Literal types become the building blocks of unions in Lesson 2.2.
A is wrong: That is what const capacity: number = 18 would show: the annotation throws the literal away.
C is wrong: A let can be reassigned, so its type cannot be one exact value.
D is wrong: Inference always finds a type for a value you wrote; any comes from outside data (JSON.parse) or a parameter without a type.
Q2
Predict both: does npm run check accept this file, and what does node scratch.ts print?
const saved = JSON.parse('{"capacity": "18"}')
const left: number = saved.capacity - 12
console.log(left)
The check is silent; Node prints 6
Why: JSON.parse returns any, and everything read from an any is any too, so saved.capacity - 12 passes the check. At run time JavaScript turns the text '18' into a number for -. It looks right by luck: with "twelve" it would be NaN. Typed unknown, the check would ask first (TS18046).
Q3
Which of these lines needs a type annotation to pass npm run check in ts-lab?
A) const crewName = 'Shoreline Crew'
B) const bags = [14, 9, 22]
C) let volunteers = 21
D) function spotsLeft(capacity, taken) { ... }
Why: Parameters are an edge: TypeScript does not guess them from the callers and reports TS7006 (Parameter 'capacity' implicitly has an 'any' type). The other three have values to infer from (Lesson 2.1, When to Write a Type).
A is wrong: Inferred as the literal "Shoreline Crew".
B is wrong: Inferred as number[] from the items.
C is wrong: Inferred as number.
Q4
npm run check prints this. What is TypeScript asking you to do?
scratch.ts:4:13 - error TS18046: 'meta' is of type 'unknown'.
A) Annotate the parameter meta
B) Prove what meta is (for example with typeof) before you use it
C) Change unknown to any so the property can be read
D) Add tagLine to the JSON text
Why: TS18046: an unknown value accepts anything but allows nothing until you narrow it. Here the check also finds the typo (tagLine vs tagline) that any let through to a crash (Lesson 2.1, any and unknown).
A is wrong: meta is a variable, not a parameter (that would be TS7006).
C is wrong: That silences the question and brings the crash back: the smoke alarm without batteries.
D is wrong: The data is right; the code misspells the property.
Q5
npm run check reports this for the last line. Which fix answers the question?
const sizes = ['S', 'M', 'L']
const big = sizes.find((size) => size === 'XL')
console.log(big.length)
A) console.log(big!.length)
B) const big: any = sizes.find(...)
C) if (big !== undefined) { console.log(big.length) }
D) Set "strict": false in tsconfig.json
Why: find returns undefined when nothing matches, so big is string | undefined and the check says <code class="inline">error TS18048: 'big' is possibly 'undefined'.</code>. Here nothing matches at all: ! or any would turn the question into a crash (Lesson 2.1, Exercise 2; Lesson 2.2's null toolkit).
A is wrong: ! promises the value is there; with no 'XL' in the list the program crashes.
B is wrong: any switches checking off for big and everything read from it.
D is wrong: Turning strict checks off hides every null question in the project, not just this one.
Q6
In ts-lab you type npx tsc types.ts. What happens, and what do you run instead?
tsc stops with error TS5112 (tsconfig.json is present but will not be loaded if files are specified on the command line); run npm run check (tsc --noEmit with no file name)
Why: Naming a file would ignore the project's settings, so TypeScript 7 refuses. npm run check checks every .ts file in the folder with the tsconfig (Lesson 2.1, Common Mistakes).

2.2 · Shaping Data: self-check

Q7
Which statement about interface and type is true?
A) Only interface can describe an object shape
B) Only type can name a union such as 'draft' | 'scheduled'
C) A type alias can be reopened to add properties later
D) They catch different mistakes in object literals
Why: An interface always describes an object; a type alias names any type, unions included. The course convention (and the API's types.ts): interface for object shapes, type for unions and everything else (Lesson 2.2, interface or type?).
A is wrong: type Site = { ... } describes the same shape and catches the same mistakes.
C is wrong: It is the other way round: two interfaces with one name merge; a second type Site is an error.
D is wrong: Both report TS2561, TS2353 and TS2741 the same way.
Q8
Does npm run check accept return state.message after only the loading check, and what does node scratch.ts print?
type LoadState =
  | { kind: 'loading' }
  | { kind: 'failed'; message: string }

function report(state: LoadState) {
  if (state.kind === 'loading') {
    return 'Loading...'
  }
  return state.message
}
console.log(report({ kind: 'failed', message: 'offline' }))
Yes, the check is silent; it prints offline
Why: Each check removes a member of the union. After if (state.kind === 'loading') return, only the failed member is left, and it has a message. Add a third member without message and the same line becomes TS2339 (Lesson 2.2, A discriminant property).
Q9
What does node scratch.ts print?
const left: number = 0
console.log(left || 'unknown', left ?? 'unknown')
A) 0 0
B) unknown unknown
C) 0 unknown
D) unknown 0
Why: || falls back on any falsy value, and 0 is falsy; ?? falls back only on null and undefined. For "missing", use ?? (Lesson 2.2, Why ?? and not ||).
A is wrong: || replaces the 0.
B is wrong: ?? keeps the 0: it is not null or undefined.
C is wrong: The two operators are the other way round.
Q10
Which use of the non-null assertion ! is honest?
A) document.getElementById('root')! in main.tsx, where index.html in the same project has the element
B) sites.find((site) => site.id === siteId)!.name
C) savedName!.trim() for a name read from sessionStorage
D) event.checkInCode!.length on a cleanup a volunteer opened
Why: ! is a promise TypeScript cannot check. It is fair only for what your own project guarantees: the root element is in your own index.html. Anything from a search, the browser's storage or the API gets an if, ?? or ?. (Lesson 2.2, The ! assertion).
B is wrong: A search can find nothing: the lesson's Seal Rock Pier crash.
C is wrong: A first visit has nothing saved: null.
D is wrong: The API leaves the code out for volunteers: undefined.
Q11
In type LoadState = { kind: 'loading' } | { kind: 'failed'; message: string } | { kind: 'ready'; events: CleanupEvent[] }, what is kind?
A) An optional property
B) A type parameter
C) The discriminant: a shared property with a different literal in each member
D) A readonly property
Why: A discriminated union tells its members apart by one shared literal property; checking it narrows to one member. The course always calls it kind for screen states (Lessons 2.2, 3.3, 4.1) and type for reducer actions (5.1).
A is wrong: Every member has it; nothing is optional.
B is wrong: Type parameters are Lesson 2.3's <T>.
D is wrong: Nothing here says readonly.
Q12
tsc prints this for capacity.toFixed(0). What do you write before the call?
scratch.ts:3:19 - error TS2339: Property 'toFixed' does not exist on type 'string | number'.
A) if (typeof capacity === 'number'), and call it inside
B) capacity: any in the parameter list
C) capacity!.toFixed(0)
D) Turn the union into an interface
Why: With a union you may only use what every member has; numbers have toFixed, strings do not. Narrow with typeof and TypeScript lets you call it inside the if (Lesson 2.2, Narrowing: typeof).
B is wrong: any hides the question; the string case would crash.
C is wrong: ! removes null and undefined, not string.
D is wrong: An interface describes an object, not a string or a number.

2.2 · Shaping Data: predict, then check

P3
Predict what npm run check says, then check.
type Size = 'S' | 'M' | 'L'
const order = { name: 'Volunteer shirt', size: 'M' }
const size: Size = order.size
npm run check
> ts-lab@1.0.0 check
> tsc --noEmit

scratch.ts:3:7 - error TS2322: Type 'string' is not assignable to type 'Size'.

3 const size: Size = order.size
        ~~~~


Found 1 error in scratch.ts:3
Why: The widening trap again: order was built without a type, so order.size is string, and a string is not a Size. const order: { name: string; size: Size } = … (or an interface) fixes it where it is created.
P4
Predict the two lines node scratch.ts prints, then run it.
function spotsText(spotsTaken: number | null) {
  return `${spotsTaken ?? 'not counted'} | ${spotsTaken || 'not counted'}`
}
console.log(spotsText(0))
console.log(spotsText(null))
node scratch.ts
0 | not counted
not counted | not counted
npm run check
> ts-lab@1.0.0 check
> tsc --noEmit
Why: ?? falls back only on null (and undefined), so 0 stays 0; || falls back on 0 too. With null both fall back. The check is silent: both are valid code, and this is a logic choice only you can make.

The Lesson Pages' Own Quick Quizzes

Lesson 2.1 · Types and Inference
  1. B const meetTime: "09:00": A const can never change, so TypeScript infers the literal type, the exact text 09:00. A let with the same value would be inferred as string.
  2. C The parameters in function spotsLeft(capacity, taken): TypeScript does not guess parameter types from the calls, so both parameters would implicitly be any, which strict mode reports as TS7006. Annotate them, for example capacity: number.
  3. A npm run check passes, and the program crashes when it runs: JSON.parse returns any, and everything read from an any is unchecked too. The check passes, and the program crashes when it runs because meta.tagLine is undefined. Typing meta as unknown would have turned this into TS18046.
  4. D TS2345: Argument of type 'number' is not assignable to parameter of type 'string': push is a function call, so the message is about an argument: Argument of type number is not assignable to parameter of type string. TS2345 is the call version of TS2322.
  5. C Use it inside if (session !== null) { … }: getItem returns string or null. Checking session !== null handles the nothing-saved case, and inside the if TypeScript knows session is a string.
Lesson 2.2 · Shaping Data
  1. B type Terrain = 'sand' | 'rocky' | 'marsh' | 'mixed': A union of literal types allows exactly these four strings. Anything else, including a typo, is TS2322 (or TS2820 with a Did you mean suggestion), and the editor suggests the four words as you type.
  2. D TS18048: 'event.checkInCode' is possibly 'undefined': An optional property reads as string or undefined, so TS18048 asks you to handle the missing case, for example with event.checkInCode?.length ?? 0 or an if.
  3. A The property was inferred as string; annotate the object: const flats: Site = …: Object properties can change later, so TypeScript infers the general type string for terrain. Writing const flats: Site = ... checks marsh against Terrain where the object is created.
  4. C Inside if (state.kind === 'failed') { … }: Checking the discriminant narrows state to the member with kind failed, which is the only one that has message.
  5. A unknown: 0 is falsy, so the OR operator falls back to the right side. For missing values use ??, which only falls back on null and undefined and prints 0 here.

Exit Ticket

  1. Annotations: function parameters, a variable that gets its value later, an empty array; data from outside as unknown.
  2. unknown: the check asks what the value is before you use it (TS18046 until you narrow it); any waves every mistake through, and it spreads to everything read from it.
  3. LoadState: type LoadState = { kind: 'loading' } | { kind: 'failed'; message: string } | { kind: 'ready'; events: CleanupEvent[] } (any discriminant name is fine; the course uses kind).

Common Wrong Answers and What They Reveal

  • Q1 A. Has not seen const give a literal type. Hover const meetTime = '09:00' together.
  • Q2 "NaN" or "an error". Thinks the check reads JSON values, or that - refuses text at run time. Run it; then type saved as unknown.
  • Q3 A, B or C. Annotates values TypeScript can see. Back to the decision diagram: does it have its value already?
  • Q5 A. Reaches for !. Run it: the list has no XL.
  • Q9 A or C. Mixes up ?? and ||. Write the falsy values on the board: false, 0, '', null, undefined, NaN.
  • Q10 B, C or D. Trusts data with !. Ask who guarantees each value.
