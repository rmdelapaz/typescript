R1
npm run check in ts-lab reports an error for this function. What does TypeScript want?
import type { LoadState } from './shapes.ts'

export function eventCount(state: LoadState): number {
  return state.events.length
}
A) A narrowing check: state.kind === 'ready' before state.events
B) An annotation: state.events as CleanupEvent[]
C) The non-null operator: state.events!.length
D) Nothing: it is a bug in TypeScript
Why: Only the ready member has events. Check the discriminant first, and TypeScript narrows the state to that member. Skill: union narrowing. Where it comes back: Lesson 2.2; 4.1's LoadState<T> and every page that loads.
R2
What type does TypeScript give items here, and what should you write instead?
const [items, setItems] = useState([])
A) never[]: write useState<Site[]>([])
B) any[]: nothing to change
C) unknown[]: add as Site[]
D) Site[]: TypeScript reads the API
Why: An empty array tells TypeScript nothing about its items. Give the type argument when the start value is empty (or null). Skill: typing empty state. Where it comes back: Lesson 3.4; 4.1's useState<Site[]>([]) and useState<LoadState<…>>.

D) Because TypeScript forbids any
Why: Types disappear before the code runs (Lesson 1.1). A type predicate is the runtime check that earns the type. Skill: data from outside is unknown. Where it comes back: Lesson 2.4; client.ts's isCleanupEvent and getJSON, which 4.1 extends.

4.1 · Effects and Fetching: self-check

Q1
Which of these jobs needs useEffect?
A) Working out how many cleanups match the search box
B) Hiding a card's details when Hide details is clicked
C) Keeping the browser tab's title in step while the sites page is open
D) Formatting a cleanup's date for its card
Why: The tab title is outside React: something to keep in step while the component is on the screen, with a cleanup that puts the old title back (Exercise 2). A value worked out from state is a plain calculation, and a click belongs in its handler: the lesson's "You might not need an effect" table.
A is wrong: Derived from state during render (Lesson 3.4); an effect would only add a second render.
B is wrong: That is the click's own handler.
D is wrong: A pure calculation: formatDate during render.
Q2
On the dev server, EffectLog logs in its effect and in its cleanup. What does the console show after a reload, and why?
import { useEffect } from 'react'

export function EffectLog() {
  useEffect(() => {
    console.log('effect: start')
    return () => console.log('effect: clean up')
  }, [])

  return <p>Open the console.</p>
}
effect: start, effect: clean up, effect: start: Strict Mode mounts, unmounts and mounts again, in development only
Why: The <StrictMode> in main.tsx proves that the cleanup really undoes the effect. The build runs each effect once. Fix a cleanup, never remove StrictMode.
Q3
npx tsc -b prints this for a component that writes useEffect(async () => { … }, []). What is the fix?
src/Scratch.tsx:8:13 - error TS2345: Argument of type '() => Promise<void>' is not assignable to parameter of type 'EffectCallback'.
Found 1 error in src/Scratch.tsx:8
A) Annotate it as useEffect<Promise<void>>
B) Put an async function inside the effect and call it (or use .then)
C) Add getSites to the dependency array
D) Return the promise from a cleanup function
Why: An async function always returns a promise, and an effect may return only nothing or a cleanup function (void | Destructor). Keep the effect synchronous and start the async work inside it.
A is wrong: useEffect takes no type argument; the effect's type is EffectCallback.
C is wrong: Dependencies decide WHEN it runs, not what it may return.
D is wrong: A cleanup must be a function; React would call a promise.

Q5
With the API running, what does this print?
const response = await fetch('http://localhost:4000/api/events?_status=500')
console.log(response.ok, response.status)
console.log(await response.json())
A) false 500, then the API's error object
B) It throws TypeError: Failed to fetch
C) true 500, then the error object
D) It throws an ApiError
Why: fetch rejects only when no answer arrives. An error status still resolves, with ok false: your code has to check it, which is why client.ts throws its own ApiError. Real output: false 500.
B is wrong: That is what happens with no answer at all (the API stopped).
C is wrong: ok is true only for statuses 200 to 299.
D is wrong: ApiError is the HQ's own class: fetch knows nothing about it.
Q6
Which type makes "show the data before it has arrived" impossible to write?
A) { loading: boolean; error?: string; data?: Site[] }
B) Site[] | null
C) { kind: string; data: Site[] }
D) { kind: 'loading' } | { kind: 'failed'; message: string } | { kind: 'ready'; data: Site[] }
Why: Only the ready member has data, so state.data is an error until state.kind === 'ready' narrows it. Lesson 2.2's LoadState, made generic: LoadState<T>.
A is wrong: Three independent fields allow loading AND an error AND data at once.
B is wrong: null cannot say whether it is loading or failed.
C is wrong: data is always there, even while loading.
Q7
Why does the project write .catch((error: unknown) => …) instead of .catch((error) => …)?
Without the annotation the rejection is any, so anything compiles (error.no.such.thing); unknown forces a check first
Why: describeError narrows it with instanceof ApiError (the API answered with an error status) and instanceof TypeError (no answer at all): two different messages for people, the details for the console.
Q8
In the sites page's .catch, why is if (controller.signal.aborted) return the first line?
A) Strict Mode needs it to run the effect twice
B) A request we canceled is not a failure to show anyone
C) abort() only throws in development
D) It retries the request once
Why: The cleanup aborts a request nobody is waiting for any more (the page left, or a dependency changed): the promise rejects with an AbortError, and that is expected, not an error message.
A is wrong: Strict Mode works either way; the check only keeps the canceled run quiet.
C is wrong: Aborting rejects the promise in development and in production.
D is wrong: Nothing retries; the next run of the effect asks again.
Q9
The Network tab on the DEV server shows two requests for /api/sites when /sites opens, the first one canceled. How many does npm run preview show, and why?
One: Strict Mode's start, clean up, start happens in development only
Why: The first request was aborted by Strict Mode's cleanup (net::ERR_ABORTED), which proves the cleanup works; the build runs the effect once.
Q10
With the API running, what does this print?
const response = await fetch('http://localhost:4000/api/events?status=scheduled&when=upcoming&perPage=1')
const items = await response.json()
console.log(items.length, response.headers.get('X-Total-Count'))
1 8: one cleanup in the body, the total of 8 in the X-Total-Count header
Why: Lists come one page at a time; how many there are in all travels in the headers, which readPage reads into Page<T>. The home page shows it: Cleanups coming up: 8.
Q11
An effect fetches and sets state, and has NO dependency array at all. What do npx tsc -b and npm run lint say, and what happens?
A) The linter warns about the missing array
B) tsc reports that useEffect needs two arguments
C) Both pass; the Network tab fills with hundreds of requests
D) React stops the loop after two renders
Why: Render, effect, fetch, setState, render, effect… The lesson measured more than 700 requests in two seconds, with both tools quiet (the kit's run of the same file: 0 warnings, no type errors). Every effect gets an array, even [].
A is wrong: No rule fires for a missing array (the kit ran it: 0 warnings).
B is wrong: The second argument is optional.
D is wrong: Nothing stops it while the page is open.
Q12
A Try again button should show "Loading…" again. Where does setState({ kind: 'loading' }) belong?
A) In the click handler, next to the attempt + 1 that runs the effect again
B) As the first line of the effect
C) In the effect's cleanup
D) In the component body, before the return
Why: Setting state synchronously at the top of an effect renders twice for nothing, and the linter's react(set-state-in-effect) rule says so (Common Mistakes). The click that caused the change sets it (Exercise 1).
B is wrong: The set-state-in-effect warning.
C is wrong: The cleanup undoes the effect; it does not start the next one.
D is wrong: Setting state during render loops forever.

The Lesson Page's Own Quick Quiz

Lesson 4.1 · Effects and Fetching
  1. B Once, after the page has first appeared on the screen: An effect runs after React has updated the screen, and an empty dependency array means only after the first render. The start, clean up, start sequence is Strict Mode, and only in development.
  2. D TS2345: Promise<void> is not assignable to void | Destructor: An async function returns a promise, and EffectCallback may only return nothing or a cleanup function. Put an async function inside the effect and call it, or use then and catch.
  3. A It resolves with a Response whose ok is false and status is 500: fetch rejects only when no answer arrives. A 500 is an answer, so the promise resolves with ok false and the error body. The HQ's request function checks ok and throws an ApiError.
  4. C Strict Mode ran the effect, its cleanup (which aborted the request), and the effect again: In development, StrictMode runs the effect, its cleanup and the effect again. The cleanup aborts the first request, the second one delivers the sites, and the production build sends only one.
  5. B Still Pelican Point's count, and the linter warned about the missing siteId: With an empty array the effect never runs again, so the count stays Pelican Point's. The linter's exhaustive-deps rule warns about exactly this; the fix is the array siteId.

Exit Ticket

  1. The three parts: the effect (runs after the screen is updated), the cleanup it returns (before the next run and when the component goes away), the array (run again when x changed).
  2. [] with siteId read: the effect never runs again, so a new site still shows the first site's data; oxlint's react-hooks(exhaustive-deps) warns; tsc is silent.
  3. Three states: loading ("Loading …", role status), failed (what could not be done and what to try, role alert; details in the console), ready (the data; an empty list is ready with zero items, with its own words).

Common Wrong Answers and What They Reveal

  • Q1 A or D. Reaches for an effect for derived values. Show the lesson's table: is there an outside system?
  • Q3 A or C. Treats the async error as a dependency or typing problem. Read void | Destructor aloud.
  • Q4 B. Believes React re-runs effects on any prop change. Rerun the missing-dependency demo with [siteId] and without.
  • Q5 B or D. Expects fetch to throw on an error status. P1 shows false 500.
  • Q11 A or B. Trusts the tools to catch the flood. Both were quiet in the kit's run; only the Network tab shows it.
  • Q12 B. The set-state-in-effect warning; the click handler owns "show Loading again".
