10.2 · Deploying: self-check

Q1
You deploy the NORMAL build of the HQ (VITE_API_URL=http://localhost:4000) and send the link to a friend. What do they see?
A) The HQ with your computer's data, while your API runs
B) Pages that say they could not reach the server: localhost is THEIR computer
C) The demo with sample data: Netlify switches MSW on
D) A blank page: Netlify refuses React apps
Why: Every VITE_ value is written into the JavaScript at build time; in a visitor's browser localhost is the visitor's own machine. Three honest ways out: the demo build, a hosted API, or a site that only works for you (Lesson 10.2, Environments).
A is wrong: Your laptop is not reachable from their browser.
C is wrong: Only the demo build starts MSW, and only because the build said so.
D is wrong: Static hosts serve any folder of files.
Q2
The live home page works, but reloading /events/e08 shows "Not Found". What fixes it?
A) /* /index.html 200 in public/_redirects
B) A Cache-Control rule in _headers
C) Adding events/:eventId to the router twice
D) Deploying the normal build instead
Why: React Router changed the address without asking the host; on reload the host looks for a file /events/e08 and has none. The rewrite sends index.html with 200 for every address that is not a real file (the SPA fallback); real files still win.
B is wrong: Caching does not create missing files.
C is wrong: The router is fine; the host never reaches it.
D is wrong: Both builds need the fallback.
Q3
A teammate starts the demo API with a hostname check instead of the mode check. The normal build then prints this. What is wrong?
dist/assets/browser-urx2_hst.js                          429.68 kB │ gzip: 164.46 kB
A) Nothing: the browser file is never downloaded
B) tsc should have refused it
C) The minifier failed
D) The API's code is in the normal build, and any HQ deployed to Netlify would answer from sample data
Why: The bundler cannot know the hostname at build time, so the branch and its import stay. import.meta.env.MODE is replaced with text, the dead branch removed. A build decision belongs in the build (Lab 10.2, Task 1).
A is wrong: It is in the build, and on any .netlify.app address it runs.
B is wrong: It type-checks: the bug is about builds, not types.
C is wrong: The minifier did its job; the condition was simply not constant.
Q4
Why may files in /assets/ be cached for a year, but not index.html?
A) Netlify ignores caching for HTML
B) index.html is too small to matter
C) Hashed files get a new name when they change; index.html keeps its name and points at the newest files
D) The service worker caches index.html
Why: A new version of an asset is a new URL, so an old copy can never be used by mistake. index.html must be checked on every visit, or returning visitors keep the old page (and the old file names) for a year.
A is wrong: Hosts apply your headers to any file.
B is wrong: Size is not the point; freshness is.
D is wrong: MSW's worker answers /api requests; it does not cache the page.
Q5
npm run lint prints this and exits with 0. Why does the CI workflow call npm run lint -- --deny-warnings?
⚠ eslint(no-unused-vars): Variable 'password' is declared but never used. Unused variables should start with a '_'.
...
Found 1 warning and 0 errors.
A) To make oxlint faster
B) Without it a warning never fails the step; the HQ's rule is zero warnings
C) --deny-warnings fixes the warnings
D) GitHub requires it
Why: oxlint exits 0 with warnings; with --deny-warnings it exits 1 (measured), which is what turns a CI step red. The -- passes the flag through npm to oxlint.
A is wrong: Speed is unchanged.
C is wrong: It only changes the exit code.
D is wrong: GitHub runs whatever you write.
Q6
In the HQ's workflow, why does the e2e job say needs: checks?
A) The first job installs shoreline-api
B) The e2e job deploys when it passes
C) GitHub runs only one job at a time
D) It waits for the quick checks and skips itself when they are red: no browser minutes for a change that does not compile
Why: needs orders jobs and stops the chain on failure. The e2e job then tests the NORMAL build against the real shoreline-api, which is already in the repository and needs no install.
A is wrong: shoreline-api needs no install; playwright.config.ts starts it.
B is wrong: Nothing in CI deploys; deploying is a step you take on purpose.
C is wrong: Jobs run in parallel unless needs says otherwise.
Q7
Why does the course folder (with shoreline-api and shoreline-hq side by side) become ONE repository?
A) The e2e job starts ../shoreline-api, and workflows live in .github/workflows at the TOP
B) GitHub allows one repository per account
C) Netlify deploys whole repositories
D) So node_modules is shared
Why: playwright.config.ts starts the API from ../shoreline-api, and GitHub only reads workflows at the top of a repository. The top-level .gitignore keeps node_modules, .env.local and .netlify out of all three projects.
B is wrong: Accounts can have many repositories.
C is wrong: The CLI uploads one folder (dist); the repository is for code and CI.
D is wrong: node_modules is never committed.
Q8
What does this print in the course folder, and what does each line prove?
git check-ignore -v shoreline-hq/.env.local shoreline-hq/node_modules shoreline-hq/dist
One line per path naming the .gitignore rule that ignores it: .env.local (shoreline-hq/.gitignore line 13, *.local), node_modules (line 10), dist (line 11): none of them will be committed
Why: git check-ignore -v is proof, not hope: run it before the first commit, then read git status (188 files staged in the course's copy, .env.example yes, .env.local no).
Q9
On Netlify's free plan, which costs credits the course tells you to watch?
A) Every page view of the demo, 15 credits each
B) Each production deploy (15 credits), so deploy by hand after green checks
C) Draft deploys only
D) Nothing: free means unlimited
Why: Netlify Free has 300 credits a month as a hard limit; a production deploy costs 15, bandwidth and requests a little. Twenty production deploys use a month, which is why the lesson deploys by hand (draft, look, then --prod) instead of on every push.
A is wrong: 1 GB of bandwidth costs 20; a visit is about a megabyte.
C is wrong: The lesson only says production deploys cost 15; read the current terms.
D is wrong: The limit is hard: the site pauses until next month.
Q10
Why npx netlify-cli deploy --no-build --dir dist and not plain deploy?
A) --no-build makes the upload smaller
B) --no-build skips the draft
C) Without it the CLI runs a build of its own; you have just built the demo you want
D) dist is the only folder Netlify accepts
Why: The CLI builds before deploying unless told not to (its deploy --help says so), and its build would not be your build:demo. --dir dist uploads the folder as it is, with _redirects, _headers and the worker file; without --prod it is a draft at a temporary address.
A is wrong: Size is the same folder.
B is wrong: --prod decides draft or live.
D is wrong: --dir names any folder.
Q11
Name two checks of the live launch checklist that ONLY make sense from outside your computer.
Any two: the phone on mobile data opens the link; deep links reload; curl -I shows the security headers and the immutable cache on /assets; http redirects to https; no console errors on the live site
Why: Your laptop has your cache, your Wi-Fi and maybe your API running; a visitor has none of them. The checklist is the dress rehearsal for a deploy (Lesson 10.2, Step 7).
Q12
The launch-readiness check prints FIX for "shoreline-hq/.env.local is in the repository". What do you do?
A) Delete the repository on GitHub
B) Nothing: VITE_ values are public anyway
C) Add .env.local to .gitignore again
D) git rm --cached shoreline-hq/.env.local, commit, and keep the file on disk
Why: .gitignore only stops UNtracked files; a file already committed stays tracked until you remove it from the index. Anything in it that is a real secret also has to be changed, because the history keeps it (VITE_ values are public by design, which is why they must never hold secrets).
A is wrong: The local repository has the same problem.
B is wrong: The habit matters: next time it may hold a real key.
C is wrong: It is already ignored; ignoring does not untrack.

The Lesson Page's Own Quick Quiz

Lesson 10.2 · Deploying
  1. B Pages that say they could not reach the server, because localhost is their own computer: localhost in a visitor's browser is the visitor's own computer, where no API runs, so every page reports that it could not reach the server. That is why the course deploys a demo build that carries the API's code.
  2. C /* /index.html 200 in public/_redirects, so the host sends the HQ's page for every address it has no file for: The host looks for a file called events/e08 and has none. The rewrite rule in public/_redirects sends index.html with status 200 for every path without a file, and React Router shows the cleanup.
  3. A The API's code is now in the normal build too, and any HQ deployed on Netlify answers from sample data: Vite can only remove branches it can decide while building. The hostname is known only in the browser, so the API's code ships in the normal build too, and a real HQ deployed to Netlify would quietly answer from sample data.
  4. D Hashed files get a new name when they change, while index.html keeps its name and points at the newest files: A hashed file gets a new name whenever its content changes, so an old copy can never be used by mistake. index.html keeps its name and points at the current file names, so browsers must check it on every visit to see a new deploy.
  5. B It skips the slow browser tests when the quick checks fail, and it tests what a production HQ does: the normal build talking to a real API: needs makes the browser tests wait for the quick checks and skip a change that does not even compile. The normal build against the real API is what a production HQ does, and the budget test keeps proving that no demo code reached it.

Exit Ticket

  1. MODE vs hostname: Vite writes the mode into the code as text, so 'production' === 'demo' is removed with its import; the hostname exists only while the app runs, so the bundler keeps the code (measured: a 429.68 kB browser file in the normal build).
  2. The two files: _redirects rewrites every address without a file to index.html (deep links, reloads); _headers caches hashed assets for a year, leaves index.html to be checked on every visit, and adds nosniff, Referrer-Policy and X-Frame-Options.
  3. Red in CI, green locally: a file not committed (or ignored), the lockfile out of sync with package.json (npm ci refuses), something only on the laptop (.env.local, a running API, a global tool), a Node version difference, a workflow path that assumes another folder.

Common Wrong Answers and What They Reveal

  • Q1 A. Thinks of localhost as "the server". Ask: whose computer is localhost in your friend's browser?
  • Q2 B or D. Has not separated routing from caching. Reload a deep link on netlify dev without the file.
  • Q3 A. Believes unused code is harmless. Show the build table with the browser file.
  • Q6 B. Expects CI to deploy. Deploying is a step you take on purpose.
  • Q9 D. Reads "free" as unlimited. Do the credit arithmetic together.
  • Q12 C. Believes .gitignore untracks files. Run git ls-files | grep env.
