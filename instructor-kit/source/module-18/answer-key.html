Session 18 12 self-check items Confidential

Start Here · Refresher

  1. **R1.** Lesson 4.1's LoadState had three kinds. Name them, and say what TypeScript lets you read in each. **Answer:** loading (nothing), error (the message or error), ready (the data). A switch or an if on kind narrows the union; TanStack Query's result is the same idea with status as its tag.
  2. **R2.** useApi(key, load) from Lesson 4.2: what was the key for, and what happened when it changed? **Answer:** It said what the answer depends on; a new key started a new request (and kept the old data while it loaded). Today's query keys are that idea, shared across components.
  3. **R3.** A guest opens /volunteers. What runs first, and what do they see? **Answer:** The organizersOnly guard loader (Lesson 6.3) throws a redirect to /sign-in?next=%2Fvolunteers before any request; after signing in they land back on the crew list.
  4. **R4.** Why does the events page have no loader, when the sites page does? **Answer:** Its search box changes the address on every letter; a loader on that route breaks typing (Lesson 6.3 measured the caret jumping). The cache gives it the loader's benefits today.

7.1 · TanStack Query: self-check

Q1
Which of these is server state in Shoreline Crew HQ?
A) Whether the Cancel cleanup dialog is open
B) The text typed into the events search box
C) The check-in desk's undo history
D) The roster of today's cleanup
Why: shoreline-api owns the roster; the HQ only holds a copy that can change behind its back (another organizer, another phone). That is what TanStack Query's cache is for (Lesson 7.1, the server state table).
A is wrong: Only that component cares, and nothing outside the browser knows about it: component state.
B is wrong: The search lives in the address since Lesson 6.2: client state that a link can reproduce.
C is wrong: Only this desk knows what it just did: client state in a reducer.
Q2
An organizer filters the events list. Which key does the events list query need?
A) ['events']
B) ['events', 'list', search, viewer]
C) ['events', 'list', viewer]
D) ['events', viewer, 'list']
Why: Everything the answer depends on, general to specific: the search changes the cleanups, and organizers also get drafts. Starting with 'events' lets one invalidateQueries({ queryKey: ['events'] }) reach every list and detail in Lesson 7.2.
A is wrong: Every list, detail and roster would share one entry: the second search shows the first one's cleanups.
C is wrong: Leaves out the search: typing "pelican" changes the address and sends no request (measured in the lesson).
D is wrong: Works, but puts the viewer before the kind of data: keys go general to specific, the viewer last.
Q3
tsc prints this for the lesson's Scratch.tsx. What is list.data before any check, and what removes the undefined?
src/Scratch.tsx:12:8 - error TS2345: Argument of type 'Page<CleanupEvent> | undefined' is not assignable to parameter of type 'number'.
src/Scratch.tsx:13:8 - error TS2345: Argument of type 'CleanupEventDetail' is not assignable to parameter of type 'number'.
src/Scratch.tsx:15:10 - error TS2345: Argument of type 'Page<CleanupEvent>' is not assignable to parameter of type 'number'.
Found 3 errors in the same file, starting at: src/Scratch.tsx:12
Page<CleanupEvent> | undefined; checking list.isSuccess (or an early return on it) narrows it to Page<CleanupEvent>
Why: A query result is a union tagged by status, like Lesson 4.1's LoadState: data exists only on 'success'. The second error shows useSuspenseQuery's data has no undefined at all: it never returns without data. No type argument anywhere: the types come from the factory's query function.
Q4
The API runs with --latency=800. On /events you type "pelican". The events query uses placeholderData: keepPreviousData. What does the page show while the new list loads?
A) "Loading the cleanups…" until the 3 matches arrive
B) An empty list, then the 3 matches
C) The 15 cleanups, until the 3 matches replace them
D) The 3 matches at once, from the cache
Why: A new search is a new key with no data yet; keepPreviousData keeps the last answer on screen meanwhile (isPlaceholderData is true). Measured in the lesson: "Loading the cleanups…" never showed (Exercise 1 adds "Updating…").
A is wrong: That is what happens without placeholderData: the query goes back to 'pending'.
B is wrong: Nothing empties the list: the old data stays until the new data replaces it.
D is wrong: "pelican" was never asked before: there is no entry under that key yet.
Q5
The QueryClient's staleTime is 0 (the default). Maya opens Weekend Cove Cleanup, then presses Back to the events list. What happens?
A) The list appears at once from the cache, and its requests run again behind it
B) The list shows "Loading the cleanups…" until the requests come back
C) Nothing is sent: the list is in the cache
D) The list is thrown away and fetched from scratch
Why: Every answer is stale at once with staleTime 0, so remounting the list refetches it, but a stale answer is still shown immediately. Measured in the lesson: Back sent /sites and /events?perPage=50 again, the list appearing at once. With the HQ's 30 seconds, nothing was sent.
B is wrong: A cached answer, fresh or stale, is shown at once; only a key with no entry waits.
C is wrong: That is the 30-second staleTime: fresh means no request.
D is wrong: Unused entries are kept for gcTime (5 minutes by default): stale is not gone.
Q6
With the HQ's retry rule below, which failure is tried again?
retry: (failureCount, error) =>
  !(error instanceof ApiError && error.status < 500) && failureCount < 2,
A) A 404 for /api/volunteers/v99, once more
B) A 401 after a session ended, twice more
C) A 403 for a volunteer opening the crew list
D) A 500 from the API, up to two more times
Why: Only failures that can change are retried: server errors and network failures, at most twice. A 404, 401 or 403 is an answer, not an accident: asking again gives the same answer (the API says No volunteer with that id. every time).
A is wrong: status < 500: not retried. The default retry made it wait 7.4 s and send 5 requests.
B is wrong: A 401 is below 500; the HQ signs out instead (Lesson 6.3).
C is wrong: Below 500: not retried.
Q7
Code from an older tutorial gives this. What is the version 5 name of this option, and what replaced the other two v4 options in the same object?
src/Scratch.tsx:9:5 - error TS2769: No overload matches this call.
  The last overload gave the following error.
    Object literal may only specify known properties, and 'cacheTime' does not exist in type 'UseQueryOptions<Site[], Error, Site[], string[]>'.

9     cacheTime: 10 * 60 * 1000,
      ~~~~~~~~~
gcTime; keepPreviousData: true became placeholderData: keepPreviousData, and onSuccess was removed from queries
Why: TypeScript stops at the first unknown property (TS2769 names only 'cacheTime'); fix it and the next one shows. isLoading changed meaning too (isPending is "no data yet"). The v5 renames table in Common Mistakes.
Q8
What does this loader line do?
await queryClient.query({ ...sitesQuery(), staleTime: 'static' })
A) Always fetches the sites, then caches them for good
B) Uses any cached copy of the sites, however old, and fetches only when there is none
C) Marks the sites as never stale, so the page never refreshes them
D) Prefetches the sites without waiting for them
Why: staleTime 'static' for this one call makes any cached copy good enough, so a page you have visited before opens at once. It is what the deprecated ensureQueryData did. The page then reads with useSuspenseQuery, whose own staleTime (30 s) still refreshes it in the background.
A is wrong: With a cached copy, nothing is fetched.
C is wrong: The 'static' applies to the loader's call only, not to the entry.
D is wrong: The loader awaits it: the page renders only once the sites are in the cache.
Q9
Why does EventPage build its key from the loader's {eventId, viewer} instead of reading useAuth()?
A) On sign-out the session changes before the loader re-runs; a key from the session would ask for the guest's copy of a draft too early
B) useAuth() cannot be called in a page
C) The loader's viewer is a different person
D) Query keys cannot hold values from context
Why: The loader turns a 404 into "Cleanup not found"; with the key from the loader, the page and its loader always agree, so a signed-out organizer on a draft sees that page instead of an error.
B is wrong: Pages call useAuth() all the time (the events page does).
C is wrong: It is the same person: read at a different moment.
D is wrong: Keys can hold any serializable value.
Q10
Someone removes viewer from the events list key. tsc says this. What would Maya see on the dev server (which does not type-check) after signing in?
src/api/queries.ts:44:45 - error TS6133: 'viewer' is declared but its value is never read.
Found 1 error in src/api/queries.ts:44
The guest's 15 cleanups under an empty Drafts heading: the cache served the guest's entry, because the key did not change when she signed in
Why: Who asks is part of the question. Here tsc caught it only because the parameter became unused (noUnusedParameters); leaving out search instead compiles cleanly (the kit ran it: no output). Make "everything the function uses goes in the key" a reflex.
Q11
The Impact tab's ErrorBoundary has no onRetry={reset}. The report failed to load; the person presses Try again. What happens?
A) A new request, and the report if the API is back
B) The same error at once, and no request
C) The whole page reloads
D) The query retries three times, then the error
Why: The failed query keeps its error in the cache; useSuspenseQuery sees it and throws it again before asking. reset from useQueryErrorResetBoundary() tells the queries below that the next render may try again (measured: 3 attempts, then Try again sent a 4th).
A is wrong: Only with the reset.
C is wrong: The boundary re-renders its children, nothing more.
D is wrong: Retries happened before the error reached the boundary; Try again without reset sends nothing.
Q12
Which value does a component read with useSuspenseQuery(eventQuery(eventId, viewer)).data?
A) CleanupEventDetail | undefined
B) Promise<CleanupEventDetail>
C) CleanupEventDetail
D) unknown, until you add a type argument
Why: useSuspenseQuery suspends while there is no data and throws errors to the nearest boundary, so when it returns, data is there: no undefined, no narrowing (the second TS2345 in Item 3's output).
A is wrong: That is useQuery's data before isSuccess.
B is wrong: use() from Lesson 4.4 took a promise; useSuspenseQuery returns the data.
D is wrong: The type comes from the factory's query function.

Lab 7.1: a cache with good keys (labs/module-18/l7_1-tanstack-query/starter → solution)

As shipped, npm test ends with:

Tests  8 failed (8)

The solution:

Tests  8 passed (8)

and npm run typecheck prints nothing after its two > lines. The solution's key and retry rule:

export function siteEventsQuery(siteId: string, viewer: string) {
  return queryOptions({
    queryKey: ['events', 'site', siteId, viewer],
    queryFn: ({ signal }) => getSiteEvents(siteId, signal),
  })
}

export function shouldRetry(failureCount: number, error: Error): boolean {
  return !(error instanceof ApiError && error.status < 500) && failureCount < 2
}
  • Task 1: the starter's key ['events', 'site', viewer] compiles and lints; with a 30-second staleTime the second site gets the first site's entry and no request. ['events'] still reaches the fixed key because keys match by prefix.
  • Task 2: after if (events.isPending) return … and if (events.isError) return …, events.data is CleanupEvent[] with no undefined; events.error.message is the API's message (No site with that id.). Watch for events.data?.map(...): it hides the narrowing instead of using it.
  • Task 3: the starter's failureCount < 3 retried the 404 three times (4 requests). The solution: 1 request for a 404, 3 for a 500 (the first try and two retries).
  • Stretch: placeholderData: keepPreviousData on the query and a line that says "Updating…" while events.isPlaceholderData.

The Lesson Page's Own Quick Quiz

Lesson 7.1 · TanStack Query
  1. C Page<CleanupEvent> | undefined: The type comes from getEvents through queryOptions, and undefined is there because a pending query has no data yet. Checking list.isSuccess narrows it to Page of CleanupEvent; useSuspenseQuery never has undefined.
  2. A One: The first visit fills the entry; ten seconds later it is still fresh (staleTime is 30 seconds), so the loader and the page both use it without asking the API. That was measured on the preview and the dev server.
  3. D The retry function in queries.ts skips errors below 500: The QueryClient's retry function returns false for an ApiError below 500, so a 404 fails on the first answer. With the default (three retries with growing pauses) the same page took over seven seconds.
  4. B The viewer is part of the key, so a guest's key points at a different entry: The key ends with the viewer: after sign-out it is guest, a different entry with no data yet, so the page asks the API for the guest's list (15 cleanups). The organizer's entry stays in memory until gcTime, but nothing reads it.
  5. C onRetry={reset}, with reset from useQueryErrorResetBoundary(): useSuspenseQuery rethrows a cached error unless the error reset boundary has been reset. The ErrorBoundary calls onRetry, which is reset from useQueryErrorResetBoundary, before rendering the children again, so the query fetches.

Exit Ticket

  1. A key for one site: ['events', 'site', siteId, viewer] (or any key that starts general and holds the site and the viewer).
  2. At once, and a request: the entry is cached but stale; stale answers are shown immediately and refetched in the background.
  3. No 404 retries: the answer cannot change by asking again; the retry function skips ApiErrors below 500.

Common Wrong Answers and What They Reveal

  • Item 1 B (the search text). Thinks "comes from typing into the app" makes it server-ish. Ask: who owns it, and can it change behind your back?
  • Item 2 A or C. Keys as names, not as "what the answer depends on". Lab Task 1 is the cure.
  • Item 5 B. Believes stale means "not shown". Draw the diagram again: stale = shown, then refreshed.
  • Item 6 A. Thinks retries are always kind. Ask what a fourth try at a 404 could return.
  • Item 11 A. Expects boundaries to reset queries by themselves. Show Try again with and without reset in the Network tab.
