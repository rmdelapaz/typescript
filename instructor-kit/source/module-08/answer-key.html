3.6 · Styling and Accessible Components: self-check

Q1
Scratch.module.css has a .note rule. Which class does the browser see on the element that uses styles.note?
A) note
B) styles.note
C) _note_ followed by a short code made from the file and the line number
D) Scratch-module-note
Why: Vite renames every class in a module: an underscore, your name, a code from the file, the line (_note_1pozh_1 in the lesson). The same name in another module gets another code, so they cannot clash (the radio's "Driftwood lead").
A is wrong: That is global CSS: one namespace for the whole app.
B is wrong: That is the JavaScript expression; its VALUE is the generated name.
D is wrong: Not Vite's format; and you never type the generated name yourself.
Q2
A helper function noteClass(): string { return styles.note } gives this. Why is styles.note not a string?
src/Scratch.tsx:5:3 - error TS2322: Type 'string | undefined' is not assignable to type 'string'.
  Type 'undefined' is not assignable to type 'string'.

5   return styles.note
    ~~~~~~


Found 1 error in src/Scratch.tsx:5
vite/client types every module as CSSModuleClasses (any string key), and noUncheckedIndexedAccess adds undefined to every read: TypeScript cannot know the class exists
Why: className accepts string | undefined, so JSX is fine; a function that promises a string is not. It is the honest answer, not a bug (Lesson 3.6, What TypeScript knows about styles).
Q3
You change className={styles.note} to className={styles.ntoe}. What do npx tsc -b and npm run lint say, and what does the page show?
A) tsc reports TS2551 with a Did you mean
B) oxlint warns about an unknown class
C) The build fails, so the page keeps its old look
D) Both are silent; the note loses its border and its element has no class attribute
Why: Any key is allowed, so the typo is a valid string | undefined: undefined, which React leaves out. Run for real: tsc prints nothing and lint says Found 0 warnings and 0 errors. CSS Modules make clashes impossible, not typos.
A is wrong: Only with a declaration file (Exercise 3).
B is wrong: oxlint does not read CSS.
C is wrong: Nothing fails: that is the trap.
Q4
In Badge.tsx, className={${styles.badeg} ${styles[tone]}} (a typo). What does the Elements panel show as the badge's class?
A) class="_badge_1nzko_1 _info_1nzko_9"
B) class="undefined _info_1nzko_9"
C) No class attribute at all
D) Nothing: the badge is not rendered
Why: A template literal turns undefined into the text "undefined". The tone class still works, so the badge keeps its color and loses its pill shape. If you ever see undefined in a class, look for a misspelled module class (Exercise 2).
A is wrong: That is the correct name: the typo reads a key that does not exist.
C is wrong: That happens with className={styles.ntoe} alone: React drops an undefined className, but not a string.
D is wrong: It renders; only its styles change.
Q5
Style object or CSS Module class? (a) a bar as wide as the share of spots taken; (b) a darker color on hover; (c) the card's padding and border.
(a) a style object (the value comes from data); (b) and (c) a class in the component's module
Why: Inline styles are for values computed at run time. A style object cannot express :hover, :focus-visible, dark mode or a media query, and a page full of them is as hard to change as one big stylesheet.
Q6
tsc prints this for a typed style object. Which change fixes it?
src/Scratch.tsx:4:3 - error TS2353: Object literal may only specify known properties, and ''background-color'' does not exist in type 'Properties<string | number, string & {}>'.

4   'background-color': 'var(--kelp)',
    ~~~~~~~~~~~~~~~~~~


Found 1 error in src/Scratch.tsx:4
A) Write backgroundColor
B) Add as CSSProperties after the object
C) Remove the : CSSProperties annotation
D) Put the value in quotes twice
Why: TS2353 is the excess property check from Lesson 2.2: CSSProperties lists every property in camelCase. The annotation is what made TypeScript check the object before it reached style.
B is wrong: An assertion silences the check; the browser would still ignore the property.
C is wrong: Then nothing checks it until the style prop, or never.
D is wrong: The key is the problem, not the value.
Q7
className={styles.skip-link} gives four errors from one line. Why?
A) The module has no skip-link class
B) JavaScript reads it as styles.skip - link: a subtraction
C) CSS Modules forbid dashes
D) The import is missing
Why: styles.skip is possibly undefined, link is not a name, a subtraction gives a number, and className wants a string: four errors. Use camelCase (.skipLink); 'skip-link' in brackets would work but loses the dot.
A is wrong: Even with the class there, the dot syntax cannot read a name with a dash.
C is wrong: Dashes are valid CSS; only the dot access fails.
D is wrong: The import is there; the expression is the problem.
Q8
After a rename, tsc prints this. What is wrong?
src/components/Card.tsx:11:32 - error TS2339: Property 'card' does not exist on type 'typeof import("*.css")'.
Found 1 error in src/components/Card.tsx:11
A) The class is called something else in the CSS file
B) The component must import React
C) styles needs a type annotation
D) The file is Card.css: only *.module.css files are CSS Modules
Why: A plain .css import is global CSS with no class names to hand back, so vite/client types it as an empty module. Rename it Card.module.css and fix the import (Common Mistakes).
A is wrong: The CSS is never read by TypeScript.
B is wrong: The JSX transform needs no import.
C is wrong: An annotation would only hide the real problem.
Q9
With the jsx-a11y plugin on, npm run lint prints this for a site tile. What is the fix?
⚠ jsx-a11y(click-events-have-key-events): Enforce a clickable non-interactive element has at least one keyboard event listener.  src/Scratch.tsx:10:5
⚠ jsx-a11y(no-static-element-interactions): Static HTML elements with event handlers require a role.  src/Scratch.tsx:10:6
⚠ jsx-a11y(alt-text): Missing `alt` attribute.  src/Scratch.tsx:11:7
Found 3 warnings and 0 errors.
The right element: a <button type="button"> instead of the div, and alt="" on the image (the name is already there in text)
Why: Not three attributes on the div: a button is focusable, works with Enter and Space and is announced as a button. tsc said nothing: the types were fine. After the fix: Found 0 warnings and 0 errors.
Q10
The events page has fifteen buttons, each named "Show details". What does the lesson do?
A) Adds <VisuallyHidden> for {event.title}</VisuallyHidden> after the visible words
B) Adds aria-label="Show details" to each button
C) Adds a <span style={{ display: "none" }}> with the title
D) Adds a title attribute with the event's title
Why: Text that screen readers read but that takes no room: every name becomes unique ("Show details for Tide Pool Morning Cleanup") and the visible words still come first, so voice control can say "click Show details". No tool flagged the problem: each button had a name, just not a useful one.
B is wrong: Same name fifteen times again.
C is wrong: display: none hides the text from screen readers too.
D is wrong: A tooltip is not reliably part of the name and is invisible to keyboard users.
Q11
Inside the dark header the focus ring must be orange. How does the lesson do it?
A) A second :focus-visible rule inside Header.module.css
B) outline: none and a box-shadow
C) --focus: var(--sunrise) on .header: the token changes for everything inside, and the one global rule uses it
D) An inline style on every header link
Why: Custom properties are inherited, not scoped by modules: a module can SET a token for its subtree. The global ring reads var(--focus), so one rule serves the whole app.
A is wrong: Two focus rules to keep in step instead of one.
B is wrong: outline: none is the mistake the lesson warns about.
D is wrong: Inline styles cannot express :focus-visible at all.
Q12
Name the layers the lesson checks accessibility with, and one problem only a person finds.
The linter (jsx-a11y), the browser's audits (Lighthouse, axe DevTools), you (a keyboard pass, a screen reader), and later automated tests (Lesson 9.3). A person finds e.g. fifteen identical button names, a wrong alt text, a confusing order
Why: Automated tools are a floor, not a ceiling: they find what a rule can decide, and only some of it.

The Lesson Page's Own Quick Quiz

Lesson 3.6 · Styling and Accessible Components
  1. D A generated name that starts with _card_, unique to that file: Vite renames each class to an underscore, the name you wrote, a short code made from the file and the line number. No other file can produce the same name, so the rule cannot clash.
  2. B string | undefined: vite/client types every CSS Module as an index signature of strings, and noUncheckedIndexedAccess adds undefined to every read, because TypeScript cannot know whether the class exists.
  3. C An empty string, alt="": The text next to it already names the link, so the logo is decorative here. An empty alt tells screen readers to skip it, and the link is announced once as Shoreline Crew HQ.
  4. A Style the ring with :focus-visible instead of :focus: focus-visible shows the ring for keyboard focus and usually not after a mouse click, so the designer gets what they asked for and keyboard users keep the ring they navigate by.
  5. B The problems a rule can find are fixed; a keyboard pass and a screen reader check are still needed: Automated tools catch problems a rule can decide, and only some of all problems. Fifteen buttons named Show details passed both; a keyboard pass and a screen reader find what rules cannot judge.

Exit Ticket

  1. Modules: class names scoped to their file, so no clashes and no leftovers when a component goes; a misspelled class still compiles (string | undefined), so look at the page.
  2. Button vs div: reachable with Tab, works with Enter and Space, announced as a button with its name, shows the focus ring (any two).
  3. Record: the type has one key per member of the union, so npm run typecheck reports every table that lacks the new status until it has one.

Common Wrong Answers and What They Reveal

  • Q1 A ("note"). Still thinks in global CSS. Open the Elements panel on their own page.
  • Q3 A (TS2551). Expects TypeScript to read CSS. Show the vite/client line: any key is allowed.
  • Q4 C (no class attribute). Mixes the two typos: React drops an undefined className, but a template literal writes the word.
  • Q6 B (as CSSProperties). Reaches for assertions to silence errors: the property would still be ignored by the browser.
  • Q10 B or C. Thinks a name is enough. Ask them to imagine the screen reader's list of fifteen buttons.
  • Q11 A. Duplicates rules instead of setting a token: show that custom properties are inherited.
