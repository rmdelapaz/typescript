3.5 · Forms and Actions: self-check

Q1
Which field should be a CONTROLLED input (value + onChange)?
A) The email on a one-time sign-up form
B) A note field that is only read when the form is sent
C) The description, when a live "N of 2000 characters" count sits under it
D) Every field in every form: it is the React way
Why: Controlled inputs are for values the screen needs while someone types (a count, a live search, fields that depend on each other); fill-in-and-submit fields are less code as uncontrolled fields read through FormData (Lesson 3.5, Controlled and Uncontrolled Inputs).
A is wrong: Read once at submit: uncontrolled with a name is enough.
B is wrong: Same: nothing needs it before the submit.
D is wrong: Neither kind is "the React way"; each fits a job.
Q2
readTitle declares const title: string = formData.get('title'), and tsc prints this. Which fix is safe?
src/Scratch.tsx:2:9 - error TS2322: Type 'FormDataEntryValue | null' is not assignable to type 'string'.
  Type 'null' is not assignable to type 'string'.
A) typeof value === 'string' ? value.trim() : '' (narrow it)
B) formData.get('title') as string
C) formData.get('title')!
D) String(formData.get('title'))
Why: get returns FormDataEntryValue | null: a string, a File or null. typeof narrows it, and a missing field becomes '' that your checks report (Lesson 3.5, What formData.get really returns).
B is wrong: It compiles and crashes on a misspelled name: Cannot read properties of null.
C is wrong: The ! is the same promise as as string, with less to read.
D is wrong: String(null) is the text "null": a title nobody typed.
Q3
A teammate writes const value = formData.get('titel') as string and then value.trim() in an action. What do npx tsc -b and npm run lint say, and what happens when someone presses Save?
Both tools pass it; the action crashes in the browser: Uncaught TypeError: Cannot read properties of null (reading 'trim')
Why: There is no field named titel, so get returns null, and as string told TypeScript not to worry. One typeof check turns the crash into a message (Lesson 3.5; Lab 3.5 Task 1 is the same bug).
Q4
The waiting-list action was written as joinWaitingList(formData: FormData, _previous: JoinState) and tsc prints this first line. What is wrong?
src/Scratch.tsx:18:46 - error TS2769: No overload matches this call.
A) useActionState needs a type argument
B) The action's parameters are in the wrong order: previous state first, then the FormData
C) JoinState must be an interface, not a union
D) The form needs onSubmit as well as action
Why: An action for useActionState gets (previousState, formData); a plain form action gets (formData). Read the long message from the bottom: a { kind: "idle" } object is not a FormData (Lesson 3.5, Common Mistakes).
A is wrong: The state type is inferred from the action's return type.
C is wrong: A union is exactly right for the state.
D is wrong: With an action React does the submit handling.
Q5
NewEventForm's fieldProps sets defaultValue: values[field]. What would happen without it, after a Publish with mistakes?
A) Nothing: React keeps what was typed in uncontrolled fields
B) tsc reports that defaultValue is missing
C) The messages would not appear
D) The messages appear, and every field is empty again: React resets the form after every action
Why: React resets the form after each action; a field goes back to its defaultValue. The state remembered the values; without defaultValue nothing puts them back. Neither tool catches it (Lesson 3.5, Exercise 2; the kit ran tsc and lint on that change: both silent).
A is wrong: That was true for onSubmit forms; actions reset the form.
B is wrong: defaultValue is optional: tsc has no reason to complain.
C is wrong: The messages come from the state, which still has them.
Q6
Both submit buttons have name="status" (value draft and value scheduled). How does planCleanup know which was pressed?
A) formData.get('status') holds the value of the button that submitted the form
B) React passes the button as a third argument
C) It cannot: two buttons need two forms
D) From event.submitter in an onSubmit handler
Why: The submitting button's name and value are part of the FormData. Enter in a text field presses the FIRST submit button, so Save as draft (the safe choice) comes first (Lesson 3.5, Step 3).
B is wrong: An action gets only the previous state and the FormData.
C is wrong: One form, two submits is the lesson's design.
D is wrong: There is no onSubmit: the form uses action.
Q7
Someone changes fieldProps to return 'aria-invalid': 'yes'. tsc reports 8 errors; this is the end of the first. What does it tell you about spread props?
Types of property '"aria-invalid"' are incompatible.
Type 'string' is not assignable to type '"false" | "grammar" | "spelling" | "true" | boolean | undefined'.
Every spread property is still type-checked against what the element accepts: aria-invalid takes a boolean or "true"/"false" (and grammar, spelling), not 'yes'
Why: {...fieldProps('title')} is not a way around the checks: TypeScript compares the returned object with the element's props, once per field that uses it (Lesson 3.5, Step 3).
Q8
The form has NO noValidate, the capacity input has max={200}, and an organizer types 500 and presses Publish. What happens?
A) The action runs and shows the form's capacity message
B) Chrome blocks the submit and shows its own bubble; the action never runs
C) React throws a validation error
D) The API rejects it
Why: The browser's own checks run first and stop the submit ("Value must be less than or equal to 200." in Chrome). noValidate turns the bubbles off so every message comes from one place and stays on the page (Lesson 3.5, Three places that check).
A is wrong: The action never sees it.
C is wrong: React does not validate fields.
D is wrong: Nothing is sent: the browser stopped it before the action.

Q10
What connects the capacity field to its message for a screen reader?
A) The message's red color
B) Putting the message right under the field
C) A title attribute on the field
D) aria-invalid="true" on the field and aria-describedby pointing at the message's id
Why: aria-invalid announces the field as invalid; aria-describedby makes the reader read the message with the field's name. Color and position help people who see them (Lesson 3.5, Messages that assistive technology can find).
A is wrong: Color alone tells a screen reader nothing.
B is wrong: Position is visual; the markup must connect them.
C is wrong: title is not read reliably and is not the message.
Q11
In NewEventForm, {...fieldProps('title')} became {...fieldProps('titel')}. Why is this a compile error instead of a field that is always empty?
src/components/NewEventForm.tsx:66:45 - error TS2345: Argument of type '"titel"' is not assignable to parameter of type 'EventField'.
fieldProps takes an EventField, a union of the eight field names, so a misspelled name is not a valid argument (TS2345)
Why: Without the union the field would be named titel, readValues would read title (missing, so ''), and the form would say "Add a title." for a title you typed (Lesson 3.5, Step 1 and Step 5).
Q12
What disables Save as draft and Publish while an async action is still running?
A) A useState(false) you set to true in the action
B) The browser, automatically
C) isPending, the third value of useActionState: true until the action's promise settles
D) noValidate
Why: isPending is React's: no extra state to forget to reset. Today's checks finish instantly; in Lesson 7.2 the action waits for the API and the disabled={isPending} line is already there (Lesson 3.5, isPending).
A is wrong: Possible, but more code and easy to get wrong; the Hook gives it to you.
B is wrong: Browsers do not disable buttons for you.
D is wrong: noValidate only turns off the browser's own checks.

The solution's reading and checking:

// formData.get()returns a string, a File (from a file input) or null (no such field)
function readText(formData: FormData, name: SignupField): string {
  const value = formData.get(name)
  return typeof value === 'string' ? value.trim() : ''
}

// Task 1: every field as trimmed text; a field that is missing (or a file) reads as ''.
export function readSignup(formData: FormData): SignupValues {
  return {
    name: readText(formData, 'name'),
    email: readText(formData, 'email'),
    shirt: readText(formData, 'shirt'),
    note: readText(formData, 'note'),
  }
}

// Task 2: a type guard for the four sizes (the <select> hands over any string)
export function isShirtSize(value: string): value is ShirtSize {
  return value === 'S' || value === 'M' || value === 'L' || value === 'XL'
}

// Task 2: one message per problem, under the field it belongs to. An empty object = nothing to fix.
export function validateSignup(values: SignupValues): SignupErrors {
  const errors: SignupErrors = {}
  function add(field: SignupField, message: string) {
    errors[field] = [...(errors[field] ?? []), message]
  }

  if (values.name === '') add('name', 'Add your name.')
  if (!values.email.includes('@')) add('email', 'Enter an email address, such as you@example.com.')
  if (!isShirtSize(values.shirt)) add('shirt', 'Choose a shirt size.')
  if (values.note.length > 200) add('note', 'Keep the note to 200 characters or fewer.')
  return errors
}

The Lesson Page's Own Quick Quiz

Lesson 3.5 · Forms and Actions
  1. B Nothing: React reset the form to its default values: React resets the form after an action, and an uncontrolled field goes back to its defaultValue, here an empty string. That is why the project passes the submitted values back as defaultValue.
  2. D FormDataEntryValue | null: FormDataEntryValue is File or string, and get returns null when there is no such field. Narrow it with typeof value === string before using it.
  3. A The previous state, then the FormData: The previous state comes first, then the FormData. Swapping them gives TS2769, No overload matches this call, because the state is not a FormData.
  4. C So that the chosen site survives the form reset: a new key makes a new select that starts with the newest value: In React 19.3 a select's defaultValue is applied only when the select is created, so after the reset it went back to Choose a site. A new key makes a new select with the newest defaultValue.
  5. B Because anyone can send it a request without the form, so the server must never trust what arrives: Anyone can send the API a request without your form, with curl or a script. Front-end checks are for people; the server is the authority and must check everything it receives.

Exit Ticket

  1. The reset: React resets the form after every action, so uncontrolled fields go back to their defaultValue; giving each field defaultValue from the submitted values (kept in the action's state) puts the text back.
  2. Reading a field: const value = formData.get('title') then typeof value === 'string' ? value.trim() : '' (no as).
  3. The two attributes: aria-invalid on the field and aria-describedby pointing at the message's id.
