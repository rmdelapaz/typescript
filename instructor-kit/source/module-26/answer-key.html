Session 26 12 self-check items Confidential

Part 3 Review: Self-check

Q1
What goes into a TanStack Query key?
A) Everything the query function uses, from general to specific, such as ['events', 'list', search]
B) Only the endpoint's address
C) A random id, so answers never mix
D) The component's name
Why: The key is the answer's address in the cache: two requests that can answer differently need different keys, and general-to-specific keys let one invalidation cover a whole family (['events']).
B is wrong: Two pages of the same address would share one cached answer.
C is wrong: A random key never finds its cached answer again.
D is wrong: Two components asking the same question should share the answer.
Q2
A volunteer's mark should appear at once, before the API answers. What does an optimistic mutation need besides changing the cache first?
A) Nothing: the API always agrees
B) A page reload after the request
C) A rollback to the saved value when the API refuses, then invalidating the keys when it settles
D) A second mutation that repeats the request
Why: Optimistic means the screen goes ahead of the server; when the server says no (a 409, a 500), the old value comes back and the person sees why. Lesson 7.2's test checks exactly that.
A is wrong: Servers refuse: rules, conflicts, outages.
B is wrong: A reload throws away the app's state and the message.
D is wrong: Repeating a refused request does not undo the screen.
Q3
Which value belongs in an app-wide store such as Zustand, saved in the browser?
A) The list of cleanups from the API
B) The status filter a link should share
C) Whether a form field is filled in
D) The person's chosen theme and list density
Why: It belongs to this browser, every screen reads it, and it must survive a reload. Server data lives in TanStack Query, shareable views in the address, form values in the form (Lesson 7.3's placement table).
A is wrong: Server state: TanStack Query.
B is wrong: Address state: search params.
C is wrong: Form state: React Hook Form.
Q4
What reported this typo in register('titel')?
src/Scratch.tsx:7:19 - error TS2345: Argument of type '"titel"' is not assignable to parameter of type '"capacity" | "date" | "description" | "endTime" | "meetingPoint" | "siteId" | "startTime" | "title"'.
A) Zod, when the form was submitted
B) TypeScript: register only accepts the field names of the form's values, typed from the schema
C) The browser's console
D) oxlint
Why: React Hook Form types register from the form values, which come from the Zod schema (z.input): a misspelled field is a compile error instead of a field that never saves (Lesson 8.1).
A is wrong: Zod checks values at run time; the name never reaches it.
C is wrong: This is tsc output, before anything runs.
D is wrong: oxlint does not know the form's fields.
Q5
A schema turns an empty Notes box into null with a transform. What type does the field hold (input), and what does the form hand on (output)?
Input string (the box's text); output string | null
Why: z.input is what the fields hold, z.output what onSubmit receives after the checks and transforms. The API receives the output, which is why Lesson 11.1's request schema accepts null.
Q6
A long form fails with four problems. What does the error summary from Lesson 8.2 give people?
A) A list of every problem at the top, each linking to its field
B) A red border around the whole form
C) One alert with the first problem only
D) The raw Zod issues
Why: Keyboard and screen-reader users reach the summary first and jump straight to each field; each field still shows its own message, linked with aria-describedby.
B is wrong: Color alone tells nobody what to fix.
C is wrong: People fix one problem and meet the next one on the next try.
D is wrong: Machine messages; the schema's own messages are written for people.
Q7
Why do the course's tests find a button with getByRole('button', { name: 'Save' }) rather than a test id?
A) It is faster to run
B) Test ids are not allowed in React 19
C) It finds the button the way people and screen readers do, so a button with no accessible name fails the test
D) It works without a DOM
Why: Querying by role and accessible name tests the page as it is used, and makes accessibility mistakes visible as test failures (Lesson 9.1).
A is wrong: Speed is not the reason.
B is wrong: Test ids work; they just test nothing a person sees.
D is wrong: Testing Library needs a DOM (jsdom).
Q8
A test calls server.use(...) with a handler that answers 500. What happens in the other tests?
A) They all get 500s
B) Nothing: the setup resets the handlers after each test, so the override lives for one test only
C) MSW stops answering
D) The real API is called
Why: Overrides test the error states (the message, the Try again button) without breaking the shared handlers; afterEach(server.resetHandlers) puts them back (the starter's setup does it).
A is wrong: Only until the test ends.
C is wrong: The other handlers stay in place.
D is wrong: Unhandled requests fail the test; nothing reaches a real server.
Q9
What did this end-to-end test find?
  ✘   8 e2e/accessibility.spec.ts:23:7 › dark theme › / has no axe violations (561ms)
...
    Error: expect(received).toEqual(expected) // deep equality
    - Array []
    + Array [
    +   "color-contrast: Elements must meet minimum color contrast ratio thresholds (1)",
...
A) A broken link on the home page
B) A JavaScript error in the dark theme
C) A slow page
D) Text in the dark theme without enough contrast against its background
Why: axe ran on the page in the dark theme and reported a color-contrast violation: the tokens need a dark value that reaches 4.5:1. Rubric row 7 asks for 0 violations in light and dark, at both widths.
A is wrong: axe found a contrast rule broken, not a link.
B is wrong: The page ran; the test compared axe's list with an empty one.
C is wrong: Nothing here measures time.
Q10
The new-event page is a lazy route. What does a guest who only browses the public pages download because of that?
A) Not the new-event page's code, and not the forms chunk it needs
B) Everything, a little later
C) Only the HTML, never JavaScript
D) The page's code, but not its styles
Why: A lazy route's code (and the libraries only it imports, such as the forms chunk) loads when someone opens it; the budget test measures what a guest really downloads.
B is wrong: Lazy code that is never needed is never fetched.
C is wrong: The app is JavaScript; lazy routes split it.
D is wrong: The page's code is not downloaded at all.
Q11
What does this output prove before the first push?
git check-ignore -v shoreline-hq/.env.local shoreline-hq/node_modules shoreline-hq/dist

shoreline-hq/.gitignore:13:*.local      shoreline-hq/.env.local
shoreline-hq/.gitignore:10:node_modules shoreline-hq/node_modules
shoreline-hq/.gitignore:11:dist shoreline-hq/dist
That .gitignore keeps .env.local, node_modules and dist out of Git (line 13's *.local rule covers .env.local)
Why: Each line names the .gitignore line that ignores the path. A path that is not ignored prints nothing: check before the first commit, because a pushed secret stays in the history.
Q12
Why does Milestone 2 end with a draft deploy instead of leaving deployment for the last week?
A) Netlify requires it
B) Deep-link 404s, missing variables and a CI run nobody saw green are ten-minute fixes in week one and a crisis in week four
C) It makes the app faster
D) Peer reviewers need it before Milestone 3
Why: The walking skeleton proves every joint (types, mock API, routes, build, host) while changes are cheap: Lesson 11.1's "everything on localhost until the last week" mistake.
A is wrong: Nothing forces it; it is a habit.
C is wrong: A deploy changes nothing about speed.
D is wrong: The review is Milestone 7.
