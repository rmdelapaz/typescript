7.2 · Mutations: self-check

Q1
Which of these is true of a mutation and NOT of a query?
A) It runs only when you call mutate or mutateAsync
B) Its answer is kept in the cache under a key
C) It is retried three times by default
D) It runs again when the window regains focus
Why: "Create a cleanup" must happen once, when the organizer presses Publish, not whenever a component mounts. A mutation's answer is not cached and, by default, not retried: a retried POST could create the cleanup twice.
B is wrong: Queries are cached; a mutation leaves behind a cache that is out of date, and cleaning it up is your job.
C is wrong: Queries retry by default; mutations do not (retry 0).
D is wrong: Window-focus refetching is a query's behavior.
Q2
The lesson hands useMutation(cancelEventMutation())'s parts to functions that want a number. From tsc's answer: what does mutate take, and what is data?
src/Scratch.tsx:10:17 - error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
src/Scratch.tsx:11:15 - error TS2345: Argument of type 'CleanupEvent | undefined' is not assignable to parameter of type 'number'.
src/Scratch.tsx:12:15 - error TS2345: Argument of type 'Error | null' is not assignable to parameter of type 'number'.
Found 3 errors in the same file, starting at: src/Scratch.tsx:10
mutate takes the cleanup's id, a string; data is CleanupEvent | undefined (and error is Error | null)
Why: Every type comes from the factory: the variables from the mutation function's parameter, the data from its promise. No type arguments anywhere.
Q3
An organizer marks Diego as checked in. Which keys does the HQ invalidate afterwards?
A) ['events', 'roster', 'e17', 'v01'] only
B) ['events'] only
C) ['events'] and ['volunteers']
D) Every key in the cache
Why: "What could this change have changed?" The roster and the spots left (all under ['events']: a no-show frees a spot), and a volunteer's hours, which the Volunteer type says come from attended cleanups. Code to the contract.
A is wrong: Misses the cleanup's spots line, the lists and the volunteers' hours.
B is wrong: Misses the volunteers' hoursLogged.
D is wrong: Works, but refetches the sites and the impact totals for nothing.
Q4
Which change in the HQ is a good fit for an optimistic update?
A) Publishing a new cleanup
B) Cancelling a scheduled cleanup
C) Deleting a draft
D) A check-in mark at the desk
Why: Small, frequent, easy to undo, and the answer holds nothing you need: show it at once, roll back if the API says no. The others are big or need the API's answer (a new id).
A is wrong: The new cleanup's id comes from the API: you cannot show its page before it answers.
B is wrong: Telling 18 volunteers their Saturday is off must only happen when it is true.
C is wrong: Hard to take back; wait for the API.
Q5
The rollback in markMutation's onError was written as setStatus(signupId, saved.before). Why does tsc refuse it, and what is the fix?
src/api/mutations.ts:68:27 - error TS18048: 'saved' is possibly 'undefined'.
src/api/mutations.ts:68:27 - error TS2345: Argument of type 'SignupStatus | undefined' is not assignable to parameter of type 'SignupStatus'.
Found 2 errors in the same file, starting at: src/api/mutations.ts:68
saved is undefined when onMutate itself failed, and before is undefined when the sign-up was not in the cache; check saved?.before !== undefined first
Why: onError can run without onMutate's result, so TypeScript types the third parameter { before } | undefined. The check is not ceremony: rolling back to undefined would break the desk.
Q6
markMutation's onMutate does not call cancelQueries. The API is slow; Maya checks in Diego, then Grace a second later. What can happen to Grace's badge?
A) Nothing: optimistic updates cannot conflict
B) It flips Checked in → Expected → Checked in, when a refetch started by Diego's save lands
C) It stays Expected until the API answers
D) The second PATCH is cancelled
Why: Diego's onSettled refetched the roster; that answer was asked before Grace's change reached the API, so it overwrote her optimistic mark (measured in the lesson: two flips). cancelQueries in onMutate stops refetches already on their way.
A is wrong: Every refetch can bring an older answer back.
C is wrong: That is a waiting mutation, not an optimistic one.
D is wrong: cancelQueries cancels queries (refetches), never mutations.

7.3 · Client State: self-check

Q7
Maya wants the HQ light on her tablet, whatever the tablet says. Where does that choice live?
A) In TanStack Query's cache
B) In the URL's search params
C) In a Zustand store, persisted to localStorage
D) In sessionStorage, next to the session
Why: Not the API's business, read by components far apart, and it should outlive the tab: the last row of the lesson's table. The HQ's display store keeps it under shoreline-hq-ui.
A is wrong: There is nothing to fetch: the server never hears about it.
B is wrong: A link should not change someone's theme; it is a preference, not a place.
D is wrong: sessionStorage ends with the tab; that is right for the session token, wrong for a preference.
Q8
A teammate wrote create<UiState>(persist(…)). tsc starts like this. What is missing?
src/Scratch.ts:10:3 - error TS2345: Argument of type 'StateCreator<UiState, [], [["zustand/persist", UiState]]>' is not assignable to parameter of type 'StateCreator<UiState, [], []>'.
  Type 'StateCreator<UiState, [], [["zustand/persist", UiState]]>' is not assignable to type '{ $$storeMutators?: [] | undefined; }'.
    Types of property '$$storeMutators' are incompatible.
      Type '[["zustand/persist", UiState]] | undefined' is not assignable to type '[] | undefined'.
        Type '[["zustand/persist", UiState]]' is not assignable to type '[]'.
          Source has 1 element(s) but target allows only 0.
The empty pair of parentheses: create<UiState>()(persist(…))
Why: TypeScript cannot take some type arguments from you and infer others in one call. The first call takes UiState; the second infers persist's own types. The last line says it plainly: the middleware's types were not expected ("Source has 1 element(s) but target allows only 0").
Q9
EventCard reads the density with const { density } = useUiStore() (no selector). Fifteen cards are on screen and the person chooses Dark. How many cards re-render?
A) 15
B) 0
C) 1
D) Only the cards whose density changed
Why: Without a selector the component subscribes to the whole state, so every set re-renders it. Measured in the lesson: 15 cards on every theme change, against 0 with the selector state.density === 'compact'.
B is wrong: That is the selector version.
C is wrong: Every card subscribes on its own.
D is wrong: Nobody's density changed: all 15 re-render anyway, for nothing.
Q10
DisplaySettings reads both values with one selector that builds an object. What happens on the dev server?
const { theme, density } = useUiStore((state) => ({ theme: state.theme, density: state.density }))
A) It works, one re-render per change
B) tsc refuses the destructuring
C) Only the first value updates
D) React keeps re-rendering and gives up: Maximum update depth exceeded
Why: A new object on every call is a different answer every time (Object.is), so React never sees a stable snapshot (the console says "The result of getSnapshot should be cached"). One selector per value, or useShallow.
A is wrong: That is what useShallow gives you.
B is wrong: It type-checks and lints cleanly: only running shows it.
C is wrong: Neither value ever settles.
Q11
Someone stores {oops (not JSON at all) under shoreline-hq-ui and reloads. What does the HQ start with?
A) A crash on the first render
B) Match my device and Roomy, with no error in the console
C) The last valid choices, kept somewhere else
D) A purple theme
Why: persist catches a failed parse itself and keeps the store's defaults (measured in the lesson); merge then checks each field of anything that does parse. Data from outside is unknown until a check proves its shape.
A is wrong: persist does not throw on bad JSON.
C is wrong: There is only one saved copy.
D is wrong: There is no purple here; and merge would refuse it.
Q12
Which is a good reason to reach for Redux Toolkit instead of Zustand?
A) The codebase already uses it, or the team wants every change named and replayable
B) It has persistence built in
C) It adds fewer packages
D) It makes server data easier to cache
Why: Named actions, middleware and DevTools time travel are its strength on a large team; an existing codebase is the strongest reason of all. For the HQ's two display values Zustand was 1 package and +4.7 kB against 10 packages and +25.0 kB.
B is wrong: RTK has none: teams write it by hand or add a library such as redux-persist.
C is wrong: 10 packages against 1.
D is wrong: Server data belongs in a server-state cache (TanStack Query, or RTK Query), not in a client store.

7.3 · Client State: predict, then check

P3
A first visit to the HQ: is there a shoreline-hq-ui key in localStorage? After choosing Dark, what JSON is stored under it?
{"state":{"theme":"dark","density":"roomy"},"version":0}
Why: No key on a first visit (persist writes only after the first change), so the store's defaults are what a new person sees. After Dark, the lesson measured this JSON: the actions are left out (JSON cannot hold functions), and version 0 is persist's default.
P4
Fifteen event cards, each with useUiStore((state) => state.density === 'compact'). How many re-render when the person chooses Dark? And Compact?
Dark: 0. Compact: all 15.
Why: The lesson measured it with a Profiler around each card: the boolean selector's answer does not change on a theme change; every card's answer changes on a density change, which is right.

The Lesson Pages' Own Quick Quizzes

Lesson 7.2 · Mutations
  1. D onSuccess invalidated ['events']: createEventMutation's onSuccess invalidates every key starting with events, so the list's entry is stale and is fetched again when the page shows it. Without it, the measured list still said 17.
  2. B { before: SignupStatus | undefined } | undefined: The type is inferred from what onMutate returns, plus undefined, because the mutation can fail before onMutate finished. That is why the rollback checks saved?.before.
  3. A It is a big change that is hard to take back, so the screen should say "Cancelled" only when it is true: Optimistic updates suit small, frequent, easy-to-undo changes. Cancelling affects 18 volunteers; showing it as done before it is true would mislead the organizer if the request failed.
  4. C The desk sends a second PATCH with his old status, then the reducer forgets that history entry: Undo is one more save: markMutation sends Diego's mark from before (confirmed), and when the API accepts it the reducer drops that history entry. Measured: two PATCH requests for s088.
  5. B Shows "Not saved. The server had a problem (500)…" in the form's status line and keeps what she typed: Mutations do not retry by default (a repeated POST could create the cleanup twice). mutateAsync rejects, the action's catch has no fieldErrors to show, and describeError's sentence goes in the status line; the fields keep what Maya typed.
Lesson 7.3 · Client State
  1. C In the URL's search params: A search that a link or Back should reproduce belongs in the URL's search params, where the HQ has kept it since Lesson 6.2. The query key then includes it, so the cache follows the URL.
  2. B 0: The selector still answers false, the same value as before, so Object.is says nothing changed and no card re-renders. Measured: 0, against 15 when a card read the whole store.
  3. D So you can give UiState while TypeScript still infers the middleware's types: TypeScript cannot take some type arguments from you and infer others in the same call. The first call takes UiState; the second infers the middleware's types. Without it, tsc reports TS2345 about the persist mutator.
  4. A Match my device and Compact: merge checks each saved value on its own: purple fails isTheme and falls back to the default, compact passes isDensity and is kept.
  5. B Add it to a slice the way the team does, with an action and the typed Hooks: The codebase already uses Redux Toolkit, which is the strongest reason to use it: a field and a reducer in a slice, read with the team's typed useAppSelector, keep one way of doing things.

Exit Ticket

  1. Wait and optimistic: cancel waits (big, hard to take back, 18 volunteers are told); a check-in mark is optimistic (small, frequent, easy to undo).
  2. After a mark: ['events'] (roster, spots, lists) and ['volunteers'] (hours come from attended cleanups).
  3. Compact selector: useUiStore((state) => state.density === 'compact').

Common Wrong Answers and What They Reveal

  • Item 1 B or C. Mixes up queries and mutations. Compare useQuery (runs on mount, cached, retried) and useMutation (runs when called) side by side.
  • Item 3 A. Invalidates only what is on screen. Ask what else a mark changes (spots, hours).
  • Item 4 B. Thinks optimistic means "faster, so better". Ask what a failure would have told 18 people.
  • Item 9 B. Believes React only re-renders what changed. Without a selector, the component subscribed to everything.
  • Item 12 B. Expects Redux Toolkit to persist by itself. It does not: Zustand's persist was the difference.
