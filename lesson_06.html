🌊 Lesson 2.4: Typing Real Data

Until now every value TypeScript checked was one you typed yourself. Real apps live on data that arrives from somewhere else: an API, a form, a settings file. TypeScript cannot see that data before it arrives, so today you build the door it comes through. You will share types between files instead of copying them, give Shoreline Crew HQ the API's real types, read the settings Vite chose for your project line by line, and write the client that fetches cleanups from shoreline-api and refuses anything that does not match. By the end, the HQ holds its first real data, and every line of it has been checked.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Share types between files with export and import type, and explain what verbatimModuleSyntax asks of you
  • Write type predicates (value is EventStatus) that turn unknown data into checked, typed data
  • Build new types from existing ones with Pick, Omit, Partial and Record, and read them in the API's real types
  • Read every line of the tsconfig files Vite created, and switch on noUncheckedIndexedAccess
  • Configure and type an environment variable (VITE_API_URL) and explain why front-end variables are never secret
  • Fetch cleanups from shoreline-api through a reusable, generic, checked client
  • ⏱️ Time 155 minutes
  • 📋 Prerequisites Lesson 2.3: Functions and Generics (your ts-lab with shapes.ts and functions.ts)
  • 🛠️ You will build Shoreline Crew HQ's data layer: the API's types in src/api/types.ts, a typed .env setting, and src/api/client.ts, which fetches cleanups and checks them before the app uses them
  • 🧩 Stack TypeScript 7.0, Vite 8.3, Node.js 24 (the versions this lesson was checked with)
  • 🧭 Where you work VS Code with your shoreline folder open; a terminal in ts-lab for the first half, then shoreline-api and the HQ's dev server in two terminals

📦 Modules: One Definition, Shared

In Lesson 2.3 you copied CleanupEvent and Volunteer from shapes.ts into functions.ts. Copies drift: fix a property in one file, forget the other, and the two files quietly disagree about what a cleanup is. JavaScript already has the cure, and you have used it from the other side: import and export. Every file in ts-lab is a module (the moduleDetection setting from Lesson 2.1), and a module shares only what it exports.

💡 Mental model: one roster on the board

On cleanup day the crew pins one roster to the board at the meeting point. Team leads read it; nobody keeps a private copy that goes stale when someone signs up late. A type that is exported once and imported everywhere is that roster: change it in one place, and every file that reads it sees the change, with TypeScript pointing at any code the change breaks.

🚪 Checking Data at the Door: Type Predicates

In Lesson 2.1 you learned the rule: outside data is unknown until checked. In Lesson 2.2 you checked an object's properties by hand. Real code needs those checks again and again, so they belong in functions. There is a catch, and it is the subject of this section. Put this in scratch.ts (it imports from your shapes.ts) and run npm run check:

import type { EventStatus } from './shapes.ts'

const eventStatuses: EventStatus[] = ['draft', 'scheduled', 'completed', 'cancelled']

function isEventStatus(value: unknown): boolean {
  return eventStatuses.some((status) => status === value)
}

function describeStatus(value: unknown): string {
  if (isEventStatus(value)) {
    return `a status: ${value.toUpperCase()}`
  }
  return `not a status: ${String(value)}`
}

for (const text of ['"scheduled"', '"finished"', '42']) {
  console.log(describeStatus(JSON.parse(text)))
}
console.log(['draft', 'finished', 'scheduled'].filter(isEventStatus))

A return type of the form parameter is Type is a type predicate. The function still returns a boolean, and the predicate adds a promise: "when I return true, the argument is an EventStatus". A function with one is called a type guard, and TypeScript narrows with it exactly like with typeof:

Look at the last line of output too. ['draft', 'finished', 'scheduled'].filter(isEventStatus) kept the real statuses, and its type is EventStatus[], not string[]. Remember the find overload with value is S from Lesson 2.3? filter has one too: pass a type guard and the result is narrowed as well. The 'finished' is a nod to Lesson 1.2, where the API rejected ?status=finished: now the HQ can reject it as well.

Guarding an object

Most API data is objects. A guard for an object first proves it is an object, then checks each property it promises. The first step is so common that it gets its own small guard:

import type { Volunteer } from './shapes.ts'

// An object (not null, not an array), so its properties can be read
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}

function isVolunteer(value: unknown): value is Volunteer {
  return (
    isRecord(value) &&
    typeof value.id === 'string' &&
    typeof value.name === 'string' &&
    (typeof value.phone === 'string' || value.phone === null)
  )
}

const replies = [
  '{ "id": "v03", "name": "Hannah Becker", "phone": null }',
  '{ "id": "v04", "name": "Theo Nakamura" }',
  '[ "v05", "Amara Diallo" ]',
]
for (const text of replies) {
  const data: unknown = JSON.parse(text)
  if (isVolunteer(data)) {
    console.log(`${data.name}: ${data.phone ?? 'no phone on file'}`)
  } else {
    console.log(`Rejected: ${text}`)
  }
}

Expected output (node scratch.ts; npm run check is silent)

Hannah Becker: no phone on file
Rejected: { "id": "v04", "name": "Theo Nakamura" }
Rejected: [ "v05", "Amara Diallo" ]
  • isRecord narrows unknown to Record<string, unknown>: "an object whose properties you may read, each of them still unknown". (Record is one of the utility types in the next section.) Arrays are objects too, so it rules them out.
  • After isRecord(value) &&, every typeof value.x check narrows one more property. Chaining with && means the first failed check stops the rest.
  • Theo's reply has no phone at all, and it is rejected: a missing property is undefined, which is neither a string nor null. The type said string | null, and the guard holds the data to it.
graph TD A["JSON from outside"] --> B["unknown"] B --> C{"type guard: true?"} C -->|yes| D["typed: Volunteer"] C -->|no| E["reject: never used"]

🛑 A type predicate is a promise TypeScript cannot check

TypeScript trusts the body of a type guard completely. A guard that returns value !== undefined while promising value is number compiles without a word, and every value that passes it is "a number" to TypeScript, even the string 'twelve'. So a guard deserves the same care as the code that uses it: check every property the type promises, and test it with good and bad data, as the three replies above do. Module 8 hands this job to Zod, which writes the checks and the type from one description.

🧰 Utility Types: Types from Types

Apps need many variations of one type. The volunteers list shows only a name and a phone. A "new cleanup" form sends everything except the id and the sign-up count, which the API decides. An edit sends whatever changed. Writing each variation by hand brings back the copying you just removed. Instead, TypeScript ships generic types that build new types from old ones, called utility types. You know enough generics from Lesson 2.3 to read them:

import type { CleanupEvent, EventStatus, Volunteer } from './shapes.ts'

// Pick: only these properties
type Contact = Pick<Volunteer, 'name' | 'phone'>
// Omit: every property except these
type EventDraft = Omit<CleanupEvent, 'id' | 'spotsTaken'>
// Partial: every property optional
type EventEdit = Partial<CleanupEvent>
// Record: an object with exactly these keys, each holding this type
type StatusCounts = Record<EventStatus, number>

const hannah: Contact = { name: 'Hannah Becker', phone: null }
const draft: EventDraft = {
  title: 'Harbor Kayak Cleanup',
  siteId: 'north-jetty',
  status: 'draft',
  startTime: '09:00',
  capacity: 8,
}
const edit: EventEdit = { capacity: 10 }
const counts: StatusCounts = { draft: 2, scheduled: 8, completed: 6, cancelled: 1 }

console.log(hannah.name, draft.title, edit.capacity, counts.scheduled)

With noUncheckedIndexedAccess, reading an array by index (or an object by a key it may not have) gives T | undefined, because nothing guarantees there is an item at that position. Run node scratch.ts and you see why that is right: first([]) "returned a T" and printed undefined. The fixes are the null toolkit from Lesson 2.2: siteIds[0]?.toUpperCase(), a check, or an honest T | undefined return type. Loops like for (const id of siteIds) are not affected: every item there exists. Your three ts-lab files pass unchanged, and the HQ gets the same setting in today's project.

tsc --init's block had a second setting, exactOptionalPropertyTypes. It makes phone?: string mean "may be missing, but never undefined when present". That is precise, but it clashes with how many libraries (React among them) pass optional values, so the course leaves it off, as Vite's template does.

🔐 Environment Variables

The HQ needs to know where shoreline-api runs. On your computer that is http://localhost:4000; on the deployed site in Lesson 10.2 it will be something else. A value that changes between places but not in the code is a job for an environment variable, and Vite reads them from .env files in the project folder:

FileLoadedIn Git?
.env.examplenever (it is documentation)yes: shows which variables the app needs
.envalwaysif it holds nothing personal
.env.localalways, overrides .envno: your machine's values (the template's .gitignore already lists *.local)
.env.production, .env.developmentonly in that mode (npm run build / npm run dev)usually

The code reads them as import.meta.env.VITE_API_URL. Two Vite rules decide what gets there:

  • Only names that start with VITE_ reach your code. Everything else in those files stays out, so a stray value is not exposed by accident.
  • Values are copied into the JavaScript when Vite builds. After npm run build, the text http://localhost:4000 sits in the built file in dist/assets/; the variable's name is gone. Change .env.local and you rebuild. (The dev server notices a changed .env file and restarts itself.)

🛑 Nothing in the front end is secret

Every visitor downloads the built JavaScript, and anyone can read it in the browser's DevTools. So a VITE_ variable is public, whatever file it came from: an API address is fine, a password, a private API key or a database URL never is. Keeping a secret out of Git (.env.local) does not keep it out of the bundle. Secrets live on a server, which uses them on the app's behalf; shoreline-api plays that part for the crew.

And the type? vite/client describes import.meta.env with MODE, DEV, PROD and a few more, plus a catch-all: any other name is any. That means import.meta.env.VITE_API_ULR, typo included, passes the check. In the project you will switch the catch-all off and describe VITE_API_URL yourself, so the variable is typed and a typo is an error.

⚠️ Common Mistakes

⚠️ Using as instead of a check

Tutorials often write (await response.json()) as CleanupEvent[]. as is a type assertion: you tell TypeScript what the data is, and nothing checks it.

import type { Volunteer } from './shapes.ts'

// "as" tells TypeScript what the data is. Nothing checks it.
const person = JSON.parse('{ "id": "v04" }') as Volunteer
console.log(person.name.toUpperCase())

Expected output (node scratch.ts; npm run check is silent)

file:///Users/you/shoreline/ts-lab/scratch.ts:5
console.log(person.name.toUpperCase())
                        ^

TypeError: Cannot read properties of undefined (reading 'toUpperCase')
...

The crash happens far from the line that lied, which is the worst place to debug it. Check data from outside with a type guard; keep as for the rare case where you know more than TypeScript and can say why.

⚠️ A secret in a VITE_ variable

No error message warns you: the build succeeds and the secret ships to every visitor. If a value would hurt in a stranger's hands, it does not belong in the front end at all.

⚠️ Editing the copied types

src/api/types.ts describes what shoreline-api sends; changing it in the HQ does not change the API, it only makes the HQ believe something false. If the API changes, copy the file again. Types the HQ needs on top (such as a Pick for a card) go in the HQ's own files.

  bags: number
  weightKg: number
  byCategory: Record<DebrisCategory, number>
// ...
/** PATCH /api/events/:id (organizers): any subset of the editable fields. */
export type EventChanges = Partial<Omit<NewEvent, 'status'>> & { status?: EventStatus }
// ...
/** Every error response has this body. fieldErrors only on 400 validation_failed. */
export interface ApiErrorBody {
  error: ErrorCode
  message: string
  fieldErrors?: Record<string, string[]>
}

Read each aloud. A roster entry is a sign-up plus a cut-down volunteer (Pick: organizers see the email, not the hours). The impact totals hold a count for every debris category (Record over a union). An edit is "any of the new-event fields except status, all optional" plus a status that may be any of the four (Partial<Omit<…>> joined with &, the intersection from Lesson 2.2). And an error's fieldErrors maps field names to messages (Record<string, string[]>): the shape you saw in Lesson 1.2 when the API rejected finished.

Step 3: The checks (12 min)

Create src/api/client.ts and start with the guards. They are today's predicates, applied to the real CleanupEvent:

shoreline-hq/src/api/client.ts
// Shoreline Crew HQ's API client (Lesson 2.4).
// Data from the API is unknown until a check proves its shape.
import type { CleanupEvent, EventStatus } from './types.ts'

// ---------------------------------------------------------------- checking data

/** An object (not null, not an array), so its properties can be read */
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}

function isStringArray(value: unknown): value is string[] {
  return Array.isArray(value) && value.every((item) => typeof item === 'string')
}

const eventStatuses: EventStatus[] = ['draft', 'scheduled', 'completed', 'cancelled']

export function isEventStatus(value: unknown): value is EventStatus {
  return eventStatuses.some((status) => status === value)
}

// The CleanupEvent properties that hold text
const eventTextFields: (keyof CleanupEvent)[] = [
  'id', 'title', 'siteId', 'date', 'startTime', 'endTime',
  'meetingPoint', 'description', 'leadOrganizerId', 'createdAt', 'updatedAt',
]

export function isCleanupEvent(value: unknown): value is CleanupEvent {
  return (
    isRecord(value) &&
    eventTextFields.every((key) => typeof value[key] === 'string') &&
    isEventStatus(value.status) &&
    typeof value.capacity === 'number' &&
    typeof value.spotsTaken === 'number' &&
    isStringArray(value.suppliesProvided)
  )
}

function isCleanupEventList(value: unknown): value is CleanupEvent[] {
  return Array.isArray(value) && value.every(isCleanupEvent)
}
// ...
  • import type from ./types.ts: the HQ allows the extension (allowImportingTsExtensions), and the import disappears from the built app.
  • eventTextFields is typed (keyof CleanupEvent)[]: "a list of CleanupEvent's property names" (keyof from Lesson 2.3). Eleven properties are strings, so one every checks them all, and a misspelled name in the list is an error, as you will see in Step 5.
  • isCleanupEvent covers all fifteen properties: eleven texts, the status, two numbers and the supplies list. It does not check that date looks like a date; types do not say that either.
  • isCleanupEventList reuses isCleanupEvent through every, the narrowing every overload you just met with filter.
  • Only two guards are exported: the rest are helpers of this file. Lesson 3.4 uses isEventStatus for a status filter.

Step 4: Fetch, check, return (10 min)

Add the part that talks to the API at the end of client.ts:

shoreline-hq/src/api/client.ts
// ...
// ---------------------------------------------------------------- talking to the API

function apiBaseUrl(): string {
  const url = import.meta.env.VITE_API_URL
  if (url === undefined || url === '') {
    throw new Error('VITE_API_URL is not set: copy .env.example to .env.local')
  }
  return url
}

/** GET a path under /api and return the JSON body, unchecked */
export async function apiFetch(path: string): Promise<unknown> {
  const response = await fetch(`${apiBaseUrl()}/api${path}`)
  if (!response.ok) {
    throw new Error(`GET /api${path} failed: HTTP ${response.status}`)
  }
  return response.json()
}

/** GET a path and check the JSON with a type predicate before anyone uses it */
export async function getJSON<T>(path: string, isT: (value: unknown) => value is T): Promise<T> {
  const data = await apiFetch(path)
  if (!isT(data)) {
    throw new Error(`Unexpected data from GET /api${path}`)
  }
  return data
}

export function getEvents(): Promise<CleanupEvent[]> {
  return getJSON('/events', isCleanupEventList)
}

Follow one request through it:

  1. apiBaseUrl reads the variable. Its type is string | undefined (you made it optional), so TypeScript requires the check, and the error message tells the person who forgot .env.local exactly what to do.
  2. apiFetch is async, so it returns a Promise<unknown>: "an unknown, later" (Lesson 2.3 named Promise<T>; Module 4 uses it every day). response.json() is typed Promise<any> by the DOM library, and the written return type turns that any into unknown at the door. A failed HTTP status becomes an error instead of an error page parsed as data.
  3. getJSON<T> is the reusable part: any path, any type, as long as you hand it a type guard for that type. Its second parameter is a function type with a type predicate, (value: unknown) => value is T, so T is inferred from the guard you pass.
  4. getEvents passes isCleanupEventList, so T is CleanupEvent[], and its callers get typed cleanups or an error. Never unchecked data.

💡 Mental model: the sign-in table

Volunteers do not walk straight onto the beach. They stop at the sign-in table, where an organizer checks each name against the roster before handing out gloves and grabbers. getJSON is the table, each type guard is a roster, and everything past the table can trust that whoever made it through was checked. One table, many rosters: that is why the guard is a parameter.

🏋️ Exercise 1: Check the sites

Write isSite, a guard for your draft Site from shapes.ts (including the Terrain union and the nested image object), fetch http://localhost:4000/api/sites, and print each site's name, town and terrain, or a message if the data does not match.

💡 Hint

Reuse isRecord, and write isTerrain like isEventStatus. For the image, isRecord(value.image) narrows the property itself, so the next checks can read value.image.url. A lab file can use await at the top level, because it is a module.

✅ Solution 
import type { Site, Terrain } from './shapes.ts'

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}

const terrains: Terrain[] = ['sand', 'rocky', 'marsh', 'mixed']

function isTerrain(value: unknown): value is Terrain {
  return terrains.some((terrain) => terrain === value)
}

function isSite(value: unknown): value is Site {
  return (
    isRecord(value) &&
    typeof value.id === 'string' &&
    typeof value.name === 'string' &&
    typeof value.town === 'string' &&
    isTerrain(value.terrain) &&
    typeof value.accessible === 'boolean' &&
    isRecord(value.image) &&
    typeof value.image.url === 'string' &&
    typeof value.image.alt === 'string' &&
    typeof value.image.width === 'number' &&
    typeof value.image.height === 'number'
  )
}

const response = await fetch('http://localhost:4000/api/sites')
const data: unknown = await response.json()
if (Array.isArray(data) && data.every(isSite)) {
  for (const site of data) {
    console.log(`${site.name} (${site.town}): ${site.terrain}`)
  }
} else {
  console.log('The sites do not match the Site type')
}

🏋️ Exercise 3: A guard that makes guards (Stretch)

Optional stretch, not counted in the lesson time (about 15 minutes).

isCleanupEventList is a one-line wrapper you would write again for sites, volunteers and sign-ups. Write a generic isListOf that takes a guard for one item and returns a guard for a list of them, so that const isCrew = isListOf(isVolunteer) works and isCrew(data) narrows data to Volunteer[].

💡 Hint

The parameter is (value: unknown) => value is T, like getJSON's. The return type is the same kind of function type, with value is T[]. Inside, return an arrow function.

✅ Solution 
import type { Volunteer } from './shapes.ts'

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}

function isVolunteer(value: unknown): value is Volunteer {
  return (
    isRecord(value) &&
    typeof value.id === 'string' &&
    typeof value.name === 'string' &&
    (typeof value.phone === 'string' || value.phone === null)
  )
}

// Takes a check for one item, returns a check for a list of them
function isListOf<T>(isItem: (value: unknown) => value is T): (value: unknown) => value is T[] {
  return (value: unknown): value is T[] => Array.isArray(value) && value.every(isItem)
}

const isCrew = isListOf(isVolunteer)

  console.log(`${data.length} volunteer: ${data.map((person) => person.name).join(', ')}`)
}

❓ Common Questions at This Stage

Why copy types.ts instead of importing it from ../shoreline-api?

The HQ must build on its own: on a hosting service in Lesson 10.2, or on a teammate's computer, there may be no shoreline-api folder next to it. A copy makes the contract part of the app. The volunteers' phone app in the React Native course copies the same file. On a larger team the shared types would live in a package that both sides install; the idea is the same, the delivery is fancier.

Do I have to write a type guard for every type?

For every type that arrives from outside, something must check it. By hand, that is a lot of careful code, and a hand-written guard can drift from its type when someone adds a property. That is exactly the problem Zod solves in Lesson 8.1: one schema produces both the check and the type. Until then, the HQ checks events, and later lessons add guards for what they fetch.

I have seen import { type Site, getSites }. Is that different?

It is the inline form: type in front of one name marks only that name as type-only, so one line can import a type and a value from the same file. verbatimModuleSyntax accepts both forms. When everything you import from a file is a type, import type { … } says it once.

Why is VITE_API_URL optional in the type, when .env.local sets it?

Because the type should describe what can really happen, and a fresh download has no .env.local until someone copies it. Optional forces the code to handle "not set" with a clear message. Declaring it as a plain string would be a small lie, like as: the check would pass and the app would request undefined/api/events.

🎓 Key Takeaways

  • Share types with export and import type: one definition, no copies. Type-only imports are removed before the code runs (verbatimModuleSyntax, TS1484)
  • A type predicate (value is T) turns a boolean check into narrowing; guards check every promised property, because TypeScript trusts them. as checks nothing
  • Utility types build variations: Pick, Omit, Partial, Record; the API's own types use all four
  • Vite's tsconfig is split into app and node projects; strict is the TypeScript 7 default, and noUncheckedIndexedAccess makes indexing honest (T | undefined)
  • VITE_ variables come from .env files, are typed in vite-env.d.ts, and are copied into the public JavaScript: never secrets
  • The HQ's client fetches unknown, checks it with a guard passed to the generic getJSON<T>, and returns typed data or an error
