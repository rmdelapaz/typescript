🌊 Shoreline API Reference

Everything Shoreline Crew HQ can ask shoreline-api, what it answers, and the switches that make it slow, failing or reachable from somewhere else.

🧭 About the API

shoreline-api is the course's mock back end: the cleanup events, beach sites, volunteers, sign-ups and impact numbers of Shoreline Crew, a fictional beach-cleanup group. It needs no install and has no dependencies: with Node.js 24 or newer, run node server.ts in its folder and it answers at http://localhost:4000/api. The data lives in memory and is rebuilt around today's date each time it starts. Lessons never change the API; you only download it. The React Native course builds the volunteers' phone app against the same API.

Download shoreline-api.zip (Lesson 1.2 sets it up). Its README.md is the short version of this page. For the words used here, see the Glossary; for error messages in the app, Troubleshooting.

▶️ Run It

Open a terminal in the folder, start the server and keep that terminal open while you work (a second terminal runs the HQ). Stop it with Ctrl+C. Lesson 1.2.

cd shoreline-api
node server.ts

Expected output

Shoreline Crew API running at http://localhost:4000/api
  sample sign-in: maya.okafor@example.com (organizer) or theo.nakamura@example.com (volunteer), password shoreline-demo
Press Ctrl+C to stop.

Open http://localhost:4000/api in a browser for the list of every endpoint. Starting the server again builds fresh sample data: everything you created is gone, and so is every sign-in.

node server.ts --latency=300-1500     # every answer waits 0.3 to 1.5 seconds
node server.ts --fail-rate=0.2        # about 1 request in 5 answers 500
node server.ts --port=4100 --quiet    # another port, no request log
node server.ts --help                 # the list of options

An unknown option stops the server with the list of valid ones. If the port is taken it says port 4000 is already in use. Is the API already running in another terminal? Or start it with --port=4100 (see Troubleshooting). In the folder, npm start runs node server.ts, npm run dev restarts it when a file changes (node --watch), and npm test runs the API's own tests (node --test); none of them needs npm install.

🐢 Slow and Failing Answers

Real networks are slow and servers fail. Two server options change every answer; two query parameters change one request without a restart. Lesson 4.1 uses them to test loading and error states.

SwitchScopeEffect
--latency=MS or MIN-MAXevery requestwaits before answering. /api/health and /api/_reset are never slowed down.
--fail-rate=0-1every requestthat share answers 500 with the message Simulated server error (the server was started with --fail-rate). Health and reset never fail.
?_delay=2000this requestwaits that many milliseconds (at most 10000) instead of the --latency wait
?_status=500this requestanswers that status (any 400 to 599) with the usual error body, for example { "error": "server_error", "message": "Simulated 500 response (the _status parameter)." }; a 404 gets not_found, a 401 unauthorized, and so on

Remove a ?_status= you added to a path in client.ts when you are done: left in place, every page shows the error. Lesson 4.1.

How a session works. POST /api/auth/sign-in with { "email", "password" } answers { token, user }. Send the token on every later request as Authorization: Bearer <token>. POST /api/auth/sign-out ends it (204). Tokens are opaque strings kept in the server's memory, so restarting the API or POST /api/_reset ends every session.

📦 Requests, Lists and CORS

  • Addresses: everything is under /api; a trailing slash is fine. HEAD works wherever GET does. Ids in paths are the ids in the data (e08, pelican-point, v04).
  • Bodies: JSON in (Content-Type: application/json) and JSON out. A body that is not a JSON object answers 400 The request body must be JSON. or The request body must be a JSON object. Only photo uploads send something else.
  • Caching: JSON answers carry Cache-Control: no-store, so the browser never reuses an old answer; site pictures and photos may be cached for an hour.
  • Dates: a date is "YYYY-MM-DD" and a time of day "HH:MM" (24-hour), both in the group's time zone, America/Los_Angeles; createdAt, updatedAt and other timestamps are ISO 8601 in UTC.
  • Pictures: each site's image.url is an absolute address on the server the request went to, such as http://localhost:4000/images/sites/pelican-point.jpg (1200×675, with its own alt text).

Lists and pagination

Lists (GET /api/events, GET /api/volunteers) answer with a plain JSON array of one page and put the page numbers in response headers. They take page (a whole number from 1) and perPage (1 to 50, default 10); anything else answers 400 with fieldErrors.page or fieldErrors.perPage. A page past the end is an empty array. Lesson 4.1 reads the headers; Lesson 6.2 builds page links from them.

CORS

The HQ (localhost:5173) and the API (localhost:4000) are different origins, so the browser only lets the HQ read an answer the API allows. shoreline-api allows any http://localhost:…, http://127.0.0.1:… or http://[::1]:… page: it echoes the page's origin in Access-Control-Allow-Origin (with Vary: Origin) and lists X-Total-Count, X-Total-Pages, Link, Location in Access-Control-Expose-Headers, which is why response.headers.get('X-Total-Count') works in the browser (Lesson 4.1). Preflight OPTIONS requests answer 204 and allow Authorization and Content-Type headers with every method. Any other site (a deployed HQ, say) needs --cors=https://…; without it the browser console shows a CORS error even though curl gets the answer. Lesson 10.2.

Trying it with curl

The browser can open any GET address. For the rest, curl works in a macOS or Linux terminal and Git Bash (in PowerShell type curl.exe, and quote the JSON differently). -i shows the headers.

curl "http://localhost:4000/api/events?perPage=2"
curl -i "http://localhost:4000/api/events?status=scheduled&when=upcoming"
curl -H "Authorization: Bearer dev-organizer" http://localhost:4000/api/events/e17/signups
curl -X POST http://localhost:4000/api/auth/sign-in -H "Content-Type: application/json" -d '{"email":"maya.okafor@example.com","password":"shoreline-demo"}'
curl -X POST http://localhost:4000/api/_reset

Photos

POST /api/photos (signed in) takes a JPEG, PNG or WebP of up to 5 MB, either as multipart/form-data with the file in a field named photo (what FormData sends; let the browser write the Content-Type), or as the raw body with the image's own Content-Type. It answers 201 with a Photo ({ id, url, contentType, bytes, uploadedBy, createdAt }); send its id in photoIds. Lesson 8.2.

Debris logs (the phone app)

POST /api/events/:id/logs takes { clientId, items, bags, weightKg, recordedAt, note?, photoIds? } from a volunteer with a spot (organizers too). clientId (8 to 64 characters) is made on the device: sending the same one again answers 200 with the log already saved instead of a duplicate, so an upload retried after a lost connection is safe. A new log answers 201; a cleanup in the future answers 409 This cleanup has not happened yet. GET /api/events/:id/logs lists them (organizers: all; volunteers: their own). The HQ does not use logs; the React Native course does.

🔌 How the HQ Calls It

Every request in Shoreline Crew HQ goes through one private request() function in src/api/client.ts: it builds the address from VITE_API_URL (in .env.local, copied from .env.example: VITE_API_URL=http://localhost:4000, Lesson 2.4), adds the session's token, and turns an error status into an ApiError. Restart npm run dev after changing .env.local.

/** Send a request to a path under /api, signed in if there is a session. Throws ApiError on an error status. */
async function request(path: string, init: RequestInit = {}): Promise<Response> {
  const headers = new Headers(init.headers)
  const session = readSession()
  if (session !== null) {
    headers.set('Authorization', `Bearer ${session.token}`)
  }
  const response = await fetch(`${apiBaseUrl()}/api${path}`, { ...init, headers })
  if (!response.ok) {
    if (response.status === 401 && session !== null) {
      // The API no longer knows this sign-in (it restarted, or the session ended): forget it here too
      saveSession(null)
    }
    // ...
  }
  return response
}

🧪 In Tests (MSW)

msw/handlers.ts runs the API's own code (core/api.ts, a web-standard Request in and Response out) inside Mock Service Worker 3, so tests get the same data, rules, errors and headers with no server running. createHandlers({ today, baseUrl }) returns { handlers, api }: the handlers for MSW and the API itself, whose api.reset() restores the sample data. The HQ copies core/ and msw/ into src/mocks/ unchanged and sets up the server in src/test/server.ts (Lesson 9.2):

// The mock API for tests: shoreline-api's own code answers the app's requests inside the test run
import { setupServer } from 'msw/node'
import { createHandlers } from '../mocks/msw/handlers.ts'

// The same address the app sends its requests to (vite.config.ts sets it for tests)
export const API_URL = import.meta.env.VITE_API_URL

// api = the API's code with its sample data; handlers = MSW's way in to it
export const { handlers, api } = createHandlers({ baseUrl: API_URL })
export const server = setupServer(...handlers)

The setup file starts it with server.listen({ onUnhandledFrame: 'error' }) (MSW 3; onUnhandledRequest is gone) and calls api.reset() before each test. To make one answer fail in one test, add an override with server.use(http.get(`${API_URL}/api/events`, …)).

🌐 Demo Mode

A deployed HQ cannot reach the API on your computer. The demo build (npm run build:demo, Lesson 10.2) solves this without a server: MSW's service worker answers every /api/… request on the site's own address with the same handlers the tests use, so the deployed site has the full sample data, sign-in and all. Each browser tab gets its own copy, which starts over on reload.

export async function startDemoApi() {
  // The demo answers on the site's own address, wherever it is deployed
  const { handlers } = createHandlers({ baseUrl: window.location.origin })
  const worker = setupWorker(...handlers)
  await worker.start({
    // Everything that is not /api (the page, its files, the site pictures) goes to the host as usual
    onUnhandledFrame: 'bypass',
    // No "[MSW] …" line in the console for every request
    quiet: true,
  })
}
// The demo build (npm run build:demo) starts its own API in the browser before the first request
if (import.meta.env.MODE === 'demo') {
  const { startDemoApi } = await import('./mocks/browser.ts')
  await startDemoApi()
}

The pieces: msw({ mode: 'worker-only' }) in vite.config.ts only in demo mode (it adds mockServiceWorker.js to the build), src/mocks/browser.ts above, main.tsx waiting for the worker before the first render, and client.ts using window.location.origin instead of VITE_API_URL in demo mode. The normal build still talks to a real shoreline-api. To serve a real API to a deployed site instead, run it on a Node.js host with --cors=https://your-site.netlify.app (Lesson 10.2).
