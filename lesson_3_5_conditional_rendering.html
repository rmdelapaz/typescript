🔀 Conditional Rendering Patterns

Not all components should render the same way all the time. Sometimes you show a login form, sometimes a user profile. Sometimes you display data, sometimes a loading spinner. Sometimes you show everything, sometimes just an error message. Conditional rendering is how you make your UI adapt to different states, data, and user actions. React gives you multiple ways to conditionally render content, and choosing the right pattern makes your code cleaner and easier to understand. Let's master all the patterns! 🚀

By the end of this lesson, you will be able to:

  • Use if/else statements for conditional rendering
  • Apply ternary operators in JSX
  • Use logical && and || operators effectively
  • Implement switch statements for multiple conditions
  • Use early returns and guard clauses
  • Choose the right pattern for each scenario
  • Handle loading, error, and empty states
  • Avoid common conditional rendering pitfalls
  • Write clean, readable conditional JSX

🎯 Conditional Rendering Basics

Think of a React component as a smart picture frame: instead of always showing the same photo, it looks at what is going on right now and decides which picture to slot in. Logged in? Show the dashboard. Still fetching? Show a spinner. Nothing to display? Show a friendly empty message. That decision-making is conditional rendering, and the good news is it works exactly like the conditions you already know from plain JavaScript — if, the ternary ?:, &&, ||, switch. You are not learning new React magic here; you are learning where each familiar JavaScript tool fits best inside JSX.

📖 Definition

Conditional Rendering: deciding what a component returns — a different element, a different component, or nothing at all — based on state, props, or any other data available at render time.

Why Conditional Rendering?

Real-World Examples

Scenario Condition What to Render
User Authentication Is user logged in? Dashboard vs Login Form
Data Loading Is data loaded? Content vs Spinner
Permissions Is user admin? Admin Panel vs Normal View
Form Validation Is form valid? Submit Button vs Error Message
Feature Toggle Is feature enabled? New Feature vs Old Feature
Empty State Is list empty? Empty Message vs List Items

The Basic Pattern

At its simplest, conditional rendering is one if that changes what the function returns. A React function component is just a function that returns JSX, so a plain if works exactly as you would expect:

Simple Example

function Greeting() {
    const [isLoggedIn, setIsLoggedIn] = useState(false);

    // The condition decides which JSX we return
    if (isLoggedIn) {
        return <h1>Welcome back!</h1>;
    }
    return <h1>Please sign in</h1>;
}

💡 A note on typing components in 2026 (React 19)

You will see two common styles for typing a component. The classic one uses React.FC<Props>. The style the React team and most modern codebases now favour is to type the props argument directly and let TypeScript infer the return type:

// Modern, recommended style — plain function, props typed inline
function Greeting({ isLoggedIn }: { isLoggedIn: boolean }) {
    return isLoggedIn ? <h1>Welcome back!</h1> : <h1>Please sign in</h1>;
}

Both compile to the same thing. This lesson uses React.FC in several places because you will meet it constantly in existing code, but the inline-props style is perfectly good — pick one and stay consistent. Either way, always use function components; class components are legacy.

🔀 If/Else Statements

The most straightforward way to render conditionally is the humble if/else. Because a component is a function, you can write ordinary statement-level logic before the return — run calculations, check several conditions, log things, set breakpoints. This is the pattern to reach for whenever the logic is more than a one-liner, or when the two branches return completely different components. It reads top-to-bottom like a checklist, which is exactly how our brains debug.

Basic If/Else

Component-Level Conditionals

interface GreetingProps {
    isLoggedIn: boolean;
}

const Greeting: React.FC<GreetingProps> = ({ isLoggedIn }) => {
    if (isLoggedIn) {
        return <h1>Welcome back!</h1>;
    }
    
    return <h1>Please log in</h1>;
};

// Or with explicit else:
const Greeting: React.FC<GreetingProps> = ({ isLoggedIn }) => {
    if (isLoggedIn) {
        return <h1>Welcome back!</h1>;
    } else {
        return <h1>Please log in</h1>;
    }
};

Element Variables

Store JSX in Variables

const LoginControl: React.FC = () => {
    const [isLoggedIn, setIsLoggedIn] = useState(false);
    
    let button;
    
    if (isLoggedIn) {
        button = <button onClick={() => setIsLoggedIn(false)}>Logout</button>;
    } else {
        button = <button onClick={() => setIsLoggedIn(true)}>Login</button>;
    }
    
    return (
        <div>
            <h1>{isLoggedIn ? 'Welcome!' : 'Please sign in'}</h1>
            {button}
        </div>
    );
};

If/Else If/Else Chain (Rendering by State)

A huge amount of real UI boils down to "which of these mutually-exclusive states am I in?" — idle, loading, success, or error. Model that state as a discriminated union (a union of string literals), and TypeScript keeps you honest: it narrows the type inside each branch and warns you if a state has no home.

Multiple Conditions

type Status = 'idle' | 'loading' | 'success' | 'error';

interface DataDisplayProps {
    status: Status;
    data?: string[];        // real shape — never `any`
    error?: string;
}

const DataDisplay: React.FC<DataDisplayProps> = ({ status, data, error }) => {
    if (status === 'loading') {
        return <div>Loading…</div>;
    } else if (status === 'error') {
        return <div>Error: {error ?? 'Something went wrong'}</div>;
    } else if (status === 'success') {
        // Guard against rendering undefined: default to an empty array
        return <ul>{(data ?? []).map((item) => <li key={item}>{item}</li>)}</ul>;
    } else {
        return <div>No data yet</div>;
    }
};

⚠️ Never reach for any here

The old version of this example typed data as any, which silently switches off type checking for everything you do with it. In 2026 TypeScript, prefer the real shape (string[], a proper interface, etc.). If you genuinely do not know the shape yet, use unknown and narrow it — unknown forces you to check before you use it, whereas any lets bugs walk right through.

When to Use If/Else

Use Case Example
Complex conditions Multiple checks needed
Early returns Return different components entirely
Element variables Calculate JSX before return
Readable logic When inline operators would be messy

✅ Pro Tip

If/else is great when:

  • You're returning completely different components
  • The condition logic is complex
  • You need to do calculations before rendering

❓ Ternary Operator

The ternary operator — condition ? valueIfTrue : valueIfFalse — is the workhorse of inline conditional rendering. Because it is an expression (it evaluates to a value) rather than a statement, you can drop it straight into the middle of JSX where an if would be illegal. Reach for it when you have a clean either/or choice and both outcomes are short. Think of it as the "this or that" switch you embed right where the content goes.

Basic Ternary

Inline Conditionals

const Message: React.FC<{ isOnline: boolean }> = ({ isOnline }) => {
    return (
        <div>
            {isOnline ? (
                <span style={{ color: 'green' }}>● Online</span>
            ) : (
                <span style={{ color: 'gray' }}>○ Offline</span>
            )}
        </div>
    );
};

// Or simpler:
const Status: React.FC<{ isActive: boolean }> = ({ isActive }) => (
    <span>{isActive ? 'Active' : 'Inactive'}</span>
);

Ternary with Components

Rendering Different Components

const Dashboard: React.FC = () => {
    const [isLoggedIn, setIsLoggedIn] = useState(false);
    
    return (
        <div>
            {isLoggedIn ? (
                <UserDashboard />
            ) : (
                <LoginForm />
            )}
        </div>
    );
};

// With props:
const Greeting: React.FC<{ user: User | null }> = ({ user }) => (
    <div>
        {user ? (
            <h1>Hello, {user.name}!</h1>
        ) : (
            <h1>Hello, Guest!</h1>
        )}
    </div>
);

Nested Ternaries

⚠️ Be Careful with Nested Ternaries

// ❌ Hard to read
const Status = ({ status }) => (
    <div>
        {status === 'loading' ? (
            <Spinner />
        ) : status === 'error' ? (
            <Error />
        ) : status === 'empty' ? (
            <Empty />
        ) : (
            <Content />
        )}
    </div>
);

// ✅ Better: Use if/else or switch
const Status = ({ status }) => {
    if (status === 'loading') return <Spinner />;
    if (status === 'error') return <Error />;
    if (status === 'empty') return <Empty />;
    return <Content />;
};

Ternary for Class Names and Styles

Conditional Styling

const Button: React.FC<{ isPrimary: boolean }> = ({ isPrimary }) => (
    <button
        className={isPrimary ? 'btn-primary' : 'btn-secondary'}
        style={{
            backgroundColor: isPrimary ? '#667eea' : '#f5f5f5',
            color: isPrimary ? 'white' : '#333'
        }}
    >
        Click me
    </button>
);

// Multiple conditional classes
const Card: React.FC<{ isActive: boolean; isHovered: boolean }> = ({ 
    isActive, 
    isHovered 
}) => (
    <div
        className={`card ${isActive ? 'active' : ''} ${isHovered ? 'hovered' : ''}`}
    >
        Content
    </div>
);

➕ Logical && Operator

Reach for && when you want to show something only if a condition is true, with no "else" branch — a badge, an alert, an extra section. It reads almost like English: "condition and then this element." The trick is understanding why it works, because that same mechanism hides a famous footgun with the number 0.

Basic && Usage

Render or Nothing

const Notification: React.FC = () => {
    const [hasNewMessages, setHasNewMessages] = useState(true);
    const [messageCount, setMessageCount] = useState(5);
    
    return (
        <div>
            <h1>Inbox</h1>
            
            {/* Only show if condition is true */}
            {hasNewMessages && (
                <div className="alert">
                    You have new messages!
                </div>
            )}
            
            {/* Show message count if greater than 0 */}
            {messageCount > 0 && (
                <p>{messageCount} unread messages</p>
            )}
        </div>
    );
};

How && Works in JSX

Understanding the Logic

// In JavaScript:
true && 'Hello'    // Returns 'Hello'
false && 'Hello'   // Returns false

// In JSX:
{true && <div>Hello</div>}    // Renders <div>Hello</div>
{false && <div>Hello</div>}   // Renders nothing

// React SKIPS: false, null, undefined, and true (renders nothing)
// React RENDERS: strings and numbers — including 0 and NaN!
// That last line is the whole reason for the gotcha below.

Here is the mental model: a && b does not return true/false. It returns the first operand if it is falsy, otherwise the second operand. So 0 && <p/> evaluates to 0 — and because React happily renders numbers, that 0 shows up on the page. The fix is to give && a real boolean on the left: write count > 0 && …, or wrap the value with Boolean(count) && …, or just use a ternary.

Common && Patterns

Practical Examples

const UserProfile: React.FC<{ user: User | null }> = ({ user }) => (
    <div>
        {/* Show only if user exists */}
        {user && (
            <div>
                <h2>{user.name}</h2>
                <p>{user.email}</p>
            </div>
        )}
        
        {/* Show only if user is admin */}
        {user && user.role === 'admin' && (
            <button>Admin Panel</button>
        )}
        
        {/* Show only if user has premium */}
        {user?.isPremium && (
            <div className="premium-badge">⭐ Premium</div>
        )}
    </div>
);

const TodoList: React.FC<{ todos: Todo[] }> = ({ todos }) => (
    <div>
        {/* Show only if there are todos */}
        {todos.length > 0 && (
            <ul>
                {todos.map(todo => (
                    <li key={todo.id}>{todo.text}</li>
                ))}
            </ul>
        )}
        
        {/* Show only if list is empty */}
        {todos.length === 0 && (
            <p>No todos yet!</p>
        )}
    </div>
);

⚠️ Common Pitfall: Falsy Values

Watch Out for 0 and ''

const Counter: React.FC = () => {
    const [count, setCount] = useState(0);
    
    // ❌ Problem: When count is 0, it renders "0" on screen!
    return (
        <div>
            {count && <p>Count: {count}</p>}
        </div>
    );
    // When count = 0, React renders the 0!
    
    // ✅ Solution: Explicit comparison
    return (
        <div>
            {count > 0 && <p>Count: {count}</p>}
        </div>
    );
};

// Another example:
const Items: React.FC<{ items: string[] }> = ({ items }) => (
    <div>
        {/* ❌ Shows "0" when empty */}
        {items.length && <p>{items.length} items</p>}
        
        {/* ✅ Correct */}
        {items.length > 0 && <p>{items.length} items</p>}
    </div>
);

🔄 Logical || Operator (OR)

The logical OR operator (||) is useful for providing fallback values or default content when something is null, undefined, or falsy.

Basic Pattern

Providing Fallbacks

interface UserProps {
    user?: {
        name?: string;
        avatar?: string;
    };
}

const UserDisplay: React.FC<UserProps> = ({ user }) => (
    <div className="user-card">
        {/* Show user name or fallback */}
        <h2>{user?.name || 'Anonymous User'}</h2>
        
        {/* Show avatar or default */}
        <img 
            src={user?.avatar || '/default-avatar.png'} 
            alt="User avatar"
        />
    </div>
);

// Real-world example: Settings with defaults
interface SettingsProps {
    theme?: 'light' | 'dark';
    language?: string;
    fontSize?: number;
}

const Settings: React.FC<SettingsProps> = ({ 
    theme, 
    language, 
    fontSize 
}) => (
    <div className={`theme-${theme || 'light'}`}>
        <p>Language: {language || 'English'}</p>
        <p>Font Size: {fontSize || 16}px</p>
    </div>
);

Nullish Coalescing (??)

💡 Modern Alternative

The nullish coalescing operator (??) is better than || when you want to treat 0, false, and empty strings as valid values:

const Counter: React.FC = () => {
    const [count, setCount] = useState(0);
    
    // ❌ Problem with ||: 0 is considered falsy
    return <p>Count: {count || 'No count'}</p>;
    // Renders: "Count: No count" when count is 0!
    
    // ✅ Solution with ??: only null/undefined are replaced
    return <p>Count: {count ?? 'No count'}</p>;
    // Renders: "Count: 0" correctly!
};

// More examples:
const Examples: React.FC = () => {
    const emptyString = '';
    const zero = 0;
    const falseValue = false;
    
    return (
        <div>
            {/* With || */}
            <p>{emptyString || 'default'}</p>  {/* Shows: default */}
            <p>{zero || 'default'}</p>         {/* Shows: default */}
            <p>{falseValue || 'default'}</p>   {/* Shows: default */}
            
            {/* With ?? */}
            <p>{emptyString ?? 'default'}</p> {/* Shows: (empty) */}
            <p>{zero ?? 'default'}</p>        {/* Shows: 0 */}
            <p>{falseValue ?? 'default'}</p>  {/* Shows: false */}
        </div>
    );
};

Chaining || for Multiple Fallbacks

Multiple Default Options

interface DataDisplayProps {
    primaryData?: string;
    secondaryData?: string;
    tertiaryData?: string;
}

const DataDisplay: React.FC<DataDisplayProps> = ({
    primaryData,
    secondaryData,
    tertiaryData
}) => (
    <div>
        {/* Try multiple sources in order */}
        <p>{primaryData || secondaryData || tertiaryData || 'No data available'}</p>
    </div>
);

// Example with user profiles
interface ProfileProps {
    displayName?: string;
    username?: string;
    email?: string;
}

const ProfileHeader: React.FC<ProfileProps> = ({
    displayName,
    username,
    email
}) => (
    <div className="profile-header">
        <h1>{displayName || username || email?.split('@')[0] || 'User'}</h1>
    </div>
);

✅ Best Practice

Use || for default strings/objects, but use ?? when 0, false, or empty string are valid values you want to display.

🔀 Switch Statements

When the thing you are branching on is a single value with several possible cases — an order status, a user role, an alert type — a switch reads more clearly than a long if/else if ladder. Even better, when you pair a switch with a TypeScript discriminated union, the compiler can prove you handled every case (more on that at the end of the lesson). And for the very common "same layout, different data" situation, an object map is often cleaner still.

Basic Switch Pattern

Status-Based Rendering

type OrderStatus = 'pending' | 'processing' | 'shipped' | 'delivered' | 'cancelled';

interface OrderProps {
    status: OrderStatus;
    orderId: string;
}

const OrderStatusDisplay: React.FC<OrderProps> = ({ status, orderId }) => {
    // Helper function using switch
    const getStatusDisplay = () => {
        switch (status) {
            case 'pending':
                return (
                    <div className="status status-pending">
                        <h3>⏳ Order Pending</h3>
                        <p>Waiting for confirmation...</p>
                    </div>
                );
            case 'processing':
                return (
                    <div className="status status-processing">
                        <h3>📦 Processing Order</h3>
                        <p>Your order is being prepared.</p>
                    </div>
                );
            case 'shipped':
                return (
                    <div className="status status-shipped">
                        <h3>🚚 Order Shipped</h3>
                        <p>Your package is on its way!</p>
                    </div>
                );
            case 'delivered':
                return (
                    <div className="status status-delivered">
                        <h3>✅ Delivered</h3>
                        <p>Order #{orderId} has been delivered.</p>
                    </div>
                );
            case 'cancelled':
                return (
                    <div className="status status-cancelled">
                        <h3>❌ Order Cancelled</h3>
                        <p>This order has been cancelled.</p>
                    </div>
                );
            default:
                return <p>Unknown status</p>;
        }
    };
    
    return (
        <div className="order-status">
            {getStatusDisplay()}
        </div>
    );
};

Object Mapping Pattern (Better!)

💡 More Elegant Approach

Instead of switch statements, you can use object mapping for cleaner, more maintainable code:

type AlertType = 'info' | 'success' | 'warning' | 'error';

interface AlertProps {
    type: AlertType;
    message: string;
}

const Alert: React.FC<AlertProps> = ({ type, message }) => {
    // Map types to configurations
    const alertConfig = {
        info: {
            icon: 'ℹ️',
            className: 'alert-info',
            title: 'Information'
        },
        success: {
            icon: '✅',
            className: 'alert-success',
            title: 'Success'
        },
        warning: {
            icon: '⚠️',
            className: 'alert-warning',
            title: 'Warning'
        },
        error: {
            icon: '❌',
            className: 'alert-error',
            title: 'Error'
        }
    };
    
    const config = alertConfig[type];  // fully type-safe: `type` is one of four keys

    return (
        <div className={`alert ${config.className}`}>
            <span className="alert-icon">{config.icon}</span>
            <div className="alert-content">
                <h4>{config.title}</h4>
                <p>{message}</p>
            </div>
        </div>
    );
};

Want the compiler to guarantee your map covers every variant? Type it as a Record keyed by the union: const alertConfig: Record<AlertType, AlertConfig> = { … }. Now if you add a fifth AlertType and forget to add its entry, TypeScript flags the object immediately — the same safety net a never exhaustiveness check gives a switch.

Pattern Best For Example

↩️ Early Returns

Early returns — also called guard clauses — are the antidote to the "pyramid of doom" you get from deeply nested ternaries. The idea is simple: handle every unusual or not-ready case first, returning immediately for each, so that by the time you reach the bottom of the function you are guaranteed to be on the "happy path" with valid data. Think of a bouncer at a club checking IDs one at a time: anyone who fails is turned away at the door, and everyone still inside is known to be good. This pattern pairs beautifully with TypeScript, because each guard narrows the types — after if (!user) return …, TypeScript knows user is non-null for the rest of the function.

Basic Early Return Pattern

Loading and Error States

interface DataDisplayProps {
    data: string[] | null;
    isLoading: boolean;
    error: string | null;
}

const DataDisplay: React.FC<DataDisplayProps> = ({ data, isLoading, error }) => {
    // Early return for loading
    if (isLoading) {
        return (
            <div className="loading">
                <p>⏳ Loading data...</p>
            </div>
        );
    }
    
    // Early return for error
    if (error) {
        return (
            <div className="error">
                <h3>❌ Error</h3>
                <p>{error}</p>
            </div>
        );
    }
    
    // Early return for empty data
    if (!data || data.length === 0) {
        return (
            <div className="empty">
                <p>📭 No data available</p>
            </div>
        );
    }
    
    // Main render - we know we have valid data!
    return (
        <div className="data-display">
            <h2>Data List</h2>
            <ul>
                {data.map((item, index) => (
                    <li key={index}>{item}</li>
                ))}
            </ul>
        </div>
    );
};

🎨 Common Rendering Patterns

Let's explore real-world patterns you'll use constantly in React development.

The Guard-Clause Order That Almost Never Changes

Nearly every data-driven component asks the same four questions, in the same order. Check the "not ready" states first (loading, then error, then empty), and only fall through to the real content once you have proven the data is present and non-empty. That ordering is what lets the final return assume it is working with good data.

✨ Best Practices

✅ Do's

  • Use early returns for edge cases and error states
  • Keep conditions simple - extract complex logic into functions
  • Use explicit comparisons (> 0) instead of truthy checks when appropriate
  • Prefer ?? over || when 0, false, or '' are valid values
  • Use object mapping instead of switch for configuration-based rendering
  • Extract conditional logic into well-named functions for readability
  • Handle all states: loading, error, empty, and success
  • Use TypeScript to ensure exhaustive checks with union types

❌ Don'ts

  • Don't nest ternaries more than 2 levels deep - use early returns instead
  • Don't use && with numbers or counts without explicit comparison
  • Don't forget null/undefined checks before accessing properties
  • Don't render "true" or "false" accidentally - wrap booleans properly
  • Don't over-complicate - sometimes a simple if/else is best
  • Don't ignore TypeScript warnings about potential nulls
  • Don't render different component types in the same condition chain (breaks React's reconciliation)

Readability Guidelines

// ❌ Hard to read
const Component = ({ a, b, c }) => (
    <div>
        {a && b ? c ? <X /> : <Y /> : a || b ? <Z /> : <W />}
    </div>
);

// ✅ Clear and maintainable
const Component = ({ a, b, c }) => {
    if (!a && !b) return <W />;
    if (a || b) {
        if (!a || !b) return <Z />;
        return c ? <X /> : <Y />;
    }
};

// ✅ Even better with named helpers
const Component = ({ a, b, c }) => {
    const hasBasicRequirements = a && b;
    const hasAdvancedFeatures = hasBasicRequirements && c;
    
    if (!a && !b) return <W />;
    if (!hasBasicRequirements) return <Z />;
    return hasAdvancedFeatures ? <X /> : <Y />;
};

💡 Conditional Rendering and Re-renders

// ❌ Creates new functions on every render

📚 Summary

What You Learned

Congratulations! You now know all the essential conditional rendering patterns in React:

Pattern Syntax Best For
If/Else if (condition) return <A />; else return <B />; Simple binary conditions outside JSX
Ternary {condition ? <A /> : <B />} Inline either/or rendering in JSX
&& Operator {condition && <Component />} Show/hide single elements
|| Operator {value || 'default'} Fallback values
?? Operator {value ?? 'default'} Fallback when null/undefined
Switch switch(value) { case 'a': ... } Multiple distinct conditions
Early Return if (error) return <Error />; Edge cases and guard clauses
Object Map config[type] Configuration-based rendering

🎯 Key Takeaways

  • Choose the right tool: Each pattern has its best use case
  • Readability matters: Use early returns to avoid deep nesting
  • Handle all states: Loading, error, empty, and success
  • Be explicit: Use > 0 instead of truthy checks for numbers
  • Use TypeScript: Exhaustive checking prevents missing cases
  • Think about UX: Every state should have appropriate UI feedback
