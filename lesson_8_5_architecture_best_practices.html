🎯 Principles of Good Architecture

Think of architecture like the framing of a house. 🏠 Nobody walks into a finished home and admires the studs behind the drywall — but get the framing wrong and every room you add later leans a little more, until one day the whole thing is too fragile to change. Software architecture is the framing behind your features: invisible when it's right, painfully obvious when it's wrong. Before we reach for specific patterns, let's ground ourselves in the principles that hold everything up. These apply whether you're building a weekend side project or an app that a hundred engineers touch every day.

The Core Principles

📖 What "Good" Actually Means

Good architecture is about making your codebase easy to understand, modify, and extend. It prioritizes maintainability over cleverness, clarity over brevity, and consistency over individual preferences. The real metric is cognitive load: how much you have to hold in your head to safely make a change. Every principle below is really just a different way of shrinking that mental burden — for the teammate reviewing your PR, and for the future version of you who has completely forgotten how this code works.

1. Separation of Concerns

Each part of your application should have a single, well-defined responsibility. Picture a restaurant kitchen: the person plating dessert isn't also taking orders and washing dishes. Each station does one job well, and the meal comes together because responsibilities are cleanly divided. React code works the same way — when components, hooks, and services each focus on one thing, they become dramatically easier to understand, test, and reuse. The example below shows the same feature written two ways: one where a single component tries to be the whole kitchen, and one where the work is split into stations.

// ❌ BAD - Component doing too much

  const [user, setUser] = useState(null);

    fetch('/api/user')

        setUser(data);

      });
  }, []);
  
  const saveUser = (data) => {
    fetch('/api/user', {

          {/* lots of form fields and UI logic */}
        </form>

  );
}

2. DRY (Don't Repeat Yourself)

Duplicated code multiplies maintenance work and increases the chance of bugs. Extract common logic into reusable functions, hooks, and components.

// ❌ BAD - Repeated logic
function UsersList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  
  useEffect(() => {
    setLoading(true);
    fetch('/api/users')
      .then(res => res.json())
      .then(data => {
        setUsers(data);
        setLoading(false);
      })
      .catch(err => {
        setError(err);
        setLoading(false);
      });
  }, []);
  
  // ... component JSX
}

function PostsList() {
  const [posts, setPosts] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  
  useEffect(() => {
    setLoading(true);
    fetch('/api/posts')
      .then(res => res.json())
      .then(data => {
        setPosts(data);
        setLoading(false);
      })
      .catch(err => {
        setError(err);
        setLoading(false);
      });
  }, []);
  
  // ... component JSX
}

// ✅ GOOD - Reusable hook
function useFetch<T>(url: string) {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<Error | null>(null);
  
  useEffect(() => {
    let cancelled = false;
    
    setLoading(true);
    fetch(url)
      .then(res => res.json())
      .then(data => {
        if (!cancelled) {
          setData(data);
          setLoading(false);
        }
      })
      .catch(err => {
        if (!cancelled) {
          setError(err);
          setLoading(false);
        }
      });
    
    return () => { cancelled = true; };
  }, [url]);
  
  return { data, loading, error };
}

// Now both components are simple
function UsersList() {
  const { data: users, loading, error } = useFetch<User[]>('/api/users');
  // ... component JSX
}

function PostsList() {
  const { data: posts, loading, error } = useFetch<Post[]>('/api/posts');
  // ... component JSX
}

3. KISS (Keep It Simple, Stupid)

Simple solutions are easier to understand, test, and maintain. Avoid over-engineering and premature optimization.

✅ Signs of Good Simplicity

  • A new team member can understand a component in under 5 minutes
  • Testing feels natural, not like fighting the code
  • Naming clearly describes what something does
  • You don't need comments to explain "why" (but you might need them for "what")
  • Changes in one area rarely require changes in unrelated areas

4. Single Responsibility Principle

Each component, function, or module should have one reason to change. This makes code predictable and reduces the ripple effect of modifications.

// ❌ BAD - Component has multiple responsibilities
function UserDashboard() {
  return (
    <div>
      {/* Analytics tracking logic */}
      {/* User data fetching */}
      {/* Navigation rendering */}
      {/* User profile display */}
      {/* Settings management */}
      {/* Notifications handling */}
    </div>
  );
}

// ✅ GOOD - Each component has one responsibility
function UserDashboard() {
  useAnalytics('dashboard-view');

  return (
    <DashboardLayout>
      <UserHeader user={user} />
      <UserStats userId={user.id} />

      <QuickActions />
    </DashboardLayout>
  );
}

5. Composition Over Inheritance

React's component model encourages composition. Build complex UIs by combining simple, focused components rather than creating deep inheritance hierarchies.

// ✅ GOOD - Composition pattern
function Card({ children }: { children: React.ReactNode }) {
  return <div className="card">{children}</div>;
}

function CardHeader({ children }: { children: React.ReactNode }) {
  return <div className="card-header">{children}</div>;
}

function CardBody({ children }: { children: React.ReactNode }) {
  return <div className="card-body">{children}</div>;
}

// Compose them together
function UserCard({ user }: { user: User }) {
  return (
    <Card>
      <CardHeader>
        <h2>{user.name}</h2>
      </CardHeader>
      <CardBody>
        <p>{user.bio}</p>
      </CardBody>
    </Card>
  );
}

6. Separate Server State from Client State

This is the single most important architectural shift in modern React, and it's worth pausing on. For years we jammed everything into useState and Redux — form inputs, modal toggles, and the list of users fetched from the API — as if it were all the same kind of data. It isn't.

  • 🖥️ Client state is data your app owns and fully controls: is the sidebar open? what's typed in this input? which tab is active? It's synchronous, it lives only in the browser, and you are the source of truth.
  • 🌐 Server state is a borrowed copy of data that actually lives on a server: the user list, a blog post, the shopping cart. It's asynchronous, it can go stale the moment someone else changes it, and the server — not your app — is the source of truth.

Treating borrowed server data like owned client state is why so many older codebases drown in isLoading flags, manual cache invalidation, and "why is this list out of date?" bugs. The modern answer is to stop hand-rolling that machinery and let a dedicated server-state library handle caching, refetching, and staleness for you.

💡 The 2026 Default

Reach for TanStack Query (formerly React Query) or RTK Query for anything that comes from an API, and keep a lightweight client-state tool like Zustand (or plain useState/useReducer) for the genuinely local stuff. You covered these tools in Lessons 8.1–8.4 — this lesson is about wiring them together cleanly. The rule of thumb: if the data could change on the server without your app doing anything, it's server state.

7. Design for Testability

A good architecture test: if a component is hard to test, it's probably doing too much. This isn't just a nice-to-have — testability is a diagnostic. When you find yourself mocking six things just to render one component, that pain is the code telling you its concerns are tangled. Pull the data fetching into a hook you can test in isolation, keep the presentational component a pure function of its props, and suddenly both halves become trivial to test. We call these clean boundaries testing seams: the natural places where you can slot in a fake and verify one layer without dragging in the whole app.

💡 The Testing Principle

Difficulty testing is a signal, not an inconvenience. Before you write an elaborate mock, ask whether the component should be split so that the tricky part lives behind a seam — a hook, a service, or a prop — that you can swap out cleanly.

Architecture Anti-Patterns to Avoid

Anti-Pattern Problem Solution
God Components Components that do everything Break into smaller, focused components
Prop Drilling Passing props through many layers Use Context, state management, or composition
Mixed Concerns Business logic in components Extract to custom hooks or services
Tight Coupling Components depend on implementation details Use interfaces and dependency injection
Premature Abstraction Creating abstractions before needed Wait for the third use case

📁 Feature-Based Folder Structure

Here's a question that reveals a lot about a codebase: when you sit down to change the "users" feature, how many folders do you have to open? In a small app, organizing files by type — all components in one folder, all hooks in another, all services in a third — feels tidy. But as the app grows, that tidiness turns on you. A single feature ends up smeared across four or five folders, and every change becomes a scavenger hunt.

Think of it like organizing a kitchen. 🍳 You could put all the handles in one drawer, all the blades in another, all the electrical cords in a third — sorted perfectly by type. But when you want to make an omelette, you'd be running all over the kitchen. Instead, you keep the things you use together, together. A feature-based structure does exactly this: it colocates everything a feature needs — its components, hooks, service calls, and types — so you can understand and change a feature as one complete unit.

✅ Benefits of Feature-Based Structure

  • Scalability: Add new features without cluttering existing folders
  • Maintainability: All related code lives together
  • Team collaboration: Multiple devs can work on different features
  • Code ownership: Clear boundaries for feature teams
  • Easier refactoring: Feature can be moved or removed as a unit
  • Better imports: Feature's public API through index.ts

Feature Module Example

// features/users/index.ts - Public API
export { UserList } from './components/UserList';
export { UserCard } from './components/UserCard';
export { useUsers, useUser } from './hooks';
export type { User, UserFilters } from './types/user.types';

// Other files import from the feature's public API
import { UserList, useUsers, type User } from '@/features/users';

// NOT from internal paths
// ❌ DON'T: import { UserList } from '@/features/users/components/UserList/UserList';

That index.ts file is called a barrel — it re-exports a feature's public surface from one convenient place. Barrels are genuinely useful at the boundary of a feature: they let the rest of the app import from @/features/users without knowing or caring how the folder is laid out inside. That's real encapsulation, and it means you can rename or reorganize a feature's internals without breaking a single import elsewhere.

⚠️ Use Barrels Deliberately, Not Everywhere

Barrel files have a well-known dark side. A few caveats worth internalizing:

  • Circular imports: if two files in the same feature both import through the barrel, they can form an import cycle that throws a confusing "cannot access before initialization" error at runtime. Inside a feature, import from the sibling file directly; only outside code should go through the barrel.
  • Tree-shaking & build cost: a giant barrel that re-exports everything can pull far more into a bundle than you intended and slow down cold builds and test startup. Keep barrels thin — export the feature's public API, not every internal helper.
  • Don't nest barrels deeply: one barrel per feature boundary is plenty. Barrels that re-export other barrels that re-export other barrels are how you get mysterious circular dependencies.

Path Aliases: Killing the ../../../ Problem

You've probably noticed the @/ in those imports. That's a path alias, and it's the difference between a clean import { userService } from '@/features/users' and the dreaded import { userService } from '../../../features/users' that breaks the instant you move a file. You configure it in two places — TypeScript (for type-checking and editor navigation) and your bundler (for the actual build):

// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import path from 'node:path';

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src'),
    },
  },
});

💡 Why both files?

TypeScript's paths only teaches the compiler and your editor what @/ means — it does not rewrite imports in the output. The bundler (Vite here, or the equivalent in Next.js / your tooling) needs its own matching alias so the actual build can resolve the path. Keep the two in sync and "go to definition" works while your production bundle still finds the file.

⚠️ Avoid Premature Sharing

When creating a new component, start in the feature folder. Move it to shared/ only when you actually need it in a second place. The "Rule of Three" applies: extract to shared when you need it the third time.

🧩 Component Organization Patterns

Not all components are created equal. A component that owns a route and coordinates a whole page plays a very different role from a tiny reusable button — and treating them the same way is how folders turn to mush. Understanding these roles is like understanding the ranks in a kitchen brigade: the head chef (page) plans the meal, station chefs (feature containers) run their sections, and line cooks (presentational components) execute one dish well. When everyone knows their job, the kitchen runs smoothly.

💡 A Note on "Container vs Presentational" in 2026

The strict container/presentational split you'll see below was coined back when class components and Redux connect() ruled React. With Hooks, the modern version is subtler: instead of a wrapper component whose only job is to fetch data, you extract that logic into a custom hook and call it right inside the component that needs it. The principle — separate "how we get the data" from "how we show it" — is as vital as ever; the mechanism is now a hook, not a wrapper. We show the explicit container form here because it makes the roles crystal clear, but in real code a single component plus a well-named hook usually does the job.

1. Page Components (Route Components)

Top-level components that correspond to routes. They orchestrate feature components and manage page-level concerns.

import { PageHeader } from '@/shared/components';
import { MainLayout } from '@/layouts';

export function UsersPage() {
  return (
    <MainLayout>
      <PageHeader

      <UserList />
    </MainLayout>

// - Maps to a route

2. Container Components (Smart Components)

Manage state, data fetching, and business logic. They connect to stores, hooks, and APIs, then pass data down to presentational components.

// features/users/components/UserList/UserListContainer.tsx
import { useUsers } from '../../hooks/useUsers';
import { UserListView } from './UserListView';

export function UserListContainer() {
  const { 
    users, 
    isLoading, 
    error, 
    refetch 
  } = useUsers();
  
  const [filters, setFilters] = useState<UserFilters>({});
  
  const handleFilterChange = (newFilters: UserFilters) => {
    setFilters(newFilters);
  };
  
  const filteredUsers = useMemo(() => {
    return users?.filter(user => {
      // Filtering logic
      return true;
    });
  }, [users, filters]);
  
  if (isLoading) return <LoadingSpinner />;
  if (error) return <ErrorMessage error={error} onRetry={refetch} />;
  
  return (
    <UserListView
      users={filteredUsers}
      filters={filters}
      onFilterChange={handleFilterChange}
    />
  );
}

// Characteristics:
// - Manages state and side effects
// - Connects to data sources
// - Contains business logic
// - Handles loading and error states
// - Passes data to presentational components

3. Presentational Components (Dumb Components)

Focus purely on rendering UI. They receive data through props and notify parents of user interactions through callback props.

// features/users/components/UserList/UserListView.tsx
interface UserListViewProps {
  users: User[];
  filters: UserFilters;
  onFilterChange: (filters: UserFilters) => void;
}

export function UserListView({ 
  users, 
  filters, 
  onFilterChange 
}: UserListViewProps) {
  return (
    <div className="user-list">
      <UserFilters 
        filters={filters} 
        onChange={onFilterChange} 
      />
      
      <div className="user-grid">
        {users.map(user => (
          <UserCard key={user.id} user={user} />

🔀 Separation of Concerns

We touched on separation of concerns as a principle earlier; now let's make it concrete. The idea is to organize code into layers, each with a clear job, stacked so that each one only talks to the layer directly below it. Think of a restaurant again: the dining room (presentation) never walks into the walk-in freezer (data access) to grab ingredients — it sends an order through the kitchen (business logic), which decides what's needed and requests it from the pantry. Each layer trusts the next to do its job and doesn't reach past it. That discipline is what lets you swap out your entire API client later without touching a single button.

// hooks/useCart.ts
export function useCart() {
  const [cart, setCart] = useState<CartItem[]>([]);
  
  const addToCart = useCallback((product: Product) => {
    // Business rule: Max 10 items
    if (cart.length >= 10) {
      throw new Error('Cart is full. Maximum 10 items allowed.');
    }
    
    // Business logic: Calculate totals
    const tax = calculateTax(product.price);
    const total = product.price + tax;
    
    const cartItem: CartItem = {
      ...product,
      tax,
      total,
      addedAt: new Date()
    };
    
    setCart(prev => [...prev, cartItem]);
    return cartItem;
  }, [cart.length]);
  
  const removeFromCart = useCallback((itemId: string) => {
    setCart(prev => prev.filter(item => item.id !== itemId));
  }, []);
  
  const cartTotal = useMemo(() => {
    return cart.reduce((sum, item) => sum + item.total, 0);
  }, [cart]);
  
  const itemCount = cart.length;
  const isFull = itemCount >= 10;
  
  return {
    cart,
    cartTotal,
    itemCount,
    isFull,
    addToCart,
    removeFromCart
  };
}

// Utility function for business logic
function calculateTax(price: number): number {
  const TAX_RATE = 0.08;
  return price * TAX_RATE;
}

🪝 Custom Hooks for Business Logic

If separation of concerns is the goal, custom hooks are the workhorse that gets you there in React. A custom hook is just a function whose name starts with use and that calls other hooks — but that simple idea is quietly powerful. It lets you lift stateful logic out of a component and into a named, reusable, independently testable unit, leaving the component free to do what it's best at: describe what the UI looks like. Think of a hook as a self-contained appliance: your component plugs into useCart() the way you plug a toaster into the wall, without needing to know a thing about the wiring inside.

// hooks/useForm.ts
interface UseFormOptions<T> {
  initialValues: T;
  onSubmit: (values: T) => void | Promise<void>;
  validate?: (values: T) => Record<string, string>;
}

export function useForm<T extends Record<string, any>>({
  initialValues,
  onSubmit,
  validate
}: UseFormOptions<T>) {
  const [values, setValues] = useState<T>(initialValues);
  const [errors, setErrors] = useState<Record<string, string>>({});
  const [isSubmitting, setIsSubmitting] = useState(false);
  
  const handleChange = (name: keyof T, value: any) => {
    setValues(prev => ({ ...prev, [name]: value }));
    // Clear error when user starts typing
    if (errors[name as string]) {
      setErrors(prev => {
        const newErrors = { ...prev };
        delete newErrors[name as string];
        return newErrors;
      });
    }
  };
  
  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    
    // Validate
    if (validate) {
      const validationErrors = validate(values);
      if (Object.keys(validationErrors).length > 0) {
        setErrors(validationErrors);
        return;
      }
    }
    
    // Submit
    setIsSubmitting(true);
    try {
      await onSubmit(values);
      setValues(initialValues); // Reset form
    } catch (error) {
      // `error` is `unknown` in strict mode — narrow before reading .message
      const message = error instanceof Error ? error.message : 'Submission failed';
      setErrors({ submit: message });
    } finally {
      setIsSubmitting(false);
    }
  };
  
  const reset = () => {
    setValues(initialValues);
    setErrors({});
  };
  
  return {
    values,
    errors,
    isSubmitting,
    handleChange,
    handleSubmit,
    reset
  };
}

// hooks/useShoppingCart.ts
export function useShoppingCart() {
  const [items, setItems] = useState<CartItem[]>([]);
  
  const addItem = useCallback((product: Product, quantity = 1) => {
    setItems(prev => {
      const existing = prev.find(item => item.product.id === product.id);
      
      if (existing) {
        // Update quantity if item exists
        return prev.map(item =>
          item.product.id === product.id
            ? { ...item, quantity: item.quantity + quantity }
            : item
        );
      }
      
      // Add new item
      return [...prev, { product, quantity }];
    });
  }, []);
  
  const removeItem = useCallback((productId: string) => {
    setItems(prev => prev.filter(item => item.product.id !== productId));
  }, []);
  
  const updateQuantity = useCallback((productId: string, quantity: number) => {
    if (quantity <= 0) {
      removeItem(productId);
      return;
    }
    
    setItems(prev =>
      prev.map(item =>
        item.product.id === productId
          ? { ...item, quantity }
          : item
      )
    );
  }, [removeItem]);
  
  const clearCart = useCallback(() => {
    setItems([]);
  }, []);
  
  // Computed values
  const subtotal = useMemo(() => {
    return items.reduce((sum, item) => {
      return sum + (item.product.price * item.quantity);
    }, 0);
  }, [items]);
  
  const tax = useMemo(() => subtotal * 0.08, [subtotal]);
  const total = subtotal + tax;
  const itemCount = items.reduce((sum, item) => sum + item.quantity, 0);
  
  return {
    items,
    itemCount,
    subtotal,
    tax,
    total,
    addItem,
    removeItem,
    updateQuantity,
    clearCart
  };
}

// hooks/useDebounce.ts
export function useDebounce<T>(value: T, delay: number): T {
  const [debouncedValue, setDebouncedValue] = useState<T>(value);
  
  useEffect(() => {
    const handler = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);
    
    return () => clearTimeout(handler);
  }, [value, delay]);
  
  return debouncedValue;
}

// hooks/useLocalStorage.ts
export function useLocalStorage<T>(key: string, initialValue: T) {
  const [storedValue, setStoredValue] = useState<T>(() => {
    try {
      const item = window.localStorage.getItem(key);
      return item ? JSON.parse(item) : initialValue;
    } catch (error) {
      console.error(error);
      return initialValue;
    }
  });
  
  const setValue = (value: T | ((val: T) => T)) => {
    try {
      const valueToStore = value instanceof Function ? value(storedValue) : value;
      setStoredValue(valueToStore);
      window.localStorage.setItem(key, JSON.stringify(valueToStore));
    } catch (error) {
      console.error(error);
    }
  };
  
  return [storedValue, setValue] as const;
}

// hooks/useMediaQuery.ts
export function useMediaQuery(query: string): boolean {
  const [matches, setMatches] = useState(() => {
    return window.matchMedia(query).matches;
  });
  
  useEffect(() => {
    const mediaQuery = window.matchMedia(query);
    
    const handleChange = (e: MediaQueryListEvent) => {
      setMatches(e.matches);
    };
    
    mediaQuery.addEventListener('change', handleChange);
    return () => mediaQuery.removeEventListener('change', handleChange);
  }, [query]);
  
  return matches;
}

🔌 Service Layer Pattern

The service layer is a dedicated abstraction for all external communication — the one place in your app that actually knows the shape of your backend. Instead of scattering fetch('/api/users') calls across twenty components (each with its own slightly different error handling and its own chance to typo the URL), you funnel everything through a typed service. It's the embassy of your application: all diplomacy with the outside world happens here, in one language, with one set of rules.

💡 Typed inputs, typed outputs

The real payoff in TypeScript is that a service turns a raw HTTP call into a typed contract. userService.getById(id) returns a Promise<User>, not a Promise<any> — so the moment the backend's User shape and your type drift apart, the compiler flags it. Whether you use axios (shown here) or the native fetch API underneath is a detail; what matters architecturally is that callers never see it. They see typed methods, and the transport stays swappable.

🚨 Error Handling Architecture

Errors aren't edge cases — they're a first-class part of your app's behavior, and users judge you by how gracefully you handle them. The difference between "Something went wrong, please try again" with a working retry button and a blank white screen of death is entirely architectural. The trick is to decide, deliberately, which layer handles which kind of failure. A network hiccup is caught differently from a validation error, which is caught differently from a bug that crashes rendering. Think of it as a set of nets stacked under a trapeze artist: most falls are caught by the first net (the API layer), and the last net (an error boundary) exists only to make sure nobody ever hits the floor.

// lib/axios.ts
import { AppError, ValidationError, AuthenticationError } from '@/shared/errors';

apiClient.interceptors.response.use(
  (response) => response,
  (error) => {
    if (axios.isAxiosError(error)) {
      const status = error.response?.status;
      const data = error.response?.data;

      switch (status) {
        case 400:
          throw new ValidationError(
            data?.message || 'Validation failed',
            data?.errors
          );
        case 401:
          throw new AuthenticationError(data?.message);
        case 403:
          throw new AuthorizationError(data?.message);
        case 404:
          throw new NotFoundError(data?.resource || 'Resource');
        default:
          throw new AppError(
            data?.message || 'An error occurred',
            'UNKNOWN_ERROR',
            status || 500,
            data
          );
      }
    }

    throw error;
  }
);

3. Error Boundaries

// shared/components/ErrorBoundary.tsx
interface ErrorBoundaryProps {
  children: React.ReactNode;
  fallback?: React.ComponentType<{ error: Error; reset: () => void }>;
}

interface ErrorBoundaryState {
  hasError: boolean;
  error: Error | null;
}

export class ErrorBoundary extends React.Component<
  ErrorBoundaryProps,
  ErrorBoundaryState
> {
  constructor(props: ErrorBoundaryProps) {
    super(props);
    this.state = { hasError: false, error: null };
  }

  static getDerivedStateFromError(error: Error): ErrorBoundaryState {
    return { hasError: true, error };
  }

  componentDidCatch(error: Error, errorInfo: React.ErrorInfo) {
    console.error('Error caught by boundary:', error, errorInfo);
    // Log to error reporting service
    // errorReportingService.log(error, errorInfo);
  }

  reset = () => {
    this.setState({ hasError: false, error: null });
  };

  render() {
    if (this.state.hasError) {
      const FallbackComponent = this.props.fallback || DefaultErrorFallback;
      return <FallbackComponent error={this.state.error!} reset={this.reset} />;
    }

    return this.props.children;
  }
}

// Default error fallback
function DefaultErrorFallback({ error, reset }: { error: Error; reset: () => void }) {
  return (
    <div className="error-fallback">
      <h2>Something went wrong</h2>
      <p>{error.message}</p>
      <button onClick={reset}>Try again</button>
    </div>
  );
}

⚠️ Error boundaries are still class components

This is the one place the "function components only" rule bends: React — including React 19 — has no Hook equivalent of getDerivedStateFromError or componentDidCatch, so a boundary must be a class. In practice, almost nobody hand-writes one anymore. Install the tiny react-error-boundary package and you get a battle-tested <ErrorBoundary> plus a useErrorBoundary() Hook, so your own code stays function components end to end:

import { ErrorBoundary } from 'react-error-boundary';

function App() {
  return (
    <ErrorBoundary
      FallbackComponent={DefaultErrorFallback}
      onReset={() => queryClient.clear()}
    >
      <Routes />
    </ErrorBoundary>
  );
}

React 19 also improved error reporting: uncaught errors now route through onUncaughtError / onCaughtError options you can pass when creating the root, giving you a single place to log to your error-tracking service.

// Component with error handling
function UserProfile({ userId }: { userId: string }) {
  const { data, error, isLoading } = useUser(userId);
  const updateMutation = useUpdateUser();

  const handleUpdate = async (data: UpdateUserDto) => {
    try {
      await updateMutation.mutateAsync({ id: userId, data });
      toast.success('Profile updated successfully!');
    } catch (error) {
      if (error instanceof ValidationError) {
        // Show field-specific errors
        Object.entries(error.details || {}).forEach(([field, message]) => {
          toast.error(`${field}: ${message}`);
        });
      } else if (error instanceof AppError) {
        toast.error(error.message);
      } else {
        toast.error('An unexpected error occurred');
      }
    }
  };

  if (isLoading) return <Spinner />;
  
  if (error) {
    if (error instanceof NotFoundError) {
      return <NotFound message="User not found" />;
    }
    if (error instanceof AuthorizationError) {
      return <Unauthorized />;
    }
    return <ErrorMessage error={error} />;
  }

  return <UserForm user={data} onSubmit={handleUpdate} />;
}

💡 Error Handling Best Practices

  • Fail Fast: Catch errors as early as possible
  • Be Specific: Use custom error classes for different scenarios
  • User-Friendly: Show helpful messages, not technical jargon
  • Logging: Log errors to a service for debugging
  • Recovery: Provide ways to recover (retry button, reset)
  • Boundaries: Use Error Boundaries for unexpected errors

🧠 Knowledge Check Quiz

Question 1: Separation of Concerns

What are the three main layers in a well-architected React application, and what is each responsible for?

Show Answer

Answer:

  1. Presentation Layer (Components): Handles rendering UI and user interactions. Components should be focused on display logic only, not business rules or data fetching.
  2. Business Logic Layer (Custom Hooks): Contains application logic, calculations, validations, and state management. This is where you implement business rules and domain logic.
  3. Data Access Layer (Services): Handles all external communication like API calls, localStorage, or other data sources. Services provide a clean abstraction for data operations.

Question 2: Component Types

What's the difference between Container Components and Presentational Components? When should you use each?

Show Answer

Answer:

Container Components (Smart Components):

  • Manage state and side effects
  • Connect to data sources (hooks, context, stores)
  • Contain business logic
  • Pass data down to presentational components
  • Use when: You need to fetch data, manage state, or implement business logic

Presentational Components (Dumb Components):

  • Receive data only through props
  • Focus purely on UI rendering
  • No state or side effects
  • Highly reusable and testable
  • Use when: You need a reusable UI component that just displays data

Question 3: Folder Structure

Why is a feature-based folder structure better than organizing by file type (components/, hooks/, services/)? Give at least three reasons.

Show Answer

Answer:

  1. Scalability: As the app grows, feature folders don't become cluttered. Each feature is self-contained.
  2. Maintainability: All related code lives together, making it easier to understand and modify a feature.
  3. Team Collaboration: Different teams can work on different features without conflicts.
  4. Code Ownership: Clear boundaries make it obvious who owns what code.
  5. Easier Refactoring: Features can be moved, removed, or extracted as complete units.
  6. Better Imports: Features export a public API through index.ts, hiding implementation details.

Question 4: Service Layer

What should go in a service layer, and what should NOT go there?

Show Answer

Should go in services:

  • API calls (GET, POST, PUT, DELETE)
  • Request/response transformation (if needed)
  • HTTP configuration (headers, auth tokens)
  • Basic error throwing

Should NOT go in services:

  • Business logic (calculations, validations)
  • React state updates
  • Component dependencies
  • UI logic or rendering
  • Direct access to React hooks

Principle: Services should be pure data access - they communicate with external systems and return/send data, nothing more.

What are the different layers where you should handle errors in a React application? What type of errors should be handled at each layer?

Show Answer

Answer:

  1. API Layer (Axios Interceptors):

Question 8: Architecture Principles

Explain the SOLID principle that's most important in React: Single Responsibility Principle. How does it apply to React components?

Show Answer

Single Responsibility Principle:

Each component, function, or module should have one reason to change - one well-defined responsibility.

In React Components:

  • A component should do ONE thing (display user data, OR fetch it, OR validate it - not all three)
  • If you can't describe what a component does in one sentence, it's doing too much
  • Changes to business logic shouldn't require changes to UI components
  • Changes to API structure shouldn't require changes to components

Example:

  • ❌ BAD: UserProfile fetches data, validates form, handles submission, and renders UI
  • ✅ GOOD: UserProfile just orchestrates. Data fetching is in useUser hook, form logic in useForm, validation in validators, and UI in presentational components
