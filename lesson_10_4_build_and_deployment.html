🌟 Introduction to Production Deployment

Congratulations! You've built amazing React TypeScript applications throughout this course. Now it's time for the most exciting step—sharing your work with the world by deploying to production. 🌍

Think of deployment like opening a restaurant. All through development you've been cooking in a private kitchen—tasting, tweaking, throwing out the dishes that didn't work. Deployment is the night you unlock the front door and let real customers walk in. That means the food has to be plated, the lights have to work, and the kitchen has to keep running even when fifty orders come in at once. In web terms: your code gets compiled into a small, fast bundle, served from a global network of computers, secured with HTTPS, and configured so it behaves the same for every visitor. This lesson walks you through that whole journey, and by the end you'll have a live URL you can text to a friend.

The good news? Modern tooling has made this dramatically easier than it was even a few years ago. With Vite building your bundle and a platform like Vercel or Netlify hosting it, going from "works on my machine" to "live on the internet" can take under five minutes.

📖 What is Deployment?

Deployment is the process of moving your application from your local development environment to a production server where real users can access it over the internet. This involves building optimized code, configuring servers, and ensuring everything works correctly in the production environment.

🎯 Development vs Production

Understanding the differences between development and production environments is crucial:

Aspect Development Production
Goal Fast feedback, easy debugging Performance, stability, security
Build Size Large (includes dev tools) Optimized (minified, tree-shaken)
Error Messages Detailed, helpful warnings User-friendly, minimal details
Source Maps Enabled for debugging Optional or disabled
Hot Reload Enabled for fast iteration Not needed
Environment Local machine (localhost) Remote server (public URL)

📦 Creating Production Builds

Before deploying, you need to create an optimized production build of your application. This process transforms your development code into highly optimized files ready for production.

📖 What is a Production Build?

A production build is an optimized version of your application where code is minified, compressed, and stripped of development tools. This results in smaller file sizes and faster load times for your users.

🔨 Building with Vite

If you're using Vite (the recommended toolchain for React TypeScript projects in 2026—Create React App is deprecated and should not be used for new work), building is a single command:

# Build for production (runs the "build" script in package.json)
npm run build

# Preview that production build locally on a static server
npm run preview

That npm run build is just an alias. In a scaffolded Vite + React + TS project the script is tsc -b && vite build, which does two things in order:

  1. tsc -b — runs the TypeScript compiler in build mode across your project references, type-checking every file. Vite itself strips types with esbuild for speed but does not type-check, so this step is your safety net: if a type is wrong, the build fails here before a broken bundle is ever produced.
  2. vite build — bundles, minifies, tree-shakes, and hashes your assets with Rollup, writing the result to dist/.

💡 vite preview is not a production server

npm run preview spins up a tiny static server so you can sanity-check the real dist/ output on your machine. It's perfect for catching "works in dev, breaks in prod" bugs, but it is not meant to serve real traffic—that's the hosting platform's job.

The build creates a dist folder containing your optimized application:

dist/
├── assets/
│   ├── index-a1b2c3d4.js      # Your bundled JavaScript
│   ├── index-e5f6g7h8.css     # Your bundled CSS
│   └── logo-i9j0k1l2.svg      # Optimized assets
├── index.html                   # Entry point
└── favicon.ico                  # Site icon

💡 What Happens During Build?

  • Minification: Removes whitespace, shortens variable names
  • Tree shaking: Removes unused code from bundles
  • Code splitting: Creates separate chunks for better caching
  • Asset optimization: Compresses images and other assets
  • TypeScript compilation: Converts TS to optimized JS
  • CSS bundling: Combines and minifies stylesheets

⚙️ Vite Configuration

You can customize the build process in vite.config.ts:

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  
  // Build options
  build: {
    // Output directory
    outDir: 'dist',
    
    // Generate source maps for debugging
    sourcemap: false, // Set to true for debugging production
    
    // Minification (esbuild is Vite's fast default)
    minify: 'esbuild',

    // Target browsers. Vite's default is 'baseline-widely-available'
    // (features supported across all current evergreen browsers).
    // Override only if you must support something older.
    target: 'es2020',

    // Warn when any single chunk exceeds this size (kB) — a simple perf budget
    chunkSizeWarningLimit: 600,
    
    // Rollup options for advanced configuration
    rollupOptions: {
      output: {
        // Manual chunk splitting for better caching
        manualChunks: {
          'react-vendor': ['react', 'react-dom'],
          'router': ['react-router-dom'],
        },
      },
    },
  },
  
  // Base path for deployment
  base: '/', // Change if deploying to a subdirectory
  
  // Preview server configuration
  preview: {
    port: 3000,
    host: true,
  },
});

✂️ Code Splitting and Lazy Loading

By default your whole app ships as one big JavaScript file. That's fine for a small project, but as you add routes and heavy dependencies (a charting library, a rich-text editor), users end up downloading code for pages they may never visit. Code splitting breaks the bundle into smaller chunks that load on demand—like a restaurant serving courses one at a time instead of dumping the entire meal on the table at once.

In React the primary tool is React.lazy combined with <Suspense>. Vite/Rollup automatically turns every dynamic import() into its own chunk:

import { lazy, Suspense } from 'react';

// Dashboard's code is only fetched when the user actually visits it
const Dashboard = lazy(() => import('./pages/Dashboard'));

function App() {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <Dashboard />
    </Suspense>
  );
}

You can also group stable dependencies into their own long-lived chunk with manualChunks (shown in the config above). Because React and React DOM rarely change, putting them in a react-vendor chunk means returning visitors keep that file in cache across your deploys.

🗺️ Source Maps in Production

A source map is a translation table that maps your minified production code back to the original TypeScript. Without one, a production stack trace looks like a.b is not a function at index-a1b2c3.js:1:4821—useless. With one, your error monitoring tool shows the real file, line, and variable names.

💡 To ship or not to ship source maps?

Setting build.sourcemap: true emits .map files next to your bundles. The trade-off: they make debugging production errors easy, but they also expose your original source to anyone who opens DevTools. A common middle ground is sourcemap: 'hidden', which generates the maps (so you can upload them privately to Sentry) without referencing them in the shipped files.

⚠️ Common Build Issues

  • TypeScript errors: Fix all type errors before building
  • Missing dependencies: Ensure all packages are in package.json
  • Path issues: Use relative imports, not absolute paths
  • Environment variables: Configure properly (next section)
  • Large bundle size: Use code splitting and lazy loading

🎯 Build Best Practices

// package.json scripts (Vite + React 19 + TS 5.x)
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "lint": "eslint .",
    "type-check": "tsc -b --noEmit"
  }
}

A few notes on these current defaults: tsc -b uses build mode so it respects the project references that a Vite scaffold sets up (typically a tsconfig.app.json and tsconfig.node.json). And eslint . has no --ext flag because ESLint 9's flat config (eslint.config.js) decides which files to lint itself—the old --ext ts,tsx style is gone.

🔐 Environment Variables

Environment variables allow you to configure your application differently for development, staging, and production without changing code. They're essential for managing API keys, feature flags, and environment-specific settings.

📖 What are Environment Variables?

Environment variables are key-value pairs that exist outside your codebase. They let you keep sensitive information (like API keys) out of version control and configure your app for different environments without code changes.

🔑 Using Environment Variables in Vite

Vite has built-in support for environment variables through .env files:

# .env.local (for local development - NOT committed to git)
VITE_API_URL=http://localhost:3001/api
VITE_API_KEY=dev_key_12345
VITE_ENABLE_ANALYTICS=false

# .env.production (for production - committed to git)
VITE_API_URL=https://api.myapp.com
VITE_ENABLE_ANALYTICS=true
# Note: Never put secret keys in .env.production!

⚠️ Important: VITE_ Prefix Required

In Vite, environment variables must start with VITE_ to be exposed to your app. This is a security feature to prevent accidentally leaking server-side secrets into the client bundle.

❌ "Client-side env var" is a contradiction—there are no secrets here

This trips up almost everyone once. Vite does not read import.meta.env.VITE_API_KEY at runtime. During the build it textually replaces every import.meta.env.VITE_* reference with the literal string value and bakes it into your JavaScript. Anyone can open DevTools, view the bundle, and read it. So a VITE_ variable is fine for public config (an API base URL, a public analytics ID, a Stripe publishable key) but is the wrong place for any real secret. True secrets belong on a server or a serverless function that the browser calls.

📝 Accessing Environment Variables

// src/config/env.ts
interface Config {
  apiUrl: string;
  apiKey: string;
  enableAnalytics: boolean;
  environment: 'development' | 'production';
}

export const config: Config = {
  apiUrl: import.meta.env.VITE_API_URL || 'http://localhost:3001/api',
  apiKey: import.meta.env.VITE_API_KEY || '',
  enableAnalytics: import.meta.env.VITE_ENABLE_ANALYTICS === 'true',
  environment: import.meta.env.MODE as 'development' | 'production',
};

// Validate required variables
if (!config.apiUrl) {
  throw new Error('VITE_API_URL is required');
}

// Log config in development only
if (import.meta.env.DEV) {
  console.log('App Configuration:', config);
}

📖 Example: API Client with Environment Variables

// src/lib/api-client.ts
import { config } from '@/config/env';

class ApiClient {
  private baseUrl: string;
  private apiKey: string;

  constructor() {
    this.baseUrl = config.apiUrl;
    this.apiKey = config.apiKey;
  }

  async fetch<T>(endpoint: string, options?: RequestInit): Promise<T> {
    const url = `${this.baseUrl}${endpoint}`;
    
    const response = await fetch(url, {
      ...options,
      headers: {
        'Content-Type': 'application/json',
        'Authorization': `Bearer ${this.apiKey}`,
        ...options?.headers,
      },
    });

    if (!response.ok) {
      throw new Error(`API Error: ${response.statusText}`);
    }

    return response.json();
  }

  async get<T>(endpoint: string): Promise<T> {
    return this.fetch<T>(endpoint);
  }

  async post<T>(endpoint: string, data: unknown): Promise<T> {
    return this.fetch<T>(endpoint, {
      method: 'POST',
      body: JSON.stringify(data),
    });
  }
}

export const apiClient = new ApiClient();

☁️ Deployment Platforms Overview

There are many platforms for deploying React applications. Let's compare the most popular options to help you choose the right one for your needs.

📖 First, know what you're shipping: SPA vs SSR/RSC

Everything we build in this lesson is a single-page application (SPA): vite build produces static files (HTML, JS, CSS) that any file host can serve, and React renders the UI in the browser. This is simple, cheap, and works on every host on the list below.

The main alternative is server-side rendering (SSR) and React Server Components (RSC), which render your components on a server per request. In 2026 the standard way to build those is a full framework like Next.js (App Router) or Remix/React Router in framework mode—not raw Vite. SSR/RSC gives faster first paint and better SEO for content-heavy sites, at the cost of needing a running server (or edge runtime) rather than plain static files. If your app is behind a login (a dashboard, a tool), a Vite SPA is usually the right, simpler choice.

💡 Decision Factors

  • Use Vercel if: You want the best Next.js support or need edge functions
  • Use Netlify if: You need built-in forms or A/B testing features
  • Use GitHub Pages if: You want simple, free hosting from your repo
  • Use Cloudflare Pages if: You need global CDN performance
  • Use AWS Amplify if: You're already using AWS services

⚡ Cloudflare Pages and Plain Static Hosts

Cloudflare Pages deserves a special mention: its free tier has unlimited bandwidth and its CDN is one of the fastest in the world. Deploying is the same story as Vercel/Netlify—connect the Git repo and set:

Build command:      npm run build
Build output dir:   dist

The same static dist/ folder also works on GitHub Pages, Amazon S3 + CloudFront, Firebase Hosting, or any web server. The one gotcha that bites every SPA on a plain host is client-side routing: when a visitor reloads /dashboard, the server looks for a /dashboard file, finds nothing, and returns a 404. The fix is a SPA fallback—tell the host to serve index.html for any path it doesn't recognize, and let React Router take over. Vercel and Netlify configure this for you; on Cloudflare Pages add a public/_redirects file:

# public/_redirects  (works on Cloudflare Pages and Netlify)
/*    /index.html   200

We'll revisit this "404 on refresh" problem, and the fix for every platform, in the Troubleshooting section.

🐳 Optional: Containerizing a Static Build with Docker

You rarely need Docker for a plain SPA—managed platforms are simpler. But if your organization deploys everything as containers (to Kubernetes, AWS ECS, Fly.io, etc.), you can wrap the static build in a tiny image. The pattern is a multi-stage build: one stage compiles with Node, a second stage copies only the finished dist/ into a lightweight Nginx image.

# Dockerfile
# --- Stage 1: build ---
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# --- Stage 2: serve ---
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
# SPA fallback: send unknown routes to index.html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

The nginx.conf just needs the same SPA fallback idea—try_files $uri $uri/ /index.html;—so deep links survive a refresh. The final image is only a few megabytes because it contains your static files plus Nginx, not Node or your node_modules.

▲ Deploying to Vercel

Vercel is one of the most popular platforms for deploying React applications. Created by the makers of Next.js, it offers an exceptional developer experience with zero-configuration deployments.

📖 Why Vercel?

Vercel specializes in frontend frameworks and offers the fastest way to deploy React applications. It handles everything from building your app to serving it on a global CDN, all with automatic HTTPS and preview deployments.

🚀 Deploying Your First App to Vercel

Step 1: Prepare Your Repository

# Ensure your code is in a Git repository
git init
git add .
git commit -m "Initial commit"

# Push to GitHub (or GitLab/Bitbucket)
git remote add origin https://github.com/yourusername/your-repo.git

Step 2: Sign Up for Vercel

  1. Go to vercel.com
  2. Click "Sign Up"
  3. Choose "Continue with GitHub" (recommended)

  1. Click "Add New Project"
  2. Select your repository from the list
  3. Vercel auto-detects Vite and configures build settings
  4. Click "Deploy"

✅ What Vercel Detects Automatically

  • Framework: Vite (from package.json)
  • Build Command: npm run build
  • Output Directory: dist
  • Node Version: Latest LTS (Node 20 or 22 in 2026)

⚙️ CI/CD with GitHub Actions

Continuous Integration and Continuous Deployment (CI/CD) automate testing and deployment. Every time you push code, your tests run automatically, and if they pass, your app deploys to production.

📖 What is CI/CD?

CI/CD is the practice of automating your development workflow. Continuous Integration (CI) runs tests on every commit. Continuous Deployment (CD) automatically deploys passing code to production.

🎯 Why Use CI/CD?

✅ Benefits

  • Catch bugs early: Tests run automatically on every commit
  • Consistent builds: Same process every time
  • Faster releases: Deploy with confidence, no manual steps
  • Team coordination: Everyone follows the same workflow
  • Rollback capability: Easy to revert if something goes wrong

GitHub Actions is a CI/CD platform built into GitHub. It runs workflows defined in YAML files:

# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# Allow manual trigger
  workflow_dispatch:

jobs:
  # Job 1: Test
  test:
    runs-on: ubuntu-latest
    
    strategy:
      matrix:
        node-version: [20, 22]
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Use Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      
      - name: Install dependencies
        run: npm ci
      
      - name: Run tests with coverage
        run: npm run test:coverage
      
      - name: Upload coverage to Codecov
        uses: codecov/codecov-action@v4
        with:
          files: ./coverage/coverage-final.json
          token: ${{ secrets.CODECOV_TOKEN }}
  
  # Job 2: Build and Deploy
  deploy:
    needs: test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      
      - name: Install dependencies
        run: npm ci
      
      - name: Build
        run: npm run build
        env:
          VITE_API_URL: ${{ secrets.VITE_API_URL }}
          VITE_API_KEY: ${{ secrets.VITE_API_KEY }}
      
      # Deploy to Vercel
      - name: Deploy to Vercel
        uses: amondnet/vercel-action@v20
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          vercel-args: '--prod'

💡 You often don't need a deploy step at all

The workflow above uses a community action to push to Vercel. It's useful when you want full control, but for most projects the simplest, most reliable path is Vercel's or Netlify's native Git integration: connect the repo once in the dashboard and the platform builds and deploys on every push automatically. In that setup your GitHub Actions workflow only needs to test (type-check, lint, unit tests)—let the platform own the deploy. Reach for a custom deploy action only when the platform's built-in flow can't do what you need.

📈 Performance Monitoring

After deployment, it's crucial to monitor your application's performance in production. Real users experience different conditions than your local development environment.

📖 Why Monitor Production?

Performance monitoring helps you understand how your app performs for real users. It tracks metrics like load time, errors, and user interactions, allowing you to identify and fix issues quickly.

📊 Key Metrics to Monitor

Metric What It Measures Good Target
LCP (Largest Contentful Paint) Loading performance < 2.5s
INP (Interaction to Next Paint) Interactivity / responsiveness < 200ms
CLS (Cumulative Layout Shift) Visual stability < 0.1
TTFB (Time to First Byte) Server response < 600ms
FCP (First Contentful Paint) Perceived load speed < 1.8s

⚠️ FID is gone—INP is the Core Web Vital now

You'll still see First Input Delay (FID) mentioned in older tutorials, but in March 2024 Google replaced it with Interaction to Next Paint (INP). FID only measured the delay before the first interaction; INP measures responsiveness across the whole visit, so it's a much better signal for a React app where re-renders can make later clicks feel sluggish. The web-vitals library (v4+) reflects this—onFID no longer exists, and you call onINP instead.

📱 Real User Monitoring (RUM)

Track real user experiences:

// Custom RUM implementation
class RUM {
  private metrics: Map<string, number> = new Map();

  trackPageView(path: string) {
    // Track page views
    this.sendEvent('pageview', { path });
  }

  trackError(error: Error) {
    // Track JavaScript errors
    this.sendEvent('error', {
      message: error.message,
      stack: error.stack,
    });
  }

  trackPerformance() {
    // Track performance metrics
    const navigation = performance.getEntriesByType('navigation')[0] as PerformanceNavigationTiming;
    
    this.metrics.set('dns', navigation.domainLookupEnd - navigation.domainLookupStart);
    this.metrics.set('tcp', navigation.connectEnd - navigation.connectStart);
    this.metrics.set('ttfb', navigation.responseStart - navigation.requestStart);
    this.metrics.set('download', navigation.responseEnd - navigation.responseStart);
    this.metrics.set('domInteractive', navigation.domInteractive - navigation.fetchStart);
    this.metrics.set('domComplete', navigation.domComplete - navigation.fetchStart);
    
    this.sendMetrics();
  }

  private sendEvent(name: string, data: any) {
    // Send to your analytics backend
    fetch('/api/analytics', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ event: name, data }),
    });
  }

  private sendMetrics() {
    // Send collected metrics
    fetch('/api/metrics', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(Object.fromEntries(this.metrics)),
    });
  }
}

export const rum = new RUM();

// Usage
rum.trackPageView(window.location.pathname);
rum.trackPerformance();

// Example: Monitor and alert on poor performance
import { onLCP, onCLS } from 'web-vitals';

function checkPerformance() {
  onLCP((metric) => {
    if (metric.value > 2500) {
      // Alert: Poor LCP
      sendAlert({
        metric: 'LCP',
        value: metric.value,
        threshold: 2500,
        severity: 'warning',
      });
    }
  });

    if (metric.value > 0.1) {
      // Alert: Poor CLS
      sendAlert({
        metric: 'CLS',
        value: metric.value,
        threshold: 0.1,
        severity: 'warning',
      });
    }
  });
}

🔧 Troubleshooting Common Issues

Deployment doesn't always go smoothly. Here are solutions to common problems you might encounter.

❌ Problem: Build Fails

Error Message

Error: Command "npm run build" exited with 1

Common Causes & Solutions

  • TypeScript errors: Run npm run type-check locally and fix all errors
  • Missing dependencies: Ensure all packages are in package.json, not just devDependencies
  • Different Node versions: Specify Node version in deployment config
  • Environment variables missing: Check that all required env vars are set

❌ Problem: 404 on Refresh

Issue

App works fine when navigating from home, but refreshing on a route (e.g., /about) gives 404 error.

Solution: Configure Redirects

For Vercel:

// vercel.json
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/" }
  ]
}

For Netlify:

# netlify.toml
[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

Or create public/_redirects:

/*    /index.html   200

❌ Problem: Environment Variables Not Working

Common Issues

  • Missing VITE_ prefix: All client-side env vars must start with VITE_
  • Not set on platform: Environment variables must be configured in deployment platform UI
  • Quotes in values: Don't use quotes around values in platform UI
  • Not rebuilding: Changes to env vars require a new deployment

Debug Steps

// Add this temporarily to check
console.log('Environment:', import.meta.env);
console.log('API URL:', import.meta.env.VITE_API_URL);

❌ Problem: Slow Build Times

Optimization Strategies

  • Cache dependencies: Most platforms cache node_modules by default
  • Reduce bundle size: Use code splitting and tree shaking
  • Skip unnecessary steps: Don't run tests in production builds
  • Use faster package manager: Try pnpm instead of npm
// Speed up npm ci
{
  "scripts": {
    "build": "npm ci --prefer-offline && vite build"
  }
}

❌ Problem: Images Not Loading

Common Causes

  • Wrong path: Use relative paths or import statements
  • Case sensitivity: Linux servers are case-sensitive (Image.png ≠ image.png)
  • Not in public folder: Static assets should be in public/
  • Base path issue: Check base config in vite.config.ts

Correct Approaches

// ✅ Import the image
import logo from './assets/logo.png';
<img src={logo} alt="Logo" />

// ✅ Use public folder
<img src="/images/logo.png" alt="Logo" />

// ❌ Don't use absolute paths
<img src="C:/Users/me/project/logo.png" alt="Logo" />

❌ Problem: API Requests Failing

CORS Issues

If API requests work locally but fail in production:

  • Backend CORS: Configure your API to allow requests from your domain
  • Use proxy: Configure Vite proxy for development
  • Use serverless functions: Netlify/Vercel functions can act as proxy
// vite.config.ts - Development proxy
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3001',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },
});

❌ Problem: Large Bundle Size

Reduction Strategies

# Analyze bundle
npm install --save-dev rollup-plugin-visualizer
npm run build
  • Lazy load routes: Use React.lazy() for route components
  • Remove unused dependencies: Check with depcheck
  • Use lighter alternatives: Replace heavy libraries (e.g., moment.js → date-fns)
  • Tree shake properly: Import specific functions, not entire libraries
// ❌ Bad - imports entire library
import _ from 'lodash';

// ✅ Good - imports specific function
import debounce from 'lodash/debounce';

// ✅ Even better - use native methods when possible
const debounce = (fn: Function, ms: number) => {
  let timeout: NodeJS.Timeout;
  return (...args: any[]) => {
    clearTimeout(timeout);
    timeout = setTimeout(() => fn(...args), ms);
  };
};

🛠️ General Debugging Tips

✅ Debugging Checklist

  1. Check build logs: Read the entire error message carefully
  2. Build locally first: Run npm run build and npm run preview
  3. Clear cache: Try clearing platform's build cache
  4. Check environment: Verify all required env vars are set
  5. Verify dependencies: Make sure package.json is correct
  6. Test in production mode: Some issues only appear in production builds
  7. Check browser console: Look for JavaScript errors
  8. Verify routes: Test all routes and page refreshes
  9. Check network tab: See if assets are loading correctly
  10. Compare with working version: Look at what changed since last successful deploy
